# The allocator of the C engine

The allocator of the C engine in `engine/`. The Go host and the native test host (`engine/test/`) both use it.

## Layers

```
js_malloc, js_free, js_realloc, js_malloc_usable_size (and the _rt forms)
  front cache: 32 lists of up to 256 freed small blocks       quickjs.c
  cache of large blocks: 57 lists of up to 8 freed blocks     quickjs.c
    of 505 to 4096 bytes, JS_LARGE_CACHE_BYTES in all
  small blocks, 16 to 512 bytes: arenas of 4 KiB               quickjs.c, as upstream
  arenas and every block over 504 bytes: TLSF                  tlsf.c
  chunks, counts, limit, budget, resize, release               heap.c
host_memory_grow, host_call (memory release, remap)            the host
```

- The small block layer is upstream's: 31 size classes, an 8 byte header per block, and the reference count 4 bytes before the user data of every block (`JS_BLOCK_REF_COUNT_OFFSET` in `quickjs.h`, checked against `JSMallocBlockHeader`). Heap memory is 8 byte aligned.
- The front cache keeps freed small blocks on a list of their class, so that the next block of that class takes no arena. `JS_RunGC`, `JS_RunYoungGC`, `JS_ReleaseStart` and `JS_FreeRuntime` give it back to the arenas, and so does an allocation the heap fails: the cache goes back to the arenas and the heap is asked once more. A request refused before it reaches the heap (size 0, a size over the maximum) does not do that. `JS_SetFrontCache(rt, max)` gives the cache back and sets the length of a list (0 to 256, 0 for no cache). The cache of large blocks (below) is given back at the same moments, and `JS_SetFrontCache(rt, 0)` turns it off too.
- A large block is a TLSF block with an 8 byte header in front. TLSF grows it in place when the next block is free.
- All state is in the runtime. The runtime sits in the first chunk, so there is no global, no lock and no system call. The heap asks the host for `host_memory_grow(vm, size)`: `size` bytes, a multiple of 64 KiB, read and write, page aligned, not zeroed, or 0 when the system has none. For a dedicated chunk (see Chunks) it also uses two kinds of `host_call` (`engine/host.h`), which run no user code and do not call back into the engine: `HOST_CALL_MEMORY_RELEASE` (address, size) gives a chunk back, and `HOST_CALL_MEMORY_REMAP` (address, old size, new size) makes it bigger. Both pass the exact address and size of the chunk the host has.

## What is counted

- `count` (`JS_GetMemorySize`, `malloc_size` of `JS_ComputeMemoryUsage`) is the size of the runtime plus, for each block in use, its TLSF block size and the 8 byte size word before it. An arena counts whole, slots in the front cache included. A freed large block that waits in the cache of large blocks counts too (see below). Free memory and chunk headers do not count. `count` is what the memory limit and the GC threshold use.
- The memory limit (`JS_SetMemoryLimit`) fails an allocation when `count` plus the size asked for (the arena, or the user size plus the 8 byte header) passes it, then counts the real block. A resize is checked as upstream checks it: `count` plus the new size, less the usable size of the old block, against the limit (the old block does not count twice, and its 8 byte word stays in `count`, since the block is still a block). Once the resize is done, `count` changes by the difference of the two usable sizes. Lowering the limit frees nothing. A failure makes the engine throw out of memory.
- The footprint is what the VM took from the host, the sum of its chunks. `JS_SetFootprintLimit` bounds it, 0 for none. It only stops growth: a VM that holds more keeps it, and nothing is taken back by it. It covers the chunks only, not the shadow stack, shared bytecode or the Go side. There is no default.
- TLSF rounds a block up by at most 1/32, where the allocator of the previous engine, the one ccgo made, rounded to a power of two, so `count` is about 13% to 15% lower than that engine's `MemorySize` was for the same heap. Against glibc's malloc in the C tree it is the same within 1.3%: after 3000 renders of tifa's pages the shop holds 39.84 MB against 39.85, the MUI test app 29.91 against 29.52, the bench app 2.15 against 2.12.

## Chunks

- The first chunk is 64 KiB and holds the runtime, the TLSF control and the first pool. Later chunks are a quarter of the footprint, 64 KiB to 8 MiB, a multiple of 64 KiB. Near the budget a shared chunk shrinks to what the request needs (with the room TLSF needs to find it, `need + need/32 + 112 + 64`, rounded up to 64 KiB), and is refused when even that does not fit.
- A request of more than half of the next chunk (so over 4 MiB for good) gets a dedicated chunk. A dedicated chunk is flagged in its header (`kind`), holds one block, and is not under TLSF: the 32 byte header, the size word of the block, the block (rounded up to 8 bytes), an end marker, and room up to the next 64 KiB, which the block can grow into and nobody else gets. The block counts by its size, not by the room. `heap_check` and `heap_contains` know both kinds.
- When the block of a dedicated chunk is freed, or `heap_realloc` moves it, the chunk goes back to the host in that call (`HOST_CALL_MEMORY_RELEASE`). The heap takes the chunk out of its lists and counts first, then asks, and never reads the chunk again. There is no cache of freed dedicated chunks. A resize gets the new block and copies before it gives the old chunk back.
- A block that fits its chunk and uses at least half of it stays in it. When it outgrows the chunk and the host says it can remap (`JS_SetHostRemap(rt, 1)`, right after `JS_NewRuntime`, linux), the heap checks the budget for the growth alone and asks the host to remap the chunk (`HOST_CALL_MEMORY_REMAP`, `mremap` with `MREMAP_MAYMOVE`), which keeps the content and may change the address. The host refusing is out of memory: the resize fails and nothing changes, there is no copy. Without remap, or when the block shrinks under half of its chunk, the heap takes a new block, copies and gives the old chunk back. A block that is growing gets an eighth of its size as room in its new chunk, so a buffer that grows a little at a time does not get a new chunk, a copy or a system call at each step (the budget may take that room away).
- A resize that cannot grow in place or move inside the chunks needs a new chunk while the old block still sits in its chunk, so the budget can refuse a resize that the count allows. A refused resize leaves the old block, its address, its content and its usable size as they were, and the heap's `count` too. At the runtime, a failed request first gives the front cache back, which can empty arenas and lower `count`, so only the heap alone promises the count of a refused call.
- The largest request is 2^32 - 8 bytes: bigger ones fail before any arithmetic on the size.

## Giving memory back

Dedicated chunks are given back at once (see Chunks). Shared chunks are not: nothing of them is given back unless the host asks. `JS_ReleaseStart(rt, keep)` first gives the front cache and the cache of large blocks back to the heap, then plans to offer all the free memory but `keep` bytes. `JS_ReleaseNextChunk` then returns whole free chunks (not the first), largest first, taken out of the heap and out of the footprint, until its length is 0. `JS_ReleaseNextRange` returns the inside of free blocks of 4 KiB or more, which the host may drop the pages of: TLSF never reads it, it only writes there when it splits or merges a block. The host does not use the runtime in between, unmaps the chunks and rounds each range inward to its page size. A range may be offered again by a later release. `release_candidate` of `JS_ComputeMemoryUsage` totals what was offered. `keep` is a target and not an exact amount: chunks are counted by their whole size, ranges by what is left of a free block without its TLSF words, and a range is at least 4 KiB, so one big free block can take the total past the target.

A buffer that grows by realloc past half a chunk used to leave a chain of empty chunks behind it, mapped until a release: a string of 1 GiB built in 1 MiB steps (`staging/sm/String/replace-math.js`) took 6.7 GB. With dedicated chunks it takes 1.05 GB in 1.2 seconds with remap (the old C tree on glibc: 1.09 GB, 1.2 seconds) and 2.0 GB in 4.5 seconds without it, where the old chunk waits for the copy to end.

## The cache of large blocks

A large block of 505 to 4096 bytes that is freed waits in a list of its class, and the next request of that class takes it, with no work in TLSF. The strings and buffers a script builds are of these sizes, made and thrown away in turn, and TLSF takes a bitmap lookup, a split and a merge for each. The cache is in `quickjs.c` next to the front cache and is on while the front cache is: `JS_SetFrontCache(rt, 0)` turns both off, any other value leaves the large cache as it is.

- **Classes.** One class for each 64 bytes, 57 of them. A request of 505 to 4096 bytes is rounded up to a multiple of 64 while the cache is on, so the block it gets files under the class it will be asked for again (a block of 1000 bytes has room for 1024). A block files under its usable size divided by 64, rounded down, whatever it was asked for: a block that was resized, or that TLSF gave a little more, serves the classes up to its size. A block under 512 or over 4159 usable bytes goes to the heap when it is freed.
- **Limits.** A class keeps at most 8 blocks (`JS_LARGE_CACHE_N`) and all the classes together at most 256 KiB (`JS_LARGE_CACHE_BYTES`), counted as the sizes TLSF gave the blocks, header of 8 bytes included. A block that would pass either goes to the heap at once, and nothing is evicted to make room. The 256 KiB are for each runtime, and tifa runs several in a process: n runtimes keep at most n times 256 KiB. Why 256 KiB: hits counted on the 37 scripts of the speed tests. At 128 KiB the string builders lose 4 to 8 points (`c_string_concat` hits 67% of its large requests against 75% with no cap, the React page 93% against 97%). At 256 KiB all but `v8_regexp` are within one point of no cap, and above it only `v8_regexp` gains (3% at 256 KiB, 8% at 1 MiB). Between 4 and 32 blocks a class the hits hardly change. 256 KiB is 0.6% of the 40 MB that the biggest app of tifa holds after 3000 renders, and 12% of the 2 MB of the smallest.
- **What is counted.** A cached block is a block in use as far as the heap goes. `count` (MemorySize and the GC threshold), `blocks` (`malloc_count` of `JS_ComputeMemoryUsage`) and the memory limit all count it, and `heap_check` finds it among the blocks in use, with the same sums as for any other block. `JS_CheckMemory` adds what the heap cannot see: each block of the cache is a large block of the heap, filed under its class, and the counts of the lists and `large_bytes` are what the lists hold. Taking a block out of the cache or putting one in changes none of these counts: the cost of a block is counted when the heap gives it and taken off when the heap gets it back.
- **The memory limit.** A request that the cache can serve adds nothing to `count`, so the limit does not look at it, even when `count` is over the limit (it can be lowered under `count`). A request that goes to the heap and is refused, whether by the limit, the footprint budget or the host, gives back both caches and asks the heap once more, as for the front cache. So cached blocks never make a request fail on their own, and a request that fails leaves both caches empty. A request in the range is asked of the heap at its rounded size, up to 63 bytes more, and the limit sees that size.
- **Given back.** `JS_SetFrontCache` (with any value), `JS_RunGC`, `JS_RunYoungGC`, `JS_ReleaseStart` (before it plans what to offer, so the chunks that held cached blocks can be free), `JS_FreeRuntime` (before it counts the blocks left, so cached blocks are not leaks), and every failed request or resize that reaches the heap. A dedicated chunk is never in the cache: its blocks are over 4 MiB.
- **Poison.** In `asan-heap` a block that enters the cache is poisoned whole, and the poison comes off when it is taken. The link to the next block is in the first 8 bytes of the block, and is opened only for the moment the cache reads or writes it, so the first bytes of a cached block are found too, unlike those of the front cache. `asan` (every block from the system malloc) has no large cache, since its point is that each block stands alone.

## TLSF

`engine/tlsf.c` and `engine/tlsf.h` are Matthew Conte's TLSF 3.1 (BSD-3-Clause, see `NOTICE.md`) at commit `deff9ab509341f264addbd3c8ada533678591905` (`tlsf.c` SHA-256 `2a0f8cfc9cfe6114ccdc6cf22339059440b16f1149b5107bead4ae4c3a0d50e2`, `tlsf.h` `f7f73c48810ba60203095667c226e5a600a6ea0f69afba48efff6efbaa628d4f`, both with CRLF line ends), converted to LF, and changed in these ways:

- A request or pool TLSF cannot hold fails (issues 9, 22 and 35 of the project). `engine/test/tlsf-edges.sh` runs the edge cases on the pinned file, where four fail or crash, and on `engine/tlsf.c`, where all pass.
- No `stdio.h`, `stdlib.h`, debug self test or `tlsf_memalign`.
- Four functions for the heap: `tlsf_realloc_inplace` (resize without moving), `tlsf_next_free` (walk the free blocks, largest class first), `tlsf_free_inside` (the part of a free block TLSF never reads) and `tlsf_pool_is_free`.

## Testing

All of it runs on the native test host (see [testing.md](testing.md#the-c-tree-and-its-native-test-host)).

```sh
engine/test/tlsf-edges.sh                    # TLSF edge cases, pinned file and engine/tlsf.c
engine/test/build.sh plain                   # also asan-heap, asan-heap-iter, ubsan
engine/test/heap.sh -m plain                 # scenarios and random sequences, heap and runtime
engine/test/build.sh fuzz && engine/test/heap.sh -m plain -f 300   # the libFuzzer target
engine/test/build.sh asan                    # every block from the system malloc, with LeakSanitizer
engine/test/build.sh asan-heap               # the real allocator, free memory poisoned
engine/test/heap.sh -m asan-heap             # also poison-test: what the poison covers
engine/test/build.sh asan-heap-iter          # the same with JS_MALLOC_USE_ITER, which keeps a list of every allocated block
engine/test/heap.sh -m asan-heap-iter        # the macro must keep building and passing
engine/test/host-test.sh tsan                # the test host, make and free runtimes on two threads
```

- `heap-test.c` has a fake host that maps chunks, can refuse the nth request, and fills every range given back with 0xdd. Every block holds a pattern, checked when it is freed or resized. Every few thousand steps `heap_check` and `JS_CheckMemory` (compiled in with `JS_HEAP_CHECK`) walk TLSF, the arenas, the front cache and the cache of large blocks, and the test compares the counts with the sum over the blocks it holds. The random runs on the runtime ask for sizes in the range of the large cache too, count the cached blocks in what a failed request must give back, and judge a refusal by the size the request has once rounded to its class. A count that test builds keep (`JS_LargeCacheHits`) tells when the cache served a request, which must then have taken one block from it. `scenario_large_cache` holds the rules of the next section to the byte.
- In `asan-heap` the engine poisons the user bytes of free small slots, free TLSF payloads, the rest of an arena, the cached small blocks (all but the next pointer) and the blocks of the cache of large blocks (all of them: the link in the first 8 bytes is opened only while the allocator reads or writes it), so a use after free inside our own memory is found. `heap.c` and `tlsf.c` are built without AddressSanitizer there, since the poison is theirs to put and take. `poison-test.c` (run by `heap.sh -m asan-heap`) asks AddressSanitizer which bytes are poisoned, and runs itself as child processes that read and write a freed block of the cache of large blocks (in the middle, in the link, at the end) and checks that AddressSanitizer reports each, and that a child that uses a live block or one taken from the cache again exits with status 0, its error output read whole, and no report of any kind. What the poison does not cover: the 8 byte header of the slot after a live small block stays readable, since the allocator reads and writes headers, so an overrun of up to 8 bytes there is not found. Neither is an overrun into another live block, nor the next pointer of a cached block (for a block of 8 bytes, its whole user area). `asan` does find those, with red zones around every block, but it has no arenas and no front cache. Run both.
- `host-test.c` tests the host alone against stubs of the engine: a runtime that does not start leaves no VM and no chunk, and two threads that make and free runtimes do not race (`engine/test/host-test.sh tsan` builds it with ThreadSanitizer).
- Dedicated chunks: `heap-test` has a scenario for them (made for one block, given back in the call that frees it, resized in the chunk and out of it, refused by the host, the budget and the limit with the old chunk intact) and one for remap (the host refusing is out of memory and nothing is copied, the budget is checked for the growth alone, a buffer that grows by 64 KiB gets few chunks). Its random runs give dedicated chunks back and remap them (odd seeds, where the fake host remaps), and fail when they do not.
- The fake host remaps in two ways: `mremap` (linux), and a new mapping, a copy and an unmapping of the old chunk, which always puts the chunk at another address and works on every system (on linux the heaps of a run take turns, and macOS has the second only). One scenario grows the block at the head, in the middle and at the tail of the list of dedicated chunks, by each way and after a refusal of the host, then frees the three in each of the six orders with `heap_check` between, so that a list that kept the address of a chunk that moved walks into an unmapped chunk.
- The random runs judge a refusal by the footprint budget with the rules of the chunks, not by a pool of TLSF. The least a request adds is the chunk it gets (its own, or the shared one it shrinks to), a remapped chunk needs its growth alone, and a block that stays in its chunk or gets smaller needs nothing. The runs on the runtime judge the growth of a large block by the same rules, with the size of the dedicated chunk it is in. A scenario holds the rules to the byte for a new chunk, a remap, a copy and a move from the shared chunks: one unit under the least growth the request is refused, with the host not asked and nothing changed, and at it the request passes. Another asks for the biggest request, `JS_HEAP_MAX_REQUEST` (nearly 4 GiB, mapped sparse, with only the first and the last 64 bytes written), which a host that refuses nothing must give whole, and one byte over, which the heap refuses with the host not asked. `api-test` does the same on the real native host: the chunks it maps are counted right after a malloc, a resize and a free.
- A runtime must end with `JS_FreeRuntime` returning 0. It returns the number of blocks of the heap still in use, an arena counting as one block however many of its slots are in use, so it is not a count of leaked objects. The test host exits with status 87 otherwise.
- `engine/test/render.c` renders tifa's pages on the C tree and, with `soak=N`, prints the count, blocks and footprint every 100 renders.
