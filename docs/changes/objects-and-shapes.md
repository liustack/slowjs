# Objects and shapes

A shape is the list of an object's keys in order, shared by objects with the same keys.

## New properties of plain objects skip the generic path

Release: v0.26.13.

Defining a new property on a plain object costs less. Every other case takes the old path, and so does assignment (`o.x = v`, `Object.assign`). Nothing is cached, so memory use is the same. A property of an object literal takes about 55 ns rather than 95 on linux/amd64 (AMD EPYC), and a server render of a page of tifa's example shop about 6% less, with the same HTML.

The change is in C (`engine/quickjs.c`), at the start of `JS_DefinePropertyValue`. `engine/test/compare.sh` runs `testdata/objlit.js`.

## Kept shapes

Release: v0.26.16.

A VM keeps the shapes of plain objects once their objects are gone. The shape of an object is its keys in order, and an object literal goes through one shape for each key. `add_property` grew a shape in place when only its object used it, so the shapes in between were gone once the object had its keys, and the last one went with the last object: the next literal with the same keys copied and grew them all again. The next literal with the same keys finds every shape it needs in the shape hash table, and makes none. The times in this entry were all taken without PGO, on linux/amd64 (AMD EPYC). A copy costs an allocation and the keys so far, which an object that gets keys no other object has, one at a time, pays for each key and never gets back: such objects took 22% longer to build. So each shape `add_property` finds earns one copy, up to 64, and without credit the shape grows in place. The shapes in between are then still kept, only later: the shape an object leaves when it finds the next one kept is kept. Objects of keys no other object has now take about 6% longer to build than with the cache off, and object literals with the same keys 30% less. Only shapes whose prototype is the `Object.prototype` of the VM, that have at most 32 keys and no key that is a symbol not registered are kept, so a kept shape holds nothing alive but that prototype and the atoms of its keys, and a `WeakRef` or `FinalizationRegistry` whose target is a symbol sees it go as it would without the cache. Shapes the cycle collector frees are not kept, and `JS_FreeRuntime` lets every kept shape go. The ring is in the state of the runtime, next to the front cache (see [allocator.md](../allocator.md)). A new VM keeps `DefaultShapeCache` (2048) shapes, `VM.SetShapeCache` changes it, and `VM.Close` turns it off before it frees the context.

Memory: one VM of the shop holds 647 KiB more after a GC, and with the front cache as well 722 KiB more (8.03 MiB rather than 7.33). With 1024 shapes it was 190 KiB and 461 to 502 KiB more, and with 4096 shapes and the front cache 1.26 MiB more. How the blocks fall in the arenas moves these by up to 0.5 MiB from one run to another, with the same shapes and objects left. Loading the shop's bundle alone keeps about 1250 shapes, so a ring of 1024 is full before the first render. Kept shapes count against the memory limit of the VM, and they are not let go when an allocation fails: an allocation in `add_property` can come right before the object takes a shape that only the cache holds. A shape of 32 keys of about ten characters, that no other object has, takes about 3 KiB with the atoms of its keys, so 2048 of them take about 6 MiB, and the atom table keeps the size it grew to after they go. A script that runs close to its memory limit can run out of memory with the cache on where it would not without it: give such a VM a smaller cache, or none. Without PGO, on linux/amd64 (AMD EPYC), with the same HTML, the shape cache alone makes a render 3.6% faster, and with the front cache and the interrupt countdown a render takes 4.5% less time than without the three (six rounds). Two VMs on two hardware threads of one core render 2.9% more pages a second.

The change is in C (`engine/quickjs.c`): the field `shape_cache` of `JSRuntime`, `js_shape_keep` in `js_free_shape0`, `js_shape_keepable` and `js_shape_found` in `add_property`, `JS_SetShapeCache(ctx, n)` in `quickjs.h`, and `JS_FreeRuntime` lets every kept shape go. It is off until `JS_SetShapeCache` turns it on. `js_shape_keep` returns the shape it lets go of when the ring is full, which `js_free_shape0` then frees, rather than freeing it itself. The native runners (`jsrun` and `run-test262`) keep 2048 shapes, as a new VM does. It also checks that a full and a young collection leave the kept shapes, that the cycle collector frees the shapes of the cycles it frees, that a full ring lets its oldest shapes go, that a runtime freed with kept shapes frees them and its context, and that an allocation that fails leaves the ring whole.

## for in skips prototypes with no enumerable property

Release: v0.26.17.

A `for in` loop no longer lists the property names of each prototype to find out that it has no enumerable property. When a loop runs out of the object's own properties, the engine checks the objects of its prototype chain for enumerable string keys, to know whether it must walk the chain. It did that with `JS_GetOwnPropertyNamesInternal`, which mallocs a list, takes a reference to each name and frees it all again, in every loop and for every prototype, mostly for `Object.prototype`, which has dozens of names and none of them enumerable.

Why this is safe: for an object that is not exotic, `JS_GetOwnPropertyNamesInternal` with these flags counts only shape properties with a name, the enumerable flag and a string key, calls no method of the class and throws for nothing it does not count, so with no such property its list is empty. `forInNoEnum` answers no for every exotic object (arrays, `String` objects, proxies, ...) and for every object with an enumerable property, symbols included, and the engine lists the names as before, so the traps of a proxy in the chain run as they did. The only difference is out of memory: the empty list needs no memory, where the engine mallocs one entry, so with no memory left the loop goes on where it used to fail. It pins the text of `js_for_in_prepare_prototype_chain_enum`, `JS_GetOwnPropertyNamesInternal`, `get_shape_prop` and `JS_FreePropertyEnum` by fingerprints (`forInSites`).

On linux/amd64 without PGO, against v0.26.16 over 10 rounds, the spiral page of tifa's bench app, which runs many for in loops, renders in 0.983 of the time (a wide range, 0.888 to 1.041) and the table page in 0.971 (0.871 to 1.035). tifa's example shop barely changes (0.996, 0.987 to 1.001), nor do the MUI pages. The HTML and the memory of a VM stay the same.

The change is in C (`engine/quickjs.c`): `js_for_in_prepare_prototype_chain_enum` calls `js_for_in_no_enum` first. `engine/test/compare.sh` runs `testdata/forin.js`.

## String keys that are already atoms

Release: v0.26.17.

A string key that is already an atom costs less. On the pages of tifa's example shop, 92% of the strings `JS_ValueToAtom` gets are such atoms. Every other string, numbers and symbols take the generic path, and a number does not even make the call. Nothing is cached, so memory use is the same.

On linux/amd64 without PGO (AMD EPYC 7B13, one core), against v0.26.16, a micro benchmark reads with a string key in 13% less time, writes in 30% less, runs `k in o` in 26% less and `hasOwnProperty(k)` in 14% less, and a server render of a page of the shop takes 1.3% less time (median of 6 rounds, 0.9% to 1.5% over the rounds), with the same HTML. These were measured before the [for in](#for-in-skips-prototypes-with-no-enumerable-property), bitwise and comparison changes (see [operators.md](operators.md)).

The change is in C (`engine/quickjs.c`), at the start of `JS_ValueToAtom`: such a string returns `JS_DupAtom` of its own index. `engine/test/compare.sh` runs `testdata/atom_keys.js`, and `engine/test/unit.c` checks that an atom made from a string at run time and used as a key many times is freed with the last value that holds it.

## New functions get length and name at once

Release: v0.26.17.

A new function gets its `length` and `name` without the shapes in between. `js_function_set_properties` gave every new function the two through `JS_DefinePropertyValue` and `add_property`, one at a time: the function went from the empty shape of its prototype, through a shape with `length` only, to the shape with both. Nothing held the empty shape or the one with `length` only for long, so they were made again for each function and freed again a moment later (3,000 arrows, methods and constructors made 5,001 shapes). For each of the four prototypes of new functions (`Function.prototype` and those of async, generator and async generator functions) it remembers the empty shape and the shape with both, the first time a function goes through `add_property`, and puts the next functions with that empty shape straight onto the shape with both, and writes the two values (the same 3,000 functions made 2,000 shapes, for the object literals and the `prototype` of the constructors).

Why this is safe: a shape is shared and never changes in place while more than one object holds it (`add_property` and `js_shape_prepare_update` copy it first), and `js_function_shape` holds both, so they stay as they were and the empty shape cannot be freed and its memory taken by another shape. The shape with both is the one `add_property` gives, with the same prototype, keys, order, flags and size of the property array, and the name is made before the function changes, so the cycle collector, which can run there, finds it as it is. The shapes are held for the context, as it holds the shapes of its arrays and `arguments` objects: `JS_MarkContext` marks them, so the cycle collector frees a context that only they hold alive, and `JS_FreeContext` lets them go. Everything else, an object that is not an ordinary extensible one or has another shape, takes the old path.

The shapes held add one or two shapes to a VM (88 to 176 bytes in one VM of the shop). Without PGO, on linux/amd64 (AMD EPYC, one core), with the same HTML, a render of tifa's example shop takes 0.982 of the time it took with the [regexp change for alternatives](regexp.md#alternatives-that-cannot-match-are-not-pushed) alone (the median of 10 rounds, 0.967 to 0.989), the MUI pages 0.993 to 1.000 and the bench pages 0.984 and 0.995, each from one build of each side. Against `80261af`, with the code elsewhere, the shop took 0.972 (0.951 to 1.003), the MUI pages 0.990 to 1.004, and the bench pages 0.993 and 0.995. On `de42e83`, 3 rounds gave the shop 0.988 and the MUI pages 0.983 to 0.997.

The change is in C (`engine/quickjs.c`): `js_function_set_properties` calls `js_function_shape` first. There the shapes are held per context, in the field `func_shapes` of `JSContext`, rather than per runtime for the context that made the last function, so two contexts of a runtime do not take the slots from each other. `JS_MarkContext` marks them and `JS_FreeContext` lets them go. `engine/test/compare.sh` runs `testdata/funcshape.js`, and `engine/test/unit.c` checks that each of the four prototypes keeps its two shapes and new functions reuse them, that two contexts keep their own, that the cycle collector frees a context that only they hold alive, and leaves them in a live one.

## Methods of strings, numbers and arrays found in the interpreter

Release: v0.27.1.

`s.charCodeAt(i)`, `n.toFixed(2)` and `a.push(x)` find their method in the interpreter. `get_field` and `get_field2`, the opcodes of `o.x` and `o.x(...)`, look for the key on the object and its prototypes in a loop of their own, and handed everything else to `JS_GetPropertyInternal`: every value that is not an object, and every object with exotic behavior, arrays included. The CSS-in-JS code of tifa's MUI pages reads string methods about 320000 times in a render of the order list, and both of tifa's apps read array methods a few thousand times. Every other value or object takes `JS_GetPropertyInternal` as before.

Why this is safe: those are the keys for which `JS_GetPropertyInternal` itself goes straight to the prototype. A string has its indexes and `length` of its own and nothing else, and a number nothing. A fast array has its elements at indexes, and a typed array also answers `undefined` for a key that is a number in canonical form, such as `Infinity`, so typed arrays stay on the old path. The value stays on the interpreter's stack, so a getter, a proxy or another exotic object further up the chain still takes the slow path with the value as `this`, and a method or getter added to the prototype later is found where it is. Nothing is cached, so memory use is the same.

Without PGO, on linux/amd64 (AMD EPYC 7B13, one core), against v0.27.0 with the same HTML, the four MUI pages of tifa's test app render in 0.975 of the time (0.966 to 0.986 over 6 rounds in 3 code layouts) and the six pages of the shop in 0.996 (0.992 to 0.998). Under callgrind the engine runs 1.0% fewer instructions on the MUI pages and under 0.1% fewer on the shop. The time drops more than the instruction count: `JS_GetPropertyInternal` and its property lookup were mostly waiting on memory.

Tests: `fieldchain_test.go`, whose `testdata/field_chain.js` reads methods, missing keys and keys added later on strings, ropes, numbers and arrays, with getters in sloppy and strict mode, read-only keys, a proxy and a frozen object above `String.prototype`, frozen, sealed, sparse and typed arrays, `arguments`, String objects, symbols, `with` and `eval`, against Node, and checks that an interrupt or running out of memory in such a getter or method cannot be caught.

## Own keys listed from the shape

Release: Unreleased.

Listing the own keys of an ordinary object costs less. Then spread and rest (`JS_CopyDataProperties`) and `Object.keys`, `values` and `entries` (`JS_GetOwnPropertyNames2`) look each key up again to read its value. React's `jsx` spreads and copies props in nearly every element. For an object that is not exotic they list the keys from the shape in Go, in the engine's order (array indexes by value, then strings, then symbols and private names, each in shape order), and spread, rest, `values` and `entries` read the values of plain data properties straight from the object. A spread into an empty object literal of an object whose keys are all enumerable, writable and configurable strings, then symbols, with the same prototype, gives the new object the shape of the source, which defining the keys one by one would have led it to, and copies the values.

The kinds of the keys of a shape are kept in a key cache of the runtime, 256 entries of the kinds of up to 24 keys, about 8 KiB per VM, so that the next listing of an object of that shape reads no atom. It differs from the [table of shape steps](../performance.md#what-was-tried-and-not-done) that was dropped: that table held shapes alive, which added 28 KB to 142 KB per VM and changed when the cycle collector runs. The key cache holds no shape, atom or object, only a byte per key. It keeps entries only for shapes in the shape hash table and drops the entry of a shape when it leaves the table (`js_shape_hash_unlink` calls `ownKeyCacheDrop`). A shape in the table never changes in place: it leaves the table before a key is added (`add_shape_property`), before a key is deleted or its flags change (`js_shape_prepare_update`) and before it is freed (`js_free_shape0`). So the kinds the cache has for a shape are those of its keys, and its memory cannot have gone to another shape. The flags are read from the shape at each listing.

Why this is safe: for an object that is not exotic, `JS_GetOwnPropertyNamesInternal` reads only the shape, calls no method of the class, and throws only for a binding of a module namespace not yet initialized, listed with `JS_GPN_ENUM_ONLY` or `JS_GPN_SET_ENUM`. `ownKeys` leaves such a binding, and objects with more than 16 array indexes, to the engine. Exotic objects (arrays, `arguments`, `String` objects, typed arrays, proxies, module namespaces) take the old path, so the traps of a proxy run as before. Values are read directly only when every key listed is a plain data property: then nothing runs between the listing and the reads that could change the object. An object with a getter, a setter or a binding, or with a `stack` key, which can hold the marker of an [error stack](errors-and-stacks.md#error-stacks-formatted-when-first-read) not formatted yet, takes the engine's path for its values. `Object.assign` sets rather than defines, and keeps its path after the listing. What upstream does differently from Node stays: the spread of a string primitive copies nothing.

On linux/amd64 without PGO (AMD EPYC 7B13, one core), against v0.28.2 with the same HTML, the six bench pages of tifa's example shop render in 0.990 of the time (0.958 to 1.020 over 6 rounds in 3 code layouts), its ten store pages in 0.994 (0.952 to 1.036) and the four MUI pages of tifa's test app in 0.987 (0.957 to 1.047). The gain depends on the layout of the code: 0.976 to 0.978 of the time in one layout, 0.991 to 1.006 in the other two. Of the listings of a render 99.9% take the new path, with about four keys each, and about a quarter of the spreads take the shape of their source. On the Apple M4, a spread of six keys into a new literal takes 74 ns rather than 250, `{...a, ...b}` 155 rather than 372, the rest of a destructuring 239 rather than 316, `Object.keys` of six keys 134 rather than 542, `Object.values` 128 rather than 567, `Object.entries` 529 rather than 1452, and a bare `for in` 261 rather than 291. The key cache adds 8 KiB to a VM.

Tests: `own_keys_test.go`, whose `testdata/own_keys.js` lists objects of every kind every way (integer keys, symbols, private names, hidden keys, accessors, deleted keys, changed flags, frozen, sealed and null prototype objects, prototype chains, exotic objects, getters that change the object while it is spread, `for in` while the object changes, objects that share or leave a shape, 120 random objects) and whose `testdata/own_keys.golden` is what the engine gave before the change, and a module namespace before and after its bindings are set.

The change is in C (`engine/quickjs.c`): `JS_GetOwnPropertyNamesInternal`, `JS_CopyDataProperties` and `JS_GetOwnPropertyNames2` call `js_own_keys`, `js_copy_data` and `js_own_keys_array` first, the key cache is the field `own_key_cache` of `JSRuntime`, and `js_shape_hash_unlink` drops a shape from it. The keys of a listing are walked with `js_own_keys_next` rather than a callback. A key that is left out of a rest is looked up with `js_get_own_property_flags`, as the engine does. `engine/test/compare.sh` runs `testdata/own_keys.js`, and `engine/test/compare/ownkeys.js`, which lists objects of many shapes, made and dropped so that new shapes take the memory of freed ones, through every path, and checks each listing against the order it works out from the keys it added. It also lists one object after the key cache has its shape, as keys are added, deleted and made not enumerable, a key becomes a getter and the prototype changes. `engine/test/unit.c` checks listings of new objects whose shapes take the memory of shapes the cycle collector freed.


## Ordinary objects take 48 bytes, not 72

Release: Unreleased.

An ordinary object, one of class `Object` (an object literal, `{}`, `Object.create(p)`, the instance of a plain class, a React element or its props), takes a block of 48 bytes where every object took 72. A `JSObject` is a header of 40 bytes (the links of the collector, the flags, the shape and the property array) and a union of 24 bytes for the data of the class: the elements of an array, the closure of a function, the state of a `Map`. An ordinary object has no such data, so the union was dead weight. `JS_NewObjectFromShape` now allocates the header alone for class `Object` and does not write the union, and `free_object` leaves its fail-safe stores to the other classes.

Why this is safe: the union is read and written by class. The one switch that looked at every object, `JS_ComputeMemoryUsage`, now has a case for class `Object` that reads nothing. The public getters `JS_GetOpaque`, `JS_GetOpaque2` and `JS_GetAnyOpaque` answer NULL for an ordinary object, which is what they gave before, as nothing set its opaque pointer. `JS_SetOpaque` on an ordinary object aborts, as the engine does for a call its callers must not make, rather than write past the block. The engine never calls it on one, and the Go API does not call it at all. `JS_ComputeMemoryUsage` counts the smaller block in `obj_size`.

Memory, on the C tree natively (Apple M4, the same allocator and flags as the generated engine), against v0.29.0 with the same HTML:

- The highest `MemorySize` of the renders of 11 Markdown pages of 300 to 500 KB (react-markdown with remark-gfm and rehype-highlight) is 3.8% lower on average (11.8% lower to 2.7% higher: the peak sits at the threshold of the collector, 1.5 times the size after the last collection, so one page can land just before or after a collection). The page of 400 KB peaks at 180.8 MB, then 181.1 MB.
- With the collector turned off, so that no collection moves the end, the same page ends its render holding 394.3 MB, then 379.9 MB (3.7% less, 14.4 MB).
- The 20 pages of tifa's example shop peak at 253.5 MB in all, then 240.9 MB (5.0% less), and end at 244.3 MB, then 240.0 MB with the collector off (1.8% less).

Speed on linux/amd64 (AMD EPYC 7B13, one core, 8 code positions): no change. The React page, the bench, MUI and shop pages take 0.993 to 1.004 of the time, and the engine runs 0.01% to 0.27% more instructions for the extra test when it makes and frees an object ([performance.md](../performance.md#ordinary-objects-of-48-bytes) has the table).

Tests: `engine/test/unit-api.c` runs 300 ordinary objects of 70 properties with holes, frozen, sealed and with accessors, as prototypes, as keys of a `WeakMap` and a `WeakSet`, under `WeakRef` and a `FinalizationRegistry`, and in a cycle, then `JS_ComputeMemoryUsage`, and the getters. On the system malloc build (`build.sh asan`) every block stands alone with red zones, so a read or write past the 40 bytes is reported: the first try, with the smaller block only, was caught in `JS_NewObjectFromShape`, then `free_object`, `JS_ComputeMemoryUsage` and `JS_GetOpaque`. `engine/test/unit-white.c` checks the block of an ordinary object has room for less than a `JSObject` and that of an array for all of it. `engine/test/api-test.c` checks that `JS_SetOpaque` of an ordinary object ends the process with `SIGABRT` after the host has heard it.

The change is in C (`engine/quickjs.c`): `JS_NewObjectFromShape`, `free_object`, `JS_ComputeMemoryUsage`, `JS_SetOpaque`, `JS_GetOpaque` and `JS_GetAnyOpaque`, and a comment at `JS_SetOpaque` in `quickjs.h`.

## Spread, rest and Object.assign look each key up when its turn comes

Release: Unreleased.

`JS_CopyDataProperties`, behind `{...o}`, the rest of a destructuring and `Object.assign`, listed the enumerable own keys of the source once and then read each one with `JS_GetProperty`. The specification lists all the own keys, then looks each one up when its turn comes (`[[GetOwnProperty]]`, then `Get`), so a getter that deleted a later key, or made it not enumerable, leaves it out, and one that made a not enumerable key enumerable has it copied. Here a key that was gone was copied anyway, as `undefined` when nothing was left, or with the value the prototype has under that name, and a key that became enumerable was left out. `var o = { get a() { delete this.b; return 1 }, b: 2, c: 3 }; Object.keys({...o})` gave `a,b,c` where Node gives `a,c`.

Now all the own keys are listed, enumerable or not, and every one is looked up again before its value is read: an ordinary object by its shape with `find_own_property`, which costs one hash lookup, and an exotic object (an array, a typed array, a String object, `arguments`, a proxy) by `js_get_own_property_flags`, as the keys of a proxy already were. A module namespace stays as it was: it is listed with `JS_GPN_ENUM_ONLY`, which is where it throws for a binding not initialized yet, it has no getter, and its first key is not looked up again. `js_copy_data`, the path for sources whose keys are all plain data properties, runs no getter and is as it was. A getter that adds a key still has the key left out, since the keys are listed first.

Tests: `engine/test/compare/copy_data.js` against Node 24: getters that delete, change or add a key of an ordinary object, an array, a class instance and a source with 30 keys, a prototype that has the deleted key, a getter that throws, a proxy whose traps run in the order of the specification, a getter that makes a not enumerable key, symbol or index enumerable, a rest that leaves out a key a getter has changed, and the three operations on each. The keys of a result are listed with `Reflect.ownKeys`, since JSON leaves a symbol out. `testdata/own_keys.golden` has the three lines of the spread, the rest and `Object.assign` of a changing source as Node prints them.

## Object literals made at their final shape

Release: Unreleased.

An object literal of plain keys gets all its keys at once. The compiler emitted `OP_object` and then one `OP_define_field` for each key, which went through `add_property` and looked up the next shape in the shape hash table for every key, and grew the property array from 2 slots to 4, then 8. Now a run of keys of a literal that are plain names or strings, each followed by `:` and a value or written as a shorthand, compiles to the values and one `OP_object_lit`. Its operands are the number of values and the index of the run in the function. The bytecode of a function holds the keys of each run and, once the run first executes, the shape it ends with. The next objects take that shape and a property array of exactly its size, and get their values by index. React elements and their props are such literals, and so are most objects a markdown parser makes.

A run ends at a computed key, a spread, a method, a getter or setter, `__proto__`, a key that is a whole number up to 2^31 - 1 (which the engine keeps as a number, not a string), a key the literal already had, or after 32 keys. Past 65535 such literals in one function, the rest are made the old way. The keys before the break are one `OP_object_lit` and the rest take the old path, so `{ a, b, ...c, d }` makes its first two keys at once and defines the third after the spread. A literal with no plain keys first is still `OP_object`.

Why this is safe: the specification (PropertyDefinitionEvaluation, in the section on object initializers) makes the object first and then, for each property, evaluates its key and value and defines it. With plain keys nothing evaluates a key, and no value expression can reach the object: only a method or an accessor could, through its home object, and those end the run. So making the object after its values gives the same result, with the same keys in the same order, each enumerable, writable and configurable, and the same function names. A value that throws throws before the object exists, which no script can tell. The shape is found in, or put into, the shape hash table with the `Object.prototype` of the function's realm, as `add_property` would find it, so an object of `OP_object_lit` and one built key by key have the same shape and later keys go the same way. A function's realm never changes, so neither does the prototype of its literals. A shape held by more than one object never grows in place, so the shape a function holds stays as it was made. An object of the literal that later gets a new key therefore copies the shape, and `add_property` now grows the shape hash table when it links such a copy, as `js_new_shape2` does: the table grew only when a new shape was made, so with many copies it ran more than half full and caught up one size at a time. The cycle collector marks the shapes held by bytecode (they hold `Object.prototype`, and through it the realm), and freeing the function frees them.

The bytecode version goes from 5 to 6: the reader takes the keys after the closure variables of each function, checks the counts (at most 65535 runs of 1 to 32 keys, no key twice in a run), and rejects an `OP_object_lit` whose index or count does not match the keys it read (`SyntaxError: invalid object literal`). With bytecode that VMs share, each VM reads its own functions and holds its own shapes, so a table per runtime or per context is not needed.

Without PGO, on linux/amd64 (AMD EPYC 7B13, one core with its sibling idle), against the engine before the change, over 4 rounds at 8 code positions with the same HTML: the six workbench pages of tifa's example shop render in 0.956 of the time (0.935 to 0.963 over the positions), the three MUI pages of tifa's test app in 0.969 (0.948 to 0.976), the table page of its bench app in 0.942 (0.914 to 0.950), and its spiral page (0.989, with 3.5% fewer instructions) and `r_react_ssr` (0.991, with 3.1% fewer instructions) do not change by the rule. A VM of the shop holds about 0.17 MiB more after its first render, for the keys of its literals and their shapes, and a long markdown page takes 1.6% less at its peak, as its objects have no spare slots. [performance.md](../performance.md#object-literals-made-at-their-final-shape) has the rest.

The change is in C (`engine/quickjs.c`, `engine/quickjs-opcode.h`): `js_parse_object_literal` collects the keys and `emit_object_lit` emits the opcode, `JSFunctionBytecode` has `object_lits` and `object_lit_count`, `js_new_object_lit` and `js_object_lit_shape` make the object, `mark_children` marks the shapes and `free_function_bytecode` frees them, `JS_WriteFunctionTag` and `bc_read_object_lits` write and read the keys, and `add_property` grows the shape hash table before it links a copied shape (`js_shape_keepable` did that only for its own copies). `engine/test/compare.sh` runs `engine/test/compare/object_literal.js`, whose file is what Node 24 prints: the order in which keys and values are evaluated, repeated keys, index keys, `__proto__` in every form, computed keys, spreads, methods, getters and setters, `get`, `set` and `async` as keys, function names, values that throw, values that use the variables around them or the objects of the same literal made before, 32, 33 and 45 keys, a function of more literals than 16 bits number, destructuring, a setter on `Object.prototype`, and that the literals of functions made and dropped leave the same blocks of the heap in use. `engine/test/unit.c` checks that a literal gets a property array of its exact size, and `engine/test/unit-white.c` that its bytecode reads back and runs, but not with the operands of its `OP_object_lit` changed. `TestShapeCache` of `internal/cengine` checks that rounds of literals whose objects each get a key of their own leave the memory of the VM the same after the fourth round.


## Object literals keep their properties in the block of the object

Release: Unreleased.

The object that `OP_object_lit` makes and its array of properties are one block, not two. The properties take the end of the block of the object, where the data of the other classes (the elements of an array, the closure of a function) would be, and `p->prop` points there. It saves a call of the allocator when the object is made, another when it is freed, and the 8 byte header of the second block. React elements and most objects a markdown parser makes are such objects.

The object gets the room its shape has (`prop_size` properties), as it did in a block of its own, when the whole block stays a small block of the allocator (at most 504 bytes: the header of 40 bytes and up to 29 properties of 16 bytes, so a literal of 30 keys is made as before). `js_props_inline(p)` tells the two cases apart: whether `p->prop` is the address at `offsetof(JSObject, u)` in the block of `p`. A block of its own can never have that address, since it lies inside the block of `p`. Every place that allocates, resizes or frees the array looks at it:

- `free_object` frees the array only when it is a block of its own.
- `js_resize_prop` gives `resize_properties`, the found-shape branch of `add_property` and `js_copy_shape` the array they ask for. An array in the block of the object is copied to a new block of its own, and the room it leaves is not used again. Any other is resized with `js_realloc`. With no memory it returns NULL and the object is as it was, so a key that fails to add leaves the object whole.
- `compact_properties` moves the properties up in place and leaves the block of the object as it is, since it cannot give back part of it. Packing is optional: when memory runs out for the new shape (or for the smaller property array), `delete_property` still deletes, the object keeps its deleted slots for a later try, and no error is left pending. `compact_properties` takes its memory with `js_malloc_rt` and `js_realloc_rt`, which throw nothing, and `delete_property` ignores its result on purpose. It used to ignore a `-1` that had thrown, so the "out of memory" error stayed pending after a delete that worked.
- `JS_ComputeMemoryUsage` counts no block of its own for such an array, and still counts its room in `prop_size`. Its classes (`obj_size`, `prop_size`, `memory_used_size`) describe the live objects and the room their shapes have, not every byte they keep: the room that is left in the block of an object after its properties moved out, and the tail that packing the deleted keys leaves in it, is in none of them. `MallocSize` (`malloc_size`) is what the allocator holds, the same as before, and is the number the memory limit and the collector use.
- Everything else that changes an object keeps the array where it is: flags (`Object.freeze`, `defineProperty`), the prototype (set in the shape in place), deleting keys, and the shape leaving the shape hash table. A shape never has more properties than the block has room for, since a shape with another `prop_size` is only reached through `js_resize_prop`.
- `js_copy_props` (`RegisterCopyProps`) only reads `prop` of the config and adds keys to the new props with `add_property`, so it needs nothing of its own.

The room an object leaves in its block when it gets more keys than the block has is lost until the object goes. So when an object that holds its properties in its block gets a key, its shape says so (`inline_grew`, in the padding of `JSShape`), and `OP_object_lit` makes the next objects of that shape as it did before, with the array apart. Literals that are filled in afterwards (`const o = { a, b }; o.c = 1`) then waste room only once for each shape. Without that flag, a VM of the store pages of the shop held 0.7% more after rendering than before the change.

Without PGO on linux/amd64, against main, no page group passes the rule for faster or slower (the shop 0.991, the MUI pages 0.998, the bench app 0.985, a React render 0.995), the instructions of a render are 0.14% to 0.82% fewer, and the VM holds 1.0% to 2.4% less after a render and a collection ([performance.md](../performance.md#object-literals-with-their-properties-in-the-block-of-the-object) has the table).

The change is in C (`engine/quickjs.c`): `js_new_object_lit` and `js_new_object_inline` make the object, `js_props_inline`, `js_resize_prop`, `free_object`, `compact_properties`, `add_property`, `js_copy_shape`, `resize_properties` and `JS_ComputeMemoryUsage` know the two cases, and `JSShape` has `inline_grew`.

Tests: `test_object_lit_one_block` in `engine/test/unit.c` checks that 1000 literals of four keys take less than the same objects built one key at a time, that objects keep their keys through growing, packing, freezing and a new prototype, and that all of it is given back. `test_object_inline_props` and `test_object_inline_oom` in `engine/test/unit-white.c` check by address which objects hold their properties in the block (literals, but not `{}`, arrays or `Object.create`), that adding a key, deleting keys down to a packed shape, freezing, sealing, a new prototype, an accessor and a flag leave them where they belong, that objects in cycles, under a `WeakRef` and as `WeakMap` keys are freed, that `inline_grew` turns off the room for the next objects of a literal and for no other, and, failing each call of the allocator in turn while an object grows by a key in the shape hash table, grows past its room, packs its deleted keys, or while the first object of a literal is made, that it keeps its keys, that a failed first run leaves the next run whole, and that nothing leaks. A delete that works and leaves an error pending fails the test. A check that throws counts as a failed check. `test_object_inline_limit` checks that a literal of 27, 28 and 29 keys keeps its properties in its block and one of 30 and 31 does not. They also run under AddressSanitizer on the system malloc, where each block stands alone with red zones.

## Object literals of the same keys share one shape

Release: Unreleased.

The first run of an `OP_object_lit` looks for a shape with the keys of its literal in the shape hash table, so that literals of the same keys, written in different places, share one shape with each other and with objects built key by key. It used to walk there one key at a time from the empty shape of `Object.prototype`, and that empty shape is often gone: the first object that gets a key grows it in place, since no other object holds it. The walk then found nothing, and each place that wrote such a literal made a shape of its own. In tifa's example shop that was 588 of its 4203 shapes.

The shape is now looked up by its final hash. The hash of a shape is built key by key from the prototype (`shape_initial_hash`, then `shape_hash` of each key and its flags, as `add_shape_property` does), so the hash of the keys of the literal is known without the shapes in between. A shape found must have the same prototype, exactly as many keys, and the same keys in the same order, each with the flags of `OP_define_field` (`JS_PROP_C_W_E`). It may have room for more properties than the literal has keys (a shape grows its room from 2 to 3, 4, 6 and 9), which the object then gets, as an object built key by key would. It may also say that objects of it outgrew their block (`inline_grew`), and the next objects of the literal then keep their properties apart, as for a shape the literal made itself.

Why this is safe: an object built key by key that reaches the same keys, in the same order, with the same flags and prototype, gets the shape found in the table in the same way (`find_hashed_shape_prop` at each key), so sharing only does for literals what `add_property` already does. A shape changes in place only when one object holds it, after it leaves the table, and the literal holds the shape it finds, so an object of the literal that gets a key copies the shape, as before.

A VM of tifa's pages holds 12% to 15% fewer shapes after one render (the shop 3615 rather than 4203, the store pages 4403 rather than 5210, the MUI pages 3425 rather than 3896, the bench pages 928 rather than 940), and its `MallocSize` after a render is 0.7% lower for the shop and the MUI pages, 1.7% for the store pages (66 KB, 201 KB and 41 KB) and the same for the bench pages. The instructions of a render do not change (callgrind on linux/amd64: the shop -0.13%, the store pages -0.03%, the MUI pages +0.01%, the bench pages +0.02%, `r_react_ssr` +0.03%), and the HTML of the 16 pages is the same.

The change is in C (`engine/quickjs.c`): `js_object_lit_shape` calls `find_hashed_shape_keys`. `test_object_lit_shared_shape` in `engine/test/unit-white.c` checks, with the shape cache on and off, that a literal of one key in two functions, and one of three keys in three places (one of them in `eval`), share one shape, that keys in another order or a key with other flags give another shape, that a literal takes the shape of an object built key by key that has room for 6 properties and keeps that room, and that a shape whose objects outgrew their block makes the next objects of another literal of the same keys keep their properties apart. Without the change 8 of its checks fail.

## A for in loop holds the shape of its object

Release: Unreleased.

A `for in` loop listed the own keys of its object when it started, with `JS_GetOwnPropertyNamesInternal`: a list it malloc'd, with a reference to each key, freed at the end of the loop. React and the libraries around it run such a loop over the props of most elements and over many style objects. Now, for an object that is not exotic, whose shape is in the shape hash table and whose string keys hold no array index and no binding of a module namespace, the loop takes a reference to the shape instead and walks its keys in place, leaving out deleted keys, symbols and the keys that were not enumerable when it started. While the object still has that shape, it has every key of it, and the loop gives each without looking it up again. When the object has another shape, the loop looks each key up as before.

Why this is safe: a shape in the hash table never changes in place. It leaves the table before a key is added, deleted or gets other flags, and while the loop holds a second reference the object gets a copy to change instead (`add_property`, `js_shape_prepare_update`). So the shape the loop holds keeps the keys and flags the object had when the loop started, in the order `JS_GetOwnPropertyNamesInternal` gives them (with no array index, the string keys in the order of the shape). A key deleted during the loop is not given, a key added is not given, and a key made not enumerable is still given, as before. When a prototype has enumerable keys, the loop makes the keys of the shape the visited keys, as it did with the list. Arrays, `String` objects, `arguments`, proxies and the other exotic objects, objects with an array index key or a binding, and objects whose shape is out of the table take the old path. The cycle collector marks the shape the loop holds.

A loop holds no list. 1000 generators stopped in a loop over an object of 40 keys held 344 bytes more each than over an object of 1 key, and now hold the same. In the shop's workbench pages, the listing of keys, the check of the prototypes and the free of the loop take about 1.7 M fewer instructions per render, about 1%.

The change is in C (`engine/quickjs.c`): `JSForInIterator` has the field `sh`, set by `build_for_in_iterator` and read by `js_for_in_next`, and `js_for_in_prepare_prototype_chain_enum`, the finalizer and the mark of the iterator know it. `engine/test/compare.sh` runs `engine/test/compare/for_in_has_own.js`, whose file is what the engine printed before the change: loops over objects of every kind (null prototype, array index keys, symbols, keys not enumerable, getters, frozen and sealed, 40 keys, arrays, `String` objects, `arguments`, proxies and a proxy as prototype, class instances, functions, primitives), keys added, deleted, deleted and added again, made enumerable or not during the loop, a prototype set or given a key during the loop, an enumerable key on `Object.prototype`, nested loops, a loop left by a throw or by `break`, objects frozen, sealed and emptied of most of their keys during the loop, and loops stopped in a generator across collections. `engine/test/unit-api.c` checks the memory a stopped loop holds.

## hasOwnProperty.call answered in the interpreter

Release: Unreleased.

React and the libraries around it test the keys of their `for in` loops with `Object.prototype.hasOwnProperty.call(obj, key)`. That is two calls of built-in functions, `call` and then `hasOwnProperty`, each through `JS_CallInternal` and `js_call_c_function`. `OP_call_method` now answers it itself when the function called is `Function.prototype.call` and its `this` is `hasOwnProperty` (the built-in C functions, of any realm), the object is not exotic, and the key is a string that is its own atom already or an integer that is an array index. It looks the key up in the shape with `find_own_property`, as `hasOwnProperty` does.

Why this is safe: for these arguments neither call can run script or throw. The key needs no conversion that could call a method, an object is its own `ToObject`, and the own property of an ordinary object is found in its shape. A `call` or `hasOwnProperty` replaced by script, or bound, is another function and takes the calls. What the two calls do on their way in is checked first: the call depth (two levels), the shadow stack (two margins left, as each call's frame comes before its check), a pending interrupt and a pending uncatchable exception. Where either call would have thrown, the calls are made and throw as they did. A binding of a module namespace, which can throw before it is set, takes the calls too. With no call made, nothing counts toward the next poll there: loops still count at their jumps.

In the shop's workbench pages, 7,782 calls a render take the new path, and a render runs about 2.5 M fewer instructions, about 1.5%. Together with [the for in loops](#a-for-in-loop-holds-the-shape-of-its-object), the shop runs 2.5% fewer instructions, the MUI pages of tifa's test app 3.4%, `r_react_ssr` 1.8% and `r_bench_spiral` 2.8%. The time is in [performance.md](../performance.md#calls-for-in-and-hasownpropertycall).

The change is in C (`engine/quickjs.c`): `OP_call_method` and `OP_tail_call_method` call `js_has_own_call` when the function is `Function.prototype.call`. `engine/test/compare/for_in_has_own.js` calls `hasOwnProperty` with keys of every type (strings, array indexes as numbers and strings, `"01"`, the empty string, symbols, `null`, `undefined`, booleans, BigInt, objects with `toString`, one that throws) and `this` values of every kind (primitives, functions, arrays, getters, deleted keys, proxies, the global object), through `call`, `apply`, `Reflect.apply`, `bind` and as a method, with `call` and `hasOwnProperty` replaced and put back. `TestHasOwnCallDepth` (root package) checks that a recursion through it ends at the same depth as through the calls.
