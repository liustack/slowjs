# The C engine

`engine/` is the engine of the module: QuickJS at the pinned commit with slowjs's changes, compiled to Go assembly by the generator. What follows is what it does differently from upstream QuickJS. The column "What changes for a program" compares with the engine before it, the QuickJS that ccgo translated to Go (the "previous engine" below), which is what users of v0.28 and earlier ran. The changelogs have the same list for users.

## The small libc

`memcpy` is not musl's: it is written here (overlapping loads and stores of one width up to 128 bytes, then a loop of 128 bytes with the destination aligned to 16, SSE2 and NEON moves only), because musl's is slow for the strings the engine builds. See its [README](../../engine/libc/README.md).

The whole engine is built with `-ffp-contract=off` too, and the generator refuses an `llvm.fmuladd` or `llvm.fma` and any fast-math flag (`reassoc`, `nnan`, `ninf`, `nsz`, `arcp`, `contract`, `afn`, or the `unsafe-fp-math` attributes) in the IR, and on arm64 a fused instruction (`fmadd`, `fmsub`, `fnmadd`, `fnmsub`, `fmla`, `fmls`) in llc's text. What is tested, and what is not:

- linux/amd64: `engine/test/math.sh` checks, bit for bit, 100000 inputs for each of 33 functions of libc and for 33 `Math` operations as JavaScript sees them, against hashes kept in `engine/test/math`. They were first recorded from the previous engine, and the C engine gave the same bits on every result. The JavaScript check writes a NaN as the one NaN of JavaScript, so it does not check the sign and payload of a NaN. The libc check does, so it runs on x86-64 only.
- macOS arm64: `math.sh` checks the JavaScript hashes there. The libc results are the same except for the sign of a NaN, which the processor chooses (positive on arm64, negative on amd64), so that part is not checked on arm64.
- The engine runs on those two targets only, so the same last digit on both is shown.


`snprintf` reads a whole conversion, flags to conversion letter, and checks it before it takes any argument for it, a `*` included. It calls `abort` on a floating point conversion, `%n`, a positional argument, a length on `c`, `s`, `p` or `%`, any flag, width or precision written on `%` (a `*` there counts, whatever it would be given), a format that ends inside a conversion, and a width or precision that does not fit an int. A width of INT_MIN given for a `*`, and an output longer than INT_MAX, abort too, but only after the arguments are taken, since they depend on them. A new format in the engine cannot print the wrong thing. It is the `abort` of the small libc, which asks the host like every other abort, and not a trap, which in Go would end the process. `libc-test.c` lists the formats that abort and counts the arguments taken before each one does, and `api-test.c` checks that one reaches the host. The only trap left in `engine/` is the one after the `host_call` in `abort`, for a host that returns.

A format is checked before it can reach that `abort`. The engine files are built with `-Werror=format` and `-Werror=format-nonliteral` (`engine/test/flags.sh`), so a format agrees with its arguments, and is either a string constant or the format of a function that has the `printf` attribute and passes it on (`JS_ThrowError2`, `JS_ThrowError` and `js_parse_error_v` have it, with the `va_list` form `format(printf, 3, 0)`). The two helpers behind `JS_ThrowTypeErrorAtom` and `JS_ThrowSyntaxErrorAtom` pass their format with the name of an atom in place of their arguments, which clang cannot follow, and a pragma turns the check off for just those two.

`check-symbols.sh` proves the symbol level only. The engine files, with the libc, leave undefined nothing but the callbacks of `engine/host.h` and `host_memory_grow` of `engine/heap.h`. The allocator ([allocator.md](../allocator.md)) is among the engine files, and the engine calls no malloc: `dbuf` and `CharRange` have no default allocator, and `stdlib.h` of the libc declares none. It does not prove that the machine code uses no thread local storage, no system call instruction and no fixed address. Those checks come with the generator, not before.

## Time, abort and the host

`engine/host.h` declares what the engine asks of its host. `host_now(vm, kind)` gives the wall clock or a monotonic one in nanoseconds. `host_call(vm, &this, argc, argv, magic)` calls a function of the host, and a magic below 0 is a request of the engine: `HOST_CALL_ABORT` for `abort()`. The this value goes by address, and a request of the engine has none and passes NULL: a JSValue by value is two words, which with the shadow pointer, `vm`, `argc`, `argv` and `magic` makes 7, and the generated code passes a callback at most 6 words in registers in the `body` calling mode. `Math.random` asks no clock: it starts from the seed `JS_NewRuntime` was given, the same in every context of the runtime. `abort` does not know its VM and passes 0. `host_memory_grow` is in `engine/heap.h` and comes with the allocator. Two kinds of `host_call` below 0 are the allocator's: `HOST_CALL_MEMORY_RELEASE` gives a dedicated chunk back and `HOST_CALL_MEMORY_REMAP` grows one (linux, when the host said so with `JS_SetHostRemap`). They run no user code and do not call back into the engine. `host_poll` is where Go stops the goroutine in the engine and where an interrupt reaches it (see [Polls and interrupts](#polls-and-interrupts)). `JS_FreeRuntime` returns the blocks still in use, 0 when nothing leaked. An object that a reference is still held to, such as a value the host never freed, does not abort it as the assert of upstream did: it stops before it frees the rest, and the host takes the memory back as a whole.

## Depth of calls and of C recursion

The engine never reads the stack pointer. The generated assembly runs on a Go stack, which moves and grows, and keeps the locals whose address is taken on a shadow stack of its own, so an address on the stack says nothing about how deep the engine is. It counts instead, with two counts in the runtime, and throws `RangeError: Maximum call stack size exceeded` past either. Neither is ever reset: each level that is entered is left on every path, and a level that cannot be entered counts nothing, so the error path recurses no further.

- **The call depth** counts each call of a function while it runs. `JS_CallInternal` counts before it sends a call to a class, so a built-in function, a bound function and a proxy count a level as a JavaScript function does. The interpreter counts the level itself when it calls a plain C function without `JS_CallInternal` (see [How the interpreter calls a C function](#how-the-interpreter-calls-a-c-function)). A constructor that `JS_CallConstructorInternal` sends to a class counts there. The fast path of `JS_IteratorNext2`, which calls the C `next` of a built-in iterator directly, counts a level too: a chain of iterator helpers recursed through it with no other count. The exported functions that run code (`JS_Call`, `JS_CallConstructor`, `JS_CallConstructor2`, `JS_Invoke`, `JS_Eval`, `JS_EvalThis`, `JS_EvalFunction`, `JS_ExecutePendingJob`) count one level for the entry of the host, so that a host function that calls back into the engine adds a level even when the path to the next call is long, as in the parser of `JS_Eval`. The engine itself calls forms of them that do not count (`js_call` and the like). The limit is 5000 by default (`JS_DEFAULT_MAX_CALL_DEPTH`) and at most 10000 (`JS_MAX_CALL_DEPTH_LIMIT`). `JS_SetMaxCallDepth(rt, n)` sets it, and returns -1 and changes nothing when `n` is out of that range or the runtime is running code. A plain recursive function gets 2 levels short of the limit when the host started it with `JS_Eval`: one for the entry and one for the global code.
- **The internal depth** counts the recursions of C that make no call: the parser (`js_parse_unary`, `js_parse_postfix_expr`, `js_parse_assign_expr2`, `js_parse_statement_or_decl`, `js_parse_destructuring_element` and `js_parse_function_decl2`, which cut every cycle of it: the binary and logical operators are read in loops), making the functions of a script (`js_create_function`, and `get_closure_var` for a variable of a function around), `json_parse_value`, `internalize_json_property`, `js_json_to_str`, the parser of regexps (`re_parse_disjunction` and `re_parse_nested_class`, through `lre_depth_enter`), modules (`js_resolve_module` for their imports, `js_create_module_function`, `get_exported_names` for a namespace, `js_resolve_export1` for an export, linking and evaluation), `JS_ReadObjectRec` and `JS_WriteObjectRec`, `JS_FlattenIntoArray`, the methods of a proxy that go on to the target (all but call and construct, which count as calls, and the prototype, which `JS_GetPrototype` asks the proxy by name), `JS_OrdinaryIsInstanceOf` on a bound function, `JS_GetFunctionRealm`, making a lazy property (`JS_AutoInitProperty`, whose value defines properties that can be lazy too: the tables of built-in objects bound that, the call graph does not) and the define of a property of a String object or an arguments object, which goes on to the ordinary define with `JS_PROP_NO_EXOTIC` (`js_define_own_property_ordinary`: the call graph does not see the flag). Most are a wrapper that counts around the original function, renamed with a `1` at the end (`js_resolve_export1`, whose name has one already, wraps `js_resolve_export2`). The limit is `JS_MAX_INTERNAL_DEPTH`, 2000, and it is a constant of the build, not a setting like `JS_SetMaxCallDepth`: the bound on the stack the engine can use multiplies it by the stack of the deepest of these recursions, and a bound needs one fixed biggest value for any call depth. A host cannot change it, and `JS_SetInternalDepth` (below) moves the point the count starts from, not the limit. A regexp too deep throws `SyntaxError: stack overflow`, as it did.

Each runtime counts for itself, and the Go stack that the runtimes of one host share sees them all. A host that runs code of one runtime from inside a call of another therefore hands the depths over, so that the chain is held to one limit and not to one limit for each runtime in it. `JS_GetCallDepth(rt)` and `JS_SetCallDepth(rt, n)` read and write the call depth, and `JS_GetInternalDepth` and `JS_SetInternalDepth` the internal depth. Around the call, the host reads both depths of the runtime that calls, sets those of the other runtime to them, makes the call, and sets the other's old depths back (the other runtime may be in the chain already, when two runtimes call each other, and its old depths are then its own outer levels). A write takes 0 up to the limit (`JS_MAX_CALL_DEPTH_LIMIT`, `JS_MAX_INTERNAL_DEPTH`) and returns -1 and changes nothing for anything else. A depth above the limit of that runtime (the other one has a bigger limit) is kept, and the next call in it is a `RangeError`: the chain is deeper than it allows. Unlike `JS_SetMaxCallDepth`, the writes work while the runtime runs code, which is when a host makes them, and a depth that was set must be set back before the code that was running goes on, since each call that ends counts one level off whatever the depth is by then. The internal depth is handed over too: the bound on the Go stack adds the internal levels of everything on it, and runtimes that counted their own would add up to the limit once for each runtime in the chain. `unit.c` runs two runtimes that call each other until a `RangeError`: with the depths handed over the chain is one limit long, and without it twice that.

How deep nesting goes with the limit at 2000, measured on the native host by nesting one form in itself until the next level throws (`RangeError`, a `SyntaxError` for a regexp):

| Form (each nested in itself) | Levels that fit | Counted per level |
| --- | --- | --- |
| Parentheses `((1))`, calls `f(f(1))`, arrays `[[]]` | 665, 665, 666 | 3 (an assignment expression, a unary one and a postfix one, whatever operators are between) |
| Object literals `({a: {a: 1}})` | 664 | 3 |
| Arrow functions `() => () => 1` | 998 | 2 |
| Function expressions `(function () { return (function () { return 1 }) })` | 249 | 8 |
| Blocks `{{}}`, and `if (1) if (1) ;` | 2000, 1997 | 1 |
| Labeled blocks `L0:{L1:{}}` | 1000 | 2 |
| `JSON.parse` and `JSON.stringify` of nested arrays | 2000, 2000 | 1 |

JSON nested past the limit (`JSON.parse`, its reviver and `JSON.stringify`) throws `RangeError: JSON nesting too deep`, so the error names the data and not a call that recursed. A stack that runs short first, or any other recursion, still throws `RangeError: Maximum call stack size exceeded`. Of the engines measured on a Mac, V8 parses any depth (its parser has no recursion since v7.6) and stringifies about 6200 levels, Bellard's QuickJS 2026-06-04 parses 6500 and stringifies 4300, and QuickJS-NG 0.17 parses 8100 and stringifies 4600, all with a stack overflow error.

Real code stays far under it. Of 79525 files (npm packages, JSX compiled by esbuild, the output of emscripten, wasm2js, peggy, ajv and the like, and JSON), the deepest parse reaches 632, in the asm.js build of sql.js, which writes the cases of a big `switch` as 290 labeled blocks inside each other. No other file goes past 282, one in a thousand reaches 100, and the middle file 17. A C program with a `switch` of more than about 1000 jump targets, built to asm.js, would not parse. Rendering the pages of tifa's example shop takes the parser 110 levels deep, its MUI pages 99, the bench pages 62 (with the Intl polyfill), and all of test262 256. Everything else stays small on those pages: regexps 49 counted on top of the parser that compiles them, closures 15 (`get_closure_var`), making functions 8, JSON 6, `JS_GetFunctionRealm` 2. The call depth of those renders stays under 600.

Each count also checks the stack left. `__shadow_remaining()` gives the bytes left: the generator turns it into the room left on the shadow stack, and the native test host gives the room left on its thread's stack. Entering either depth needs `JS_STACK_MARGIN` (64 KiB) left, and an `alloca` of a call (the locals of `JS_CallInternal`, the arguments of a bound function) needs its size on top, or it throws the same `RangeError`. So a dynamic alloca never crosses the end of the shadow stack, whatever the depths allow.

A few recursions must not fail, so a count that throws does not fit them, and each is a loop or has a bound that a proof gives. Ropes are read, hashed, made flat and freed by loops (`string_buffer_concat_rope` copies the strings of a rope in order). A concatenation that makes a rope deeper than `JS_STRING_ROPE_MAX_DEPTH` (60) rebuilds it from its strings in order by a binary count, at most 30 deep whatever their lengths (upstream's rebuild by lengths could leave one 53 deep, and recursed). The parse records of `JSON.parse` with a reviver and the definitions of functions are freed by loops. The case conversions, the decompositions and the emoji sequences of the Unicode tables, and the strings of `\q{...}` in a class of a `v` regexp, are loops. The value printer recursed too and is left out (`CONFIG_PRINT_VALUE` above). Freeing an object can free others: `free_zero_refcount` frees in a loop of its own every object whose count reaches zero while it runs, and nothing it calls starts a collection, so it is never entered twice. `js_nest_enter(rt, JS_NEST_FREE, 1)` counts it and aborts past 1, which cannot happen as long as a finalizer, the host's among them, starts no collection (`JS_RunGC`, `JS_RunYoungGC`).

The property layer (properties, atoms, conversions, errors, string buffers, big integers and the collector) was one cycle of 173 functions in the static call graph, bounded by its data and not by a count. It is cut, and `engine/test/cycles.txt` is empty: `cycles.sh` finds no cycle that a count does not cut. No count was added to a hot path. The cuts:

- **Making an error.** `JS_ThrowError2` allocates, and running out of memory there makes the out of memory error with `JS_ThrowError2` again. A slot of its own, `JS_NEST_ERROR` (`JS_NEST_ERROR_MAX`, 2), counts the errors being made, and a third one, which only a bug could start, is thrown as running out of memory (null, uncatchable) and does not recurse. The bound of 2 rests on two facts that `internal/goasm/cmd/cycles` checks on the call graph: making an error runs no JavaScript and reads no interrupt flag (`JS_ThrowError2` reaches neither `JS_CallInternal` nor `JS_ThrowInterrupted`, nor a function that reads the flag), and a collection throws nothing (`JS_RunGC` and `JS_RunYoungGC` do not reach `JS_ThrowError2`, and the job of a `FinalizationRegistry` is queued with memory that does not throw). So the message and the stack of a new error are added with `add_property`, and the names of a stack are converted to UTF-8 by `js_string_to_cstring`, which takes a string and converts nothing.
- **Calls the data never makes**, split off so that the call graph does not see them: the element of a fast array read and written by the generic property paths (`js_get_fast_array_element`, `js_set_fast_array_element`, the fast paths of `JS_GetPropertyValue` and `JS_SetPropertyValue`), a canonical numeric key converted to a number and back (`js_string_to_number`, `js_number_to_string`), ToString of what `ToPrimitive` gives (`js_primitive_to_string`), the array length of a number (`js_number_to_array_length`), and the empty string, taken from its atom.
- **Ropes** are made flat by a loop (above).
- **Two counts of the internal depth** (above): `JS_AutoInitProperty` and `js_define_own_property_ordinary`.

The checks: `unit.c` (see [testing.md](../testing.md#the-c-tree-and-its-native-test-host)) and test262, whose 58 known errors stay the same.

### Go stack room

The generated code runs on the stack of the goroutine that calls it, and the Go runtime ends the whole process, with no panic to recover, when that stack passes its limit of 1 GB (the default on 64-bit targets). The two counts keep the engine far below it. At their largest settings (call depth 10000, internal depth 2000), one VM uses about 65 MB of Go stack, taken from the stack use per level measured on the generated code: a bit over 6% of the limit, and less with the defaults (call depth 5000). Many VMs called from inside each other on one goroutine share one stack, and the hand over of the depths above holds the chain to one limit, so that about 100 of them would be needed to reach 1 GB.

This is a measurement and not a proof. The bound the design started from (5600 bytes for each call level and 4704 for each level of the internal depth, 62.4 MiB at the largest settings) was worked out for the engine before calls were inlined, and has not been worked out again for the code that is checked in. The proof, and a check of it by the generator, are to be redone after the switch to the new engine. Until then the room (15 times what a VM uses) is what holds.

## When the engine fails

C can fail where Go code cannot, and a Go process ends for most of it: a read or a write at an address mapped to nothing prints "unexpected fault address" and exits, since only an address below 0x1000 is a panic by default, and a trap instruction (`ud2` on amd64, `brk` on arm64) is SIGILL or SIGTRAP, which the runtime never lets a program recover. The generated engine is held to this: every way it can fail is a panic that the host recovers, or cannot happen. A VM that failed is broken, as after any panic that leaves through engine frames: it refuses every call but `Close`, and the process and the other VMs go on.

| The C does | What the host sees |
| --- | --- |
| Reads or writes an address mapped to nothing: a wild pointer, or the guard page above the shadow stack | A `runtime.Error` panic that names the address. `Enter` of `internal/gohost` turns on `debug.SetPanicOnFault` for the goroutine, and the `Leave` that matches it puts back what the goroutine had. A pointer that is not canonical on amd64 faults with no address and is a panic too |
| Divides by zero (undefined in C) | amd64 raises a divide error, which Go always turns into a panic. arm64 has no such fault and gives 0 |
| Calls `abort` | `host_call` with `HOST_CALL_ABORT` panics with `gohost.ErrAbort` |
| Reaches a trap | None is left in the output. The shadow-stack pass puts a call of `host_trap(sp)` where the C has `__builtin_trap` (the one after the `host_call` in `abort`) and where its own check on a dynamic `alloca` would cross the end of the shadow stack. It panics with `gohost.ErrTrap` |
| Runs out of the shadow stack | The counts throw `RangeError` first. The guard page is the net behind them |

The generator holds this: its checks refuse `ud0`, `ud1`, `ud2`, `hlt` and `int3` in the text and in the decoded code, in llc's object and in the linked binary of amd64, and `brk`, `udf`, `hlt` and `dcps` on arm64, in the text and as words of the assembled object, which the post-link check of arm64 holds the linked code to word for word. `debugtrap` and `ubsantrap` stop the pass, and so does a trap in a register-entry leaf, which has no shadow pointer to call `host_trap` with.

Not covered, as in a program written in C: a write through a bad pointer to memory that is mapped changes that memory and nothing tells; a loop that never ends runs until the host interrupts it (see [Polls and interrupts](#polls-and-interrupts)); the runtime ends the process when a goroutine stack passes 1 GB, which the counted depths keep the engine from; and the system may kill the process for memory.

Turning on `SetPanicOnFault` takes two calls of the runtime, 3.5 ns at each entry from Go into the engine (an entry and its `Leave` go from 2.5 to 6.0 ns, and a script that does next to nothing, 1.5 µs, takes 10 ns more), and an entry from a callback inside the engine takes nothing. The scripts of the speed set take 0.3 to 0.8 s and enter the engine a few times, so it cannot be seen there. It sits in `Enter` and not where a pool lends a VM because the setting belongs to the goroutine, and a VM may be lent to a different goroutine each time. `TestFault*` in [testing.md](../testing.md#the-go-host-of-the-generated-engine) run each failure on the real engine.

### When the system refuses memory

The VM asks the system for memory in chunks (`host_memory_grow`), and a refusal ends the call that needed the chunk with the uncatchable out of memory error, the same as hitting the memory limit. `TestMapRefusedSweep`, `TestMapRefusedAmongVMs`, `TestReleaseRefused` and `TestRemapRefused` (`-tags testhooks`, they fail the calls through `hostmem.SetFault`) hold what that does:

- A script that asks for 13 chunks, with every chunk from the nth on refused, ends in out of memory for every n up to 13. The VM then runs a small script, `Close` returns nil and leaves nothing mapped, and the next VM runs the whole script.
- A single refused chunk mostly goes unseen: the engine asks again for less and the script finishes with its result.
- With 4 VMs on goroutines of their own, each making a new VM for every render, refusing every chunk to one goroutine for 400 ms fails only that goroutine's renders. The other three do not fail once, and the first renders again when the refusal ends.
- Refused `release` calls do not panic: `ReleaseMemory` gives back less. A refused `remap` ends the call with its result or with out of memory, never a panic.

### The size of the shadow stack

The shadow stack is 32 MiB (`-shadow-size-log2=25` of the generator), fixed when the engine is generated. A call level takes about 1.25 KB of it plus 16 bytes for each argument, local variable and operand slot of the function, so each level the engine counts takes 1.2 to 2.1 KB (a native function in the middle, such as `sort` or `map`, adds a count of its own). `TestShadowStackAtDepth` and `TestShadowStackInternalDepth` (with `-tags slowjs_cengine`) measure the highest point the stack reached, from the highest word that is not zero:

- At a depth limit of 10000, functions with few locals use 37% to 62% of the stack. The most is a `sort` comparator that sorts again (20.7 MB, since `sort` and the comparator each count a level). Functions with 100 locals or arguments use 85% (28 MB). A function with 250 locals gets 6379 levels deep, where the next frame would not fit, and throws `RangeError` there. A limit of 5000 uses half as much.
- The recursions of C (the parser, JSON, the regexp parser, `flat`, stringify) end at their 2000 levels of internal depth with under 3% used. A string made of arrays nested 100000 deep takes 47%.
- Rendering the 18 pages of the example shop takes at most 0.85 MiB (2.6%).
- So 32 MiB holds the depth limit of 10000 for any function with up to about 130 slots and the limit of 5000 for about 340. A bigger frame ends in a `RangeError` before the stack runs out, and the guard page is never reached. A stack of 64 MiB would only move those two numbers to 340 and 760 slots, and it costs address space on linux and darwin and committed memory on windows for every VM.

## Polls and interrupts

The Go runtime stops a goroutine, for a collection or to run another one, only where a function checks its stack, and it never stops Go assembly anywhere else. A loop of the engine that calls no function would hold up every collection of the process for as long as it runs. The C takes part only in the interpreter, which counts its bytecode itself (below).

- The counter is a word of the shadow-stack region, 384 bytes from its base (`gen.PollCounterOffset`), which the code finds by clearing the low bits of its shadow pointer. Each loop keeps the count where that costs fewer instructions, by LLVM's estimate of how often each of its blocks runs: in a register, read where the loop is entered and written back where it is left, and written back and read again around each call in the loop that may poll, or in memory, read and written at each count. So a loop that calls a function that may poll on most of its runs counts in memory, and so does a loop that runs in chunks (below), which counts once a chunk, and a loop whose hot code already needs about all the registers. An inner loop counts in the register of the loop around it, if that one has one.
- Each edge that goes back in a loop counts one, but in the interpreter.
- The interpreter, `JS_CallInternal`, counts 32 (`POLL_WEIGHT`) in memory at its entry, at each jump that does not go forward, at each return from a `finally` block, at each catch of an exception and at each `OP_nop`. The C marks these places (`poll_count` in `cutils.h`), and the pass puts a count at each mark and none on the way back into the dispatch, which stays short enough for llc to copy into the end of every handler. Between two counts the interpreter only goes forward in the bytecode. The compiler puts an `OP_nop` into each path forward of more than 127 instructions (`insert_polls` in `quickjs.c`), and the bytecode of every function is checked before it can run, the compiler's and what `JS_ReadObject` reads (`check_polls`): no path between two counts is longer than 128 instructions (`POLL_RUN`), every opcode is one the interpreter has, every jump lands at the start of an instruction, and the last instruction does not run off the end. `JS_ReadObject` fails on other bytecode with `SyntaxError: invalid bytecode`. `OP_ret`, which takes the place to go back to from the stack, goes only to the instruction after an `OP_gosub`: `check_polls` marks those places of each function in a bitmap, one bit for each byte of its code (only for a function with an `OP_gosub`), and `OP_ret` to any other number throws `InternalError: invalid ret value`, so that bytecode read with a number of its own on the stack cannot take the interpreter into the middle of an instruction or onto a path the check did not follow. So a count of 32 stands for at most 4 instructions of bytecode, a few hundred machine instructions as in the C, and at the default interval a poll comes within 40,000 instructions of bytecode, where it came within 10,000 when the dispatch counted each one. In loops it comes sooner than before: a loop of fewer than 32 instructions counts more than one for each. A Go test (`TestInterpreterJumpsCount`) holds `JS_CallInternal` to this: `pc` moves only a constant step forward or through `JUMP_TO`, which counts a move that does not go forward, and `JUMP_COUNTED`, which always counts.
- A loop needs no count of its own when LLVM's scalar evolution proves it short: innermost, calling nothing, and at most 256 instructions for each entry. Whatever enters it again counts. Any other innermost loop that calls nothing runs in chunks of that size, and the end of each chunk counts the whole chunk. So a count stands for at most a few hundred instructions, and the interval bounds the time between two polls.
- `memcpy`, `memmove` and `memset` of a length that may be over 256 KiB go through helpers that do 256 KiB at a time and count each piece. These functions have no shadow pointer and no count.
- The pass checks its output on its own: in each function, with the blocks that count or poll taken out and the back edges of the loops it proves short, no cycle is left. In the interpreter the edges into its dispatch are taken out too, its entry must count, and each mark must come right after a count of its weight. And each count takes at least 1 and polls whenever it is 0 or less: its branch tests that and calls `host_poll` on the side taken. And it follows the count through each function: each count takes from the count as it stands, each write to the counter writes the count as it stands, and each call that may poll and each return find it in memory. A count kept in a register that a callee did not see, or that is written over what a callee counted, would let more than the interval of counts pass between two polls.

`host_poll` sets the counter back to the interval of the VM (`SetPollInterval`, 10000 by default). The interval does not change the speed, only how often a poll comes.

`JSRuntime` holds an interrupt flag, whose address `JS_GetInterruptFlag` gives the host. `Interrupt` in Go records the time, and the next `host_poll` writes 1 into the flag. Only the goroutine that runs the script writes the flag, so the C reads it with plain loads. The native test host does the same with threads: a stop asked from another thread (`host_interrupt`, or the thread that ends a test after 120 seconds) waits in the host, and the engine, built for that host with `JS_HOST_POLL`, calls the host's `host_poll` at each read of the flag (`poll_flag` in `cutils.h`), where the host writes it on the engine's thread. Built for Go, `poll_flag` is a plain read, and the generated code is the same as without it. The engine reads the flag where it can throw: the interpreter at calls, jumps and the other places it counts, regexp execution and compilation, string searches, the loops of typed array `indexOf`, `lastIndexOf`, `includes`, `fill` and `copyWithin`, `String.prototype.repeat`, `Array.prototype.fill` (every 4096 elements) and `join` (every 1024), `String.prototype.normalize` (every 4096 characters as it turns the string into code points, in each of its three passes and as it builds the result), `localeCompare` (the same, and every 4096 code points as it compares), `toUpperCase` and `toLowerCase` (every 4096 characters, and as they look for the end of a word around a capital sigma), `isWellFormed` and `toWellFormed` (every 4096 characters, and between the chunks of 4096 that `toWellFormed` copies), `split` (its search, as `indexOf` does, and every 1024 pieces), `replace` and `replaceAll` with a string (their search, as `indexOf` does, and every 1024 matches), `padStart` and `padEnd` (every 65536 characters written, a filler longer than that in steps of that many), `trim`, `trimStart` and `trimEnd` (every 4096 characters skipped), the piece that `trim`, `slice`, `substring`, `substr` and `split` cut out when it is over 1048576 characters (a 16-bit string is scanned for a character past 0xff, then copied, that many at a time), the attribute of `anchor`, `fontcolor`, `fontsize` and `link` (every 1024 characters), `escape`, `unescape`, `encodeURI`, `encodeURIComponent`, `decodeURI` and `decodeURIComponent` (every 1024 characters), `Array.from`, `TypedArray.from` and the constructors of typed arrays (every 1024 elements they read from an array-like), the call of the `next` of a built-in iterator (the iterator of a string, an array, a Map, a Set or an iterator helper: `JS_IteratorNext2` calls it without `JS_CallInternal`, which reads the flag when a call starts, so it reads the flag itself, and `Object.fromEntries`, a spread, `Iterator.prototype.toArray`, `Math.sumPrecise` and the methods of `Set` that walk an iterator stop with it), the copy a method of `Set` makes of its set (every 1024 records), the hash of a `Map` or `Set` key that is a long string or rope (every 65536 characters, a string of a rope counted as one more than its length: `map_hash_key_poll` finds and adds with it, and the keys already in a table are hashed without reading the flag when the table grows), and making a rope flat or comparing two ropes with `<` (every 65536 characters, the strings of a rope counted as one more than their length), the loop of a global `replace` that matches in C, `JSON.parse` and `JSON.stringify` at each value, and sorts after each comparison. Their long loops run in chunks of at most 64Ki elements or 1 MiB and read the flag between two. The reads cost little. The one in `JS_IteratorNext2` is a load and a branch at each `next` of a built-in iterator, 2 instructions of the 680 for each item of a `for of` over an array (0.29% more instructions, 0.44% over a Map, 0.43% for a spread of an array, a Set and a string). The pages of tifa and a React render take 0.15% or less more or fewer instructions (callgrind, no PGO, a render of the six workbench pages of the shop +0.05%, the MUI pages -0.05%, the pages of the bench app +0.14%, `r_react_ssr` +0.04%). `replace` and `replaceAll` with a string search with `js_string_find`, about 160 instructions more on a string of 16 characters, and an operation of a `Map` or `Set` with a short string key takes 7 to 16 more. The typed array searches look through 16 elements at a time, in a counted loop the generator proves short, so that it needs no count of its own. There the engine throws `InternalError: interrupted`, which no `try` catches, and the host clears the flag when it next enters the engine from Go. The host converts that error without running JavaScript: with the flag set, any call of a function would throw again.

A sort stops at the first comparison that finds the flag set or an exception (`rqsort_stop` in `cutils.c`): `Array.prototype.sort` then writes nothing back, and the sort of a typed array without a comparator, which works in place, leaves its elements in some order. A loop that never reads the flag, such as `Array.prototype.slice`, `TypedArray.prototype.set` or the product of two BigInts of hundreds of thousands of bits (libbf), runs on. When the script still runs once the grace after `Interrupt` is over (`SetKillGrace`, 50 ms by default) and the engine has polled 1000 times (`gohost.KillPolls`) since the poll that set the flag, that `host_poll` panics with `gohost.ErrKilled`, which goes up through the calls inside, a callback and the script it runs among them, and the goroutine has its `SetPanicOnFault` back. The outermost call returns an interrupted `*Error` that matches `slowjs.ErrKilled` (`errors.Is`), and the VM is good only for `Close`: the methods that return an error return one that matches `ErrKilled`, the others panic, and `Value.Free` does nothing. The polls are what tell a script that runs on from one whose thread did not run: the grace is time on the clock, and a thread that the OS or the Go scheduler leaves waiting, or a Go function the script called, passes it with no work of the engine. With the time alone, a script that would have stopped within a few polls was killed whenever such a wait of 50 ms fell between the `Interrupt` and its stop, which a loaded machine (a CI runner with 3 cores running two packages' tests, or a server with more goroutines than cores) does now and then. On an Apple M performance core, a script that reads the flag stops within 1 to 13 polls of it being set, and one that first frees or collects what it made within about 600 (10 ms for the default sort of a copy of 500,000 numbers), while a loop that never reads the flag polls 33 to 163 times a millisecond, so 1000 polls come within its grace.

Only a call that runs a script is killed. The host enters the engine for it with `EnterScript`, and for anything else, a collection, a memory report or a release of memory, with `Enter`, whose polls only set the flag: a watchdog that calls `Interrupt` during a long collection does not break a VM that runs nothing of a page. What the outermost entry is decides for the calls inside it. `EnterScript` with a timeout also sets a deadline on the monotonic clock, and the first `host_poll` past it acts as `Interrupt` at the deadline would have: the flag is set and the grace counts from the deadline. An `Interrupt` later than the deadline does not move it on: the grace counts from the earlier of the two. A script that a callback runs inside it has the time that is left.

`host_poll`, `host_trap` and the abort find their VM by the shadow pointer alone. `gohost.New` writes the VM's id and its complement in the first 8 bytes of the shadow stack, and the host rounds the pointer down to the size of the stack, reads that header and checks that the VM it names has its stack there: no lock and no write to memory other VMs read, so that VMs polling on many cores do not slow each other. The host's scratch and the engine's frames start above the header. The VMs by id are in a table of atomic pointers (`internal/idtable`), and the id of a closed VM goes to a later one.

Measured on linux/amd64 (an AMD EPYC 7B13 on GCP, Go 1.27), each script pinned to one core, against the same engine built with `-poll=false`:

- Collections. While a tight loop runs (a `for` loop of the interpreter, typed array searches, `fill` and `copyWithin`, regexps, string searches, `repeat`, the sort of a typed array, react), a collection waits at most 0.33 ms for the engine to stop, where it waited up to 1.3 s without polls. Scripts that allocate a lot (`JSON.parse` of 2Mi numbers, a sort with a comparator) have rare waits up to 2.6 ms, with the 99th percentile under 0.25 ms. Straight code of the interpreter, functions of 3000 statements with no loop, where a poll can take up to 40,000 instructions of bytecode to come, makes a collection wait at most 0.1 ms.
- Interrupt, with `GOMAXPROCS=1`, 100 ms into the script: a `for` loop, regexps, typed array searches, `fill`, `copyWithin`, react and straight code of the interpreter stop within 0.3 ms (straight code within 0.15 ms), and a kill comes within 0.2 ms of the end of the grace. The stop comes later while the engine works where it reads no flag: a collection of the engine's own heap, which the allocation of the error may start (about 18 ns for each element of the arrays the heap holds: 19 ms with two arrays of 1Mi numbers, so a sort of 1Mi numbers stops after 8 to 19 ms), or a long loop such as `Array.prototype.slice` (about 40 ns for each element).
- Speed, with the other hyperthread of the core idle, as the median over 8 code positions: react and the render scripts take 5% longer, fib 4%, a `for` loop 14%, `JSON.parse` of 2Mi numbers 17%, and with the text built first 12%, the sort of a typed array 10%, string searches 8%, and regexps within 2%. Typed array `indexOf` takes 25% longer, `repeat` up to 9%, and `fill` and `copyWithin` within 1%. A tick on every run of the loops that now run in chunks would cost react 6% and regexps 20% more.

## Where the interpreter and the regexp matcher sit

After Go's prologue every generated function has a `PCALIGN $16`, so its body starts on 16 bytes and moves within its lines of 64 bytes whenever code linked before it grows. The body of `JS_CallInternal` starts at 40 bytes into its line and the body of `lre_exec_backtrack` at 16, the fastest places measured (the interpreter was at 0 until a JSValue was copied in two moves of 8 bytes, see [below](#how-a-jsvalue-is-copied)). The no-ops run once per call: 66 bytes for the interpreter, 69 for the matcher. The post-link check holds each body to its place and the padding before it to no-ops, and a test builds bodies 8 bytes off their place and sees the check refuse them.

The constant pool and the jump tables a function keeps after its code are aligned by `.p2align`, which counts from the start of the function. A body at 40 bytes into its line starts 8 bytes past a multiple of 16, so the pool of the interpreter used to sit 8 bytes off 16 where it runs. Nothing read it with an instruction that needs 16 bytes (a `paddd` or a `movdqa` with the pool for its memory operand faults on a pool off 16), so nothing failed. A build in which LLVM does (a profile-guided one made 19 such reads in the interpreter) died with SIGSEGV at the positions that keep the body 8 bytes off. The generator now puts a function in its lowered object at the place its body takes in the binary (`.p2align 6` and `.skip 40` for the interpreter, `FuncPlace`), so the alignment of every pool and table holds in the binary. For `JS_CallInternal` that moves its pool 8 bytes in the body: the only generated file that changed is the one that holds it, in the displacements of the jump table and the 8 bytes of padding. The post-link check on both architectures requires every constant pool and table to sit at a multiple of its alignment in the binary, and `TestSampleRuns` runs functions that read their pool with `paddd` and `pxor` from bodies at 8, 16 and 40 bytes into a line (`testdata/run/vecpool.c`). The `front:` positions of `xform` that are not a multiple of 16 (8 and 24) move the body and its pool together, so a build whose interpreter reads its pool with such an instruction must not be run at them. Generate it with `-align64 JS_CallInternal:48` or `:0` for those two places, which keeps the pool on 16 bytes.

A change elsewhere in the engine now moves these bodies by whole lines only. It still changes their speed somewhat, as other code and data move: see [performance.md](../performance.md#code-positions) for the numbers and for how the code positions of a measurement work with the fixed places.

## How a call sets and frees its values

`JS_CallInternal` sets each local variable of a bytecode function to `undefined` when the call starts, and frees the local variables and the operands left on the stack when it returns. `OP_call` and `OP_call_method` free the function, `this` and the arguments once the call is back. Each of these loops did one value a turn. In the generated code a turn that set a local took 9 instructions: LLVM read `b->var_count` again after every store, since a store of a JSValue might have changed it, and the poll pass cuts a loop whose count it does not know into chunks with a count of their own. A turn that freed a value took about 10. An average render of the six workbench pages of tifa's example shop enters `JS_CallInternal` 113,866 times, runs bytecode in 67,076 of them, sets 520,962 locals and frees 581,838 values at the ends of the calls: the two loops took about 6.5% of its instructions.

The locals are now set four to a turn, then the two and the one left over, from a count read once, and the values at the end are freed two to a turn, while at least two are left (`sp - pval >= 2`: a tail call leaves the stack full, and `pval + 1 < sp` would then point past the frame, which C does not allow). The calls free the function and `this` on their own before the loop over the arguments. Per render, callgrind counts 167.0 M instructions for the six workbench pages rather than 171.4 M (2.5% fewer), 3.1% fewer for `r_react_ssr` and 4.8% fewer for `r_bench_table`. `q_int_arith` does not change. `q_func_call`, whose function has no local, runs 3.0% more, about 13 instructions a call: the entry keeps `b` on the stack, and tests for the two and the one left over. Reading the count once without the turns of four gave React 1% fewer instructions, cost 3.9% more on a loop of arithmetic, and was not kept. The time is in [performance.md](../performance.md#calls-for-in-and-hasownpropertycall).

Rounding the room of the locals up to four values, so that the turns need no remainder, was left out: 48 bytes more a frame would end a deep recursion of big frames sooner on the shadow stack (see [The size of the shadow stack](#the-size-of-the-shadow-stack)).

## How the interpreter calls a C function

`OP_call`, `OP_call_method` and their tail forms used to send every call to `JS_CallInternal`, which found a C function by its class and passed it on to `js_call_c_function` through the class table. For a C function that entry did no work of its own and still ran its whole prologue: 105 instructions on amd64 (`r_react_ssr` makes 452,219 such calls in a run, 28% of the entries of `JS_CallInternal`), with the stack check of Go, the no-ops of its place, the argument block and the shared return.

The interpreter now calls a plain C function itself (`js_call_c_direct`): a function of class `JS_CLASS_C_FUNCTION`, at a level of call depth under the limit and with the stack left that `JS_CallInternal` would check for it. A bound function, a function with data (`JS_CLASS_C_FUNCTION_DATA`), a proxy, a constructor call and a call near either limit go through `JS_CallInternal` as before, and so does every call from C (`JS_Call`, `js_call`). The direct call does what the entry of `JS_CallInternal` did for a C function, in the same order: it counts `POLL_WEIGHT` towards the next poll (`poll_count`, so a call still counts once), reads the interrupt flag, returns at once while an uncatchable exception is pending, counts a level of call depth, calls `js_call_c_function` with no flags and leaves the level. `sf->cur_pc` is set before either path, and `js_call_c_function` makes the frame that the stack of an error shows and changes the realm, as before. `js_call_c_function` is never inlined, so that its frame does not join the frame of the interpreter.

The stack is the part that needed care. `JS_CallInternal` takes its frame on the shadow stack before its check, so the old call checked with that frame taken, and the C function and all it called ran with that much less stack: 1472 bytes on amd64. Without it, a recursion with big frames through a C function went deeper before the stack ran out (a recursion through `f.call` with 300 locals reached 4999 levels where it ended at 4168), against the rule that a script recurses as deep as before. So the runtime measures that frame when its first context is made (`js_measure_call_frame` calls `JS_CallInternal` with `JS_CALL_FLAG_FRAME`, which only writes the stack it finds left), and `rt->stack_debt` holds the sum of it over the direct calls running. Every check of the stack (`js_stack_short`) counts that sum as taken. The measure comes right after the count of the entry and before the checks, so a host can make the first context with the call depth at its limit, an interrupt asked or little stack left, as before. It sits in the branch for a function that is not an object, which tests the type before the checks (`js_call_checks`, the same in both branches), so a call of a function pays nothing for it. Counted with callgrind (amd64, tifa d90d1fe), `JS_CallInternal` itself runs 0.86 million fewer instructions in a render of `r_react_ssr` and 0.30 million fewer in a render of the shop's workbench than before the measure was moved, where a test of the flags at the top of the entry made it run 3.5 million more. Each recursion of `TestShadowStackAtDepth` and 98 recursions through `call`, `apply`, `map`, `sort` and `Math.max` with 1 to 300 locals at limits of 5000 and 10000 end at the same depth, with the error at the same place, as before, on linux/amd64 and darwin/arm64. The debt costs one instruction at each check.

The debt belongs to one runtime. A native C host that calls from one runtime into another on the same thread hands over the call depths (`JS_SetCallDepth`) but not the debt, so each runtime counts only its own direct calls against the stack of the thread, and a recursion that hops between them may go somewhat deeper before the stack check stops it than it did. The Go host has no such case: each VM runs on a shadow stack of its own.

`JS_SetDirectCCalls(ctx, 0)` makes a runtime call every C function through `JS_CallInternal` again (its frame can never fit), for tests. `TestCCallDepth` runs recursions through `call`, `apply`, `map`, `sort`, `Math.max`, an `abs` called with no receiver, and the tail calls `return [1].map(f)` and `return apply(f, null, [])`, with 0 to 300 locals at limits of 5000 and 10000, with direct calls on and off, and requires the same depth and the same stack of the `RangeError`. Without the debt 13 of them differ. `TestCCallDepthAfterExits` leaves nested direct calls by a `RangeError`, a caught `Error` and an interrupt in one VM, and the next recursion ends as the first did. `test_tail_c_calls` of `unit-white` checks that those returns compile to `OP_tail_call` and `OP_tail_call_method`, and `test_first_context_any_state` of `unit` makes a first context at the depth limit and with an interrupt asked.

Instructions per render, callgrind at position 0.0 against main (a9d61185): the six workbench pages of tifa's shop -0.74%, its three MUI pages -0.34%, its two bench pages -2.32%, `r_react_ssr` -0.87%. Without the debt the change gave -0.84%, -0.60%, -2.66% and -1.11%. The time is in [performance.md](../performance.md#c-functions-called-from-the-interpreter).

## The end of a call skips the values with no reference count

The end of a call of a bytecode function frees its local variables and the operands left on the stack (see [above](#how-a-call-sets-and-frees-its-values)). Most of them have no reference count to give back: a local that no code set is `undefined`, and the rest are numbers, booleans and `null` as often as strings and objects. The loop still looked at them one pair at a time, 15 instructions a pair. It calls a function in its body, so LLVM kept the pointer, the count and the poll counter on the stack around the call and read them back at the head of each turn, also in the turns where nothing was freed. A function with 200 locals, none set, took 2,314 instructions more to call than a function with none: 11.6 for each local, of which about 7.5 were the free.

The tag of a value that has a reference count is negative, and every other tag is not (`JS_TAG_FIRST` is -9 and a `_Static_assert` holds the tags of the other values at 0 or more). So the tags of eight values or'd together are negative only when one of the eight needs a free. The end of a call counts its values (`i = sp - local_buf`) and goes over them eight at a time with a loop that has no call in it, so the generated code keeps its variables in registers. A group of eight with a count in it is looked at as two groups of four, and the four of a group that has one are freed one by one with `JS_FreeValue`, from the first to the last, as the loop before did, so what is freed, how often and in which order has not changed. At most seven values are left over, freed in a group of four, two and one by the bits of `i`. Nothing points past the frame: the loop tests the count of what is left, not a pointer (when the stack is full, `sp` is the end of the frame).

A function with 200 locals, none set, now takes 1,466 instructions more than a function with none (7.3 for each local). The slowest case found is a function with every fourth local holding an object, where each group of four has a value to free: with 200 locals it takes 2.4% more instructions than before (5,530 against 5,403 a call), with 32 locals 1.5% more. ## Opcodes that do a few instructions at once

Two kinds of instruction sequence that tifa's pages run often now take one dispatch of the interpreter: a read of an argument or a local and the property read by name after it, and a `typeof` test.

### A read of a local and its get_field, and the case of a switch on a string

After the compiler has done its own rewrites (`resolve_labels`) and put in the polls (`insert_polls`), `fuse_code` turns the first instruction of each of these runs into one opcode:

| Run | Opcode |
| --- | --- |
| `get_arg0` `get_field` | `get_arg0_get_field` |
| `get_arg1` `get_field` | `get_arg1_get_field` |
| `get_loc0` `get_field` | `get_loc0_get_field` |
| `get_loc8 n` `get_field` | `get_loc8_get_field n` |
| `dup` `push_atom_value` `strict_eq` `if_false8`, the case of a `switch` on a string | `dup_case_atom` |

Only that one byte changes. The new opcode has the size, stack effect and format of the instruction it replaces, and the rest of the run stays in the code as it was. So every instruction keeps its place: the jumps, the line and column table, the polls and the stack size of the function are the same as before. A run is left alone when a jump lands inside it, after its first instruction (the targets of every jump, and the instruction after a `gosub`, are marked first).

What the opcodes do:

- The four reads look at the value of the local without taking a reference to it, and follow the path of `get_field` for a property found with nothing run: an own data property, or one on the prototype chain past objects that are not exotic, or the prototype of a string or a number, or the end of the chain. Then they push the property and step over the `get_field`. In every other case, a getter, a setter, a proxy, an exotic object, `undefined` or `null`, the `stack` of an error, they push the local as the read alone does, and the `get_field` after it runs as it always did, with its own errors and line and column.
- `dup_case_atom` compares the value of the `switch` with the string of the case when the answer needs no characters: atoms are unique in a runtime, so a string that is an atom is equal only when it is the same atom, a string of another length is not equal, and a value that is not a string never is. Then it branches as `if_false8` does, poll included. Otherwise (a string that is not an atom, a rope) it does the `dup` and the rest runs.

Why borrowing is safe: on the fast path nothing runs between the read of the local and the push of the property, so nothing can change or free the local in between. Whatever can run (a getter, a proxy trap, a collection inside them) runs on the slow path, which takes the reference first, as the two instructions did. `fuse_code` runs on finished code, so the `arguments` object, closure variables and the checks of `let` and `const` before their declaration compile as before: a local in its temporal dead zone is read with `get_loc_check`, which is not fused.

The bytecode version goes from 6 to 7. `JS_ReadObject` checks code it reads with `poll_scan`, which now also rejects a fused opcode not followed by the rest of its run (`invalid bytecode: a fused opcode without the instructions it reads`), so bytecode written by a host cannot make the interpreter step over an instruction it did not check.

`JS_SetFusedOps(ctx, 0)` makes a runtime compile the runs apart again, for tests.

### typeof as one opcode

`typeof x == "<name>"`, with `==`, `===`, `!=` or `!==`, is one opcode for any string: `typeof_is_undefined` and `typeof_is_function` as before, and the new `typeof_is`, which holds the atom of the string, for the others. A negated test takes the other branch after it, or is followed by `lnot`. Before, only `"undefined"` and `"function"` were joined, and a negated test only when `if_false` came after it. `typeof x < "u"` and `typeof x > "u"` are `typeof_is_undefined`, negated for `<`, since `"undefined"` is the only result of `typeof` that does not sort before `"u"`. Minifiers write these forms: the bundles of tifa's shop hold 189 tests for `"string"`, 165 for `"function"`, 112 for `"object"`, 65 for `"number"`, 35 of `< "u"` and 11 of `> "u"`, among others. The string first (`"string" == typeof x`) is rare in them and stays as it was.

`typeof` never throws and a comparison of two strings runs nothing, so the opcode gives what the instructions gave, the result of `typeof` for an object marked as `document.all` included. `JS_SetFusedOps(ctx, 0)` also leaves the new forms as they were before.

All three together: the bench pages 0.943, the workbench pages 0.976 and the store pages 0.980.

The compiler pays for the search of the runs: `fuse_code` walks the code of each function once more, with a table that says which opcodes are jumps or the start of a run (`fuse_kind`), and keeps its marks on the stack for a function of under 256 bytes. It takes about 0.98 M instructions to compile the bundle of `r_react_ssr`, which compiles and renders in each run, so a run there takes 1.46% more instructions in all three changes. ## How a JSValue is copied

A JSValue is 16 bytes, a value and a tag. The interpreter writes one to the value stack as two stores of 8 bytes, since the value is in a register and the tag is a constant. LLVM copies one with a single 16-byte SSE move. It makes that move in two ways: the SLP vectorizer joins two moves of neighbouring 8 bytes, and a struct copy becomes a `memcpy` of 16 bytes that LLVM expands. On Zen 3 a load of 16 bytes cannot be served from two stores of 8 bytes that are still in flight: it waits until both reach the cache (24 cycles in a loop that does nothing else, against 1 for a load of 8 bytes of a store of 8). A load of 8 bytes of a store of 16 is slow too, 11 to 13 cycles.

A trace of every load and store (valgrind lackey) of short runs counted the loads fed by two or more stores in the 120 instructions before, and the loads of less than 16 bytes fed by a 16-byte store. 95% to 99.8% of them are in `JS_CallInternal`. Per 100 instructions, the first kind and then the second: `v8_richards` 0.45 and 0.87, `q_func_call` 0.28 and 0.55, `q_int_arith` 0.44 and 0.88, `r_react_ssr` 0.13 and 0.24. The opcodes that hold most of them are the calls (`call_method`, `call1`, `call`, `tail_call_method`: they copy the function and `this` into the argument block of the callee), `put_field` (it passes the object and the value by value), `put_loc*` (the copy of the top of the stack into the local), `inc_loc` (it copies the local to a temporary and reads its halves), `get_loc*` and, in string loops, `add`.

The feature tells LLVM that an unaligned move of 16 bytes is slow. A JSValue is aligned to 8 bytes only, so LLVM now expands its copy into two loads and two stores of 8 bytes, which a load of 8 bytes can be served from. The moves the SLP vectorizer makes are not expanded again, so it is off. The same trace of the generated engine finds at most 1.5% of them left (`r_react_ssr` 4,541 and 14,349 against 433,938 and 813,223, `v8_richards` 776 and 2,056 against 408,409 and 790,662, `q_func_call` 538 and 740 against 100,676 and 201,060), and no SSE move is left in `JS_CallInternal`.

What is left out, and why:

- **The small libc and the other C files.** The `memcpy` and `memmove` of the libc move 16 bytes at a time on purpose, and with the feature a copy of 17 to 128 bytes becomes 8-byte moves, twice the loads and stores. The other files hold no JSValue.
- **The feature with the SLP vectorizer on.** It leaves 29 SSE moves in `JS_CallInternal` (the copies the vectorizer made, in `put_loc` and others), and made `r_shiki_regexp` 2.8% to 3.3% slower, at 7 or 8 of 8 positions.
- **The vectorizer off alone.** It leaves 201 SSE moves in `JS_CallInternal`, the expanded `memcpy`.
- **arm64.** Not given the flags: the feature is x86 only, and nothing was measured there.

The instructions grow a little, since a copy is four instructions in place of two: against the engine before, 0.03% to 1.8% more on 13 of the 14 scripts counted, 5.3% on `q_prop_write`, and 0.7% on `r_react_ssr`. The time goes down where the copies were on the way, see [performance.md](../performance.md#the-c-engine-copies-a-jsvalue-in-two-moves-of-8-bytes).

The change moved the best place of the interpreter's body. With the code of before it was 0 bytes into its line. With 8-byte copies, 40 was the fastest of the 8 places tried on the render scripts (see [above](#where-the-interpreter-and-the-regexp-matcher-sit)).

## Atomics without threads

`Atomics.wait` converts its arguments in the order the specification gives and then throws `TypeError: cannot block in this thread`. `Atomics.notify` converts its arguments and returns 0. test262 gives the same 58 known errors as before with 66 tests excluded in `engine/test/test262.conf`, all of `built-ins/Atomics/wait` and `notify`: 7 wait on the main thread for a time out, and 59 start agents with `$262.agent.safeBroadcast`. That function begins with an `Atomics.wait` on a value that differs, which must return at once and now throws. In 53 of the 59 an agent also waits for a wake up or a time out. In 6 nobody waits and only that probe keeps them out. `api-test.c` keeps what those 6 say that still holds: `Atomics.notify` gives 0 when nobody waits, and `Atomics.wait` converts its arguments in the order of the specification (the array and its shared buffer, the index, the value, the timeout) and throws what a conversion throws before it throws that it cannot block. It also checks that a wait with a value that differs, or with no timeout, throws the same.

`Atomics.pause` is the one function of `Atomics` that is a hint and not an operation. It used to run `pause` (x86) or `yield` (arm64) as inline assembly, which the generator cannot take, so it was the last function the generator had to stub. ecma262 has an engine send the hint only if its platform supports signaling the CPU, so the function now does nothing. Its argument is still checked: undefined or an integral Number, else a `TypeError`. The test262 the tree is pinned to tests that (`non-integral-iterationnumber-throws.js`), but ecma262 dropped the argument in June 2026 (pull request 3847) and test262 stopped testing it a few weeks later (pull request 5075), so the check can go when the pin moves.

## The C API of a Go host

A Go host calls the engine through the generated code, which passes no variable arguments and takes no C function pointer from Go. So the tree has these for it:

- `JS_NewHostFunction(ctx, name, name_len, length, id)` makes a function shaped as a built-in: its name and length, no `prototype`, not a constructor, `[native code]` in `toString`. A call of it is `host_call(vm, &this, argc, argv, id)`, with at least `length` arguments readable in `argv`. The id is an int32 of 0 or more, kept in the function object next to the 16-bit magic of the built-ins (cproto `JS_CFUNC_host`). A negative id throws a `RangeError`: `host_call` keeps the negative magics for the engine's own requests. With no memory for the function, its name or its properties, it returns the exception with the out of memory error pending, as `JS_NewCFunction2` and the others that make functions do.
- `JS_NewStringChars(ctx, len, wide)` makes a string whose characters the host writes in place before the string is used. An 8-bit string gets its NUL. `len` 0 gives the empty string, a length past the most a string holds throws a `RangeError`, and no memory throws the out of memory error.
- `JS_ThrowErrorKind(ctx, kind, msg, len)` throws an error of a `JSErrorKind` (one per native error constructor) with the message cut where `JS_ThrowTypeError(ctx, "%s", msg)` cuts it: at a NUL byte and at 255 bytes. A kind it does not know throws an `InternalError`.
- `js_host_layout`, a table of int64 indexed by `JS_HOST_LAYOUT_*`, holds what a host reads and writes in place: where the reference count is from the address a value holds (-4), the mask of the length and the wide bit in the first word of a string, where its characters start (12), the most characters a string holds, and the numbers of the built-in atoms the Go API names (`message`, `stack`, `then` and the like). Nothing in the engine reads it. The generator reads it from llc's text and writes it into `engine_decl_<arch>.go` as Go constants (`layoutStringChars`, `atomMessage` and so on), and stops when the table has more or fewer entries than it has names for (`gen.HostLayoutNames`). Add an entry at the end of both.
- `JS_NewHostFunctionRelease(ctx, name, name_len, length, id)` makes the same function for an id that is a handle of the host, something the host keeps for it such as a Go function. When the engine frees the function, at the drop of its last reference, in a collection or when the runtime is freed, it calls `host_release(vm, id)` (`host.h`) once, from its finalizer. `host_release` runs no script and does not call the engine. A call that fails made no function and releases nothing: the handle is still the host's.
- `JS_NewEscapeTextFunction(ctx, name, name_len)` makes the function of `VM.RegisterEscapeText`: React DOM's `escapeTextForBrowser` in C, shaped as a built-in like the host functions, with length 1. It is a C function of the engine, called without `host_call`, so a call costs about what a call of an empty JavaScript function costs, not what a Go function costs. The argument is converted as `"" + text` converts it, the five characters become entities one UTF-16 unit at a time, and a string with none of them comes back as itself. The loops read the interrupt flag every 4096 units. See [go-api.md](go-api.md#registerescapetext).
- `JS_NewCopyPropsFunction(ctx, name, name_len)` makes the function of `VM.RegisterCopyProps`: the loop with which React copies the keys of a config into the props of an element, in C, shaped as a built-in with length 4. `js_copy_props` answers true after it copied and false when it changed nothing, and it copies only where it knows the loop can do nothing else: the config, the props, `Object.prototype`, `hasOwnProperty` and `Function.prototype.call` are checked in the call, with no state kept between calls but the five atoms in `JSContext.copy_atoms` (`key`, `ref`, `__self`, `__source`, `call`). It is bounded by 32 keys of the config and 64 slots of the shape of the props and of `Object.prototype`, so it reads no interrupt flag. See [go-api.md](go-api.md#registercopyprops).
- `JS_FreeModuleTopLevel(ctx, m)` frees the function of the top level of a module that has run to its end without an exception, with the code of the top level and its variables that no function of the module and no export holds (the module keeps its exports apart, in its export entries, once it is linked). QuickJS keeps the function until the module goes, which for a module of the context is when the runtime is freed. It does nothing to a module that has not run, still waits at a top-level `await`, or threw.

On the Go side, `host_call` of `internal/cengine` gives an id of 0 or more to the `HostFunc` registered with `SetHostFunc`, once, from an init function, and the requests of the engine to `gohost`. The function gets the shadow pointer of the call: what it passes the engine by address, and the frames of a call back into the engine, go above it.

## Strings built by appending

QuickJS grows a string in place in one case only: `x += y` on a local (`add_loc`) whose string nothing else holds. Every other append copies the whole string while the result is shorter than 8192 characters (`JS_STRING_ROPE_SHORT2_LEN`), and then makes a rope, two strings joined only when the result is read. At the `+` of `x = x + y`, or of `x += y` on an argument or a closure variable, both the variable and the stack hold the string, so its reference count is 2 and it is always copied. A string built by n short appends is so copied n times, and the copies add up to the square of its length.

That is how React builds a page: `renderToString` appends each piece of HTML, 1 to 15 characters long, to a closure variable (`push(u) { a += u }`). With any character past Latin-1 on the page the string is 16-bit. A render of the `r_react_ssr` script copied 780 MB in 400,000 copies, 96% of all its `memcpy`. Upstream QuickJS (2026-10-26) and quickjs-ng (2026-10-24) do the same. V8 makes a rope (`ConsString`) of any result of 13 characters or more.

The engine now finds the variable instead:

- `OP_add` with a string of at least 64 characters on the left whose reference count is 2 (`JS_STRING_APPEND_MIN`) reads the next instruction, after one `dup` if there is one: a `let` that a closure checks for its temporal dead zone is stored by `dup` and `put_var_ref_check`. When it stores into a local, an argument or a closure variable whose value is that same string, the other reference is the variable's, which the store drops (`js_add_string_store`).
- `JS_ConcatStringAppend` then appends in place when the block has room. Else it copies the string with room for half its length again, so the next appends go in place. `add_loc`, when its in-place append fails, takes the same copy.
- A right side of more than 512 characters makes a rope as before, and anything else (a rope on the left, other holders, a store into anything else) goes to `JS_ConcatString`.
- A property name (an atom) is never grown, see the row above.

A string built by n appends is then copied about log1.5(n) times. A string of 64 characters or more that was copied with room keeps up to a third of its block unused until it is freed. A string `+` whose left side is a string runs about 2 more instructions in the interpreter for the checks. What it gains and costs is in [performance.md](../performance.md#strings-built-by-appending).
