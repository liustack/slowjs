# Uncatchable exceptions, out of memory and interrupts

An embedder that sets a memory limit or a timeout needs the call to end when either is hit, whatever the page code does. These changes make sure no `catch`, `finally`, rejection handler or Go function of the script can take such an exception, and that the VM stays usable or at least closable after it. The Go API reports why a call ended this way (see [go-api.md](go-api.md#error-says-why-a-call-ended)).

## No leak when converting a string runs out of memory

Release: v0.26.0.

A VM that runs out of memory inside `JSON.parse`, or anything else that converts a string with non-ASCII characters to UTF-8, no longer leaks that string. `JS_ToCStringLen2` kept a reference to its argument when allocating the UTF-8 copy failed, so the string outlived `VM.Close`. QuickJS, quickjs-ng and libquickjs still had this bug when the fork was made.

## Interrupts cannot be caught through promises or iterators

Release: v0.26.6.

Page code can no longer catch an interrupt (`VM.Interrupt` or the eval timeout) through a promise or an iterator. The engine already skipped every `catch` and `finally` block for an interrupt, but its own handlers of an exception went on with it: an async function and a promise job turned it into a rejection, which an `await`, a `.catch` or a `.then` handler then received, and so did the `Promise` constructor, `Promise.try`, `Promise.all` and the other combinators, async generators and modules. A built-in that runs an iterator's `return` method on an error (`Array.from`, ...) ran it, then threw the interrupt again as an error a `catch` could take, and any later error replaced it. Now an uncatchable exception stays pending until the Go call that ran the script takes it, and while it is pending every call into javascript fails at once. So no `catch`, `finally`, iterator `return`, generator `finally` or rejection handler runs, and the call returns the interrupt, as it does for a script without promises. Where a built-in only records the error, such as a resolve function that rejects its promise when reading `then` throws, the code after it runs on until its next function call, which fails. `ExecutePendingJobs` stops at the job that failed with an interrupt and leaves the rest queued, where it used to run them all.

## Out of memory is uncatchable

Release: v0.26.6.

Running out of memory is uncatchable too, like an interrupt, and the call returns `*Error{Name: "InternalError", Message: "out of memory"}`. Page code used to catch it, so a framework catching every error to show a fallback reported it as an error of the page, and a `finally` block or a rejection handler ran with no memory left. Every way the engine runs out of memory now ends this way: the engine's own out of memory error, the regexp engine running out of memory (it used to throw `InternalError: out of memory in regexp execution`, or a `SyntaxError` when compiling a pattern), and an error the engine could not build. That last case used to throw a catchable `null`, and an error whose message could not be allocated got the exception marker as its message, which read back as nonsense. Now the engine builds the message first, and if the message, the error object or setting the message fails, it throws `null`, uncatchable, which the VM reports as the same out of memory error. A script that throws `null` itself still gets `null`. Page code cannot fill memory on purpose and catch the failure any more: allocating until it fails ends the call. The VM stays usable after the call, and `Close` frees everything.

## Interrupts and out of memory inside Go functions

Release: v0.26.6.

An interrupt or running out of memory inside a Go function that javascript called ends the whole call too. That covers converting the function's arguments or result, and javascript the function evaluates on the same VM (`Eval`, `Call` and the like), from a function registered with `RegisterFunc` or `RegisterHostFunc`, a `Then` callback, or the module loader and normalizer. The Go function still gets the error, but the exception stays pending until it returns, so further calls into javascript fail at once. Whatever the function returns, the script that called it gets the original uncatchable exception. It used to get a catchable `TypeError` wrapping the message (for example `calling take: argument conversion error: InternalError: out of memory`), or the function's own result when it dropped the error, so a timeout in nested javascript could be caught or lost and the script ran on. The `intl` package now takes its host functions off the global object before its install changes anything, so that an install cut short this way leaves none of them in sight once the next use has installed.

Tests: `hostuncatchable_test.go`, `intl/install_test.go`.

## A panic in a Go function

Release: v0.26.6.

A panic in a Go function that javascript called (`RegisterFunc`, `RegisterHostFunc`, a `Then` callback) no longer unwinds through the engine. The VM recovers it, ends the javascript with an uncatchable `InternalError` (`panic in Go function <name>: <value>`) as for an interrupt, and panics again with the same value in the Go code that called javascript: in `Eval` or the like, or in the Go function one level up when a Go function called the javascript. Page code sees no catch or finally run for it. The panic used to unwind through the engine, which kept pointing at stack frames that were gone. The VM looked fine after a recover, but the next error it made walked those frames, forever when a new frame took the place of an old one, so the eval timeout of that VM never fired again. The panic value is the same, but its stack trace now starts where the VM panics again.

Tests: `hostpanic_test.go`.

## Compiling with little memory left

Release: v0.26.6.

Compiling a script, a function body, `eval` code or a regexp with little memory left fails with the same out of memory error. The engine used to crash there (a Go panic on a write before or past the code buffer, or a double free), report a `SyntaxError` the script does not have, or, in `Compile`, return bytecode cut short, bytecode with the out of memory error left pending, or `errors.New("OOM")`. The parser went on after its code buffer failed to grow and patched code in place at positions it had noted, past what the buffer held (a Go panic on an empty buffer, or a write past the end of a full one), and the passes after it assumed the buffer was whole. Now the parser stops at the next token once the code buffer of the function it parses failed, and checks it before each patch that does not wait for a token, the buffer takes no more bytes once it failed, and each pass that reads it back stops with the out of memory error. A scope the parser fails to push marks the function's code lost too, and its scopes then stay as they are, each later push failing with the out of memory error: the pop after a failed push used to take off the scope around it, until a pop read before the scope array. The pass that resolves jumps frees, when it fails, the jump records of the labels it has not reached yet, which used to leak. When shrinking the line table of a function fails, the compile keeps the table and leaves no error behind: it used to work and leave the out of memory error pending, for the next call to report.

## Nested calls keep the outer deadline

Release: v0.26.2.

A Go function that evaluates more javascript on its own VM, such as `intl` installing its code from inside the page's first call, no longer sets the eval timeout again or drops an `Interrupt` asked for meanwhile. The VM counts how deep the calls into javascript go, and only the outermost one sets the deadline and clears the request (see [architecture.md](../architecture.md#the-eval-timeout-and-interrupt)).

## The eval timeout runs on the monotonic clock

Release: v0.26.7.

The eval timeout (`SetEvalTimeout`) runs on the monotonic clock. It used to run on the wall clock, so setting the system clock while a script ran (NTP, a person, a machine waking from sleep) moved the deadline: set back, the timeout fired that much later or never, and set forward, at once. Even without a jump the two clocks drift apart by a few microseconds per 100 ms, so a server that keeps its own deadline on Go's monotonic clock could see the engine interrupt before that deadline. A timeout too long for the clock, up to `math.MaxInt64`, never fires: the deadline used to wrap around to the past and interrupt the call at once.

Test: `clock_test.go`.

## Interrupt is safe during and after Close

Release: v0.26.10.

`VM.Interrupt` can be called from any goroutine while the VM closes and after `Close`, where it does nothing. It used to read the address of the interrupt flag, which `Close` frees and then clears, so a watchdog firing just as the script finished could write to freed memory or panic on a nil pointer. The race detector also reported a race when `Interrupt` stopped a script and the VM was closed after the call returned. That one was not real: the two goroutines are ordered by the atomic flag, but the flag is in C memory, outside Go's heap, where the race detector ignores atomic operations. `Interrupt` and `Close` now meet at a mutex in Go memory that `Close` never clears.

Test: `interrupt_test.go`.

## Compiling a regexp counts toward the interrupt check

Release: v0.27.2.

The eval timeout and `Interrupt` stop a loop that compiles regexps within a few milliseconds, and stop one long compile in the middle. The interpreter calls the interrupt handler once every 10000 polls, and a compile was one poll however long the pattern, as it is upstream. A loop that built `new RegExp` from a new long pattern each time ran thousands of compiles between two checks: with a 10 ms timeout, `'(a|b|c)+d'.repeat(200)` stopped after 170 ms on a Mac, 225 ms on linux/amd64 (AMD EPYC) and over 2 s on a loaded machine, a pattern of 2000 alternatives after 3.6 s, and a class of 3000 CJK characters after 184 s. One compile of 100000 alternatives ran its full 8.5 s.

The regexp parser now counts a step on the counter of the context for each term, alternative and atom of a class, and one more for each 256 bytes of code or ranges the step moves (an alternative moves the code before it to insert its split, an atom of a class copies the ranges before it, a term of a lookbehind moves in front of the terms before it), through `lre_poll_interrupts`. When the counter runs out it calls the handler through `lre_check_timeout`, as `lre_exec` does. When the handler asks to stop, the parse fails with the message `interrupted`, the compile frees what it built as for any syntax error, and `js_compile_regexp` throws the uncatchable interrupt, the same error the interpreter throws, so a catch block does not see it. A lookup in the regexp cache counts the bytes of the pattern it hashes and compares (see below). On the same machine every one of those loops now stops 10 to 12 ms after it started, and the long compile at 10 ms.

## Parsing and building strings count toward the interrupt check

Release: v0.27.2.

A loop of built-in calls that parse source or build long strings stops within a few milliseconds of the eval timeout or `Interrupt`. Each such call was one poll of the interrupt check however much it did, so with a 10 ms timeout on linux/amd64 (AMD EPYC) a loop of `JSON.parse` of 60 KB stopped after 8.6 s, `JSON.stringify` after 11.7 s, `eval` of 500 functions after 10 s, `new Function` after 5.3 s, `'x'.repeat(1e6)` after 13 s, `padStart` after 18 s, `replaceAll` after 18.7 s and `join` of 100000 numbers after 37.5 s.

`js_charge_interrupts` counts steps on the counter of the context and leaves the call of the handler to the next poll of the interpreter, so it throws nothing where it is called. The counter stops at 0, so a huge charge cannot wrap it to a large count. `js_parse_init` counts a step for each byte of the source it is given, for `eval`, `new Function`, scripts, modules and `JSON.parse`: parsing and compiling cost far more for each byte than copying, and one step for each 32 bytes left a loop of `eval` 10 to 15 ms late, and 130 ms late on a loaded machine. `string_buffer_init2` and `string_buffer_realloc` count a step for each 8 characters of room they make, for `JSON.stringify`, `join`, `repeat`, `padStart`, `replaceAll` and every other built-in that builds a string in a `StringBuffer`. The regexp cache counts a step for each 32 bytes of each pattern it looks up. A step counted too many only calls the handler, which reads a flag and the clock, a little earlier. Those loops now stop 10 to 15 ms after they started on the same machine. One call still runs to its end: one `JSON.parse` of 13 MB takes 385 ms, one `repeat` of 200 million characters 620 ms, one `eval` of 50000 functions 1.1 s, and the timeout stops the script right after. `indexOf`, `lastIndexOf` and `includes` of strings count the indexes they look through ([strings.md](strings.md#searches-skip-to-where-the-string-is)). The other built-ins that scan or sort without building a string (`indexOf` and `includes` of arrays, `split`, `fill`, `sort` of arrays and typed arrays) do not count yet: a loop of them stops 3 to 29 s late with such inputs.

Neither change slows a render. Without PGO, on linux/amd64 (AMD EPYC), against v0.27.1, in 6 rounds over 3 code layouts with the order of the two builds flipped each round, the sums of the P50 render times take 0.993 of the time on the pages of tifa's example shop (0.978 to 1.002) and 0.997 on the MUI pages of its test app (0.989 to 1.007), with the same HTML and the same memory. Compiling one regexp of 900 KB takes 23 ms where it took 21 ms, and a compile of 100000 alternatives no longer than before. A script that ran past its deadline inside one long compile used to finish when nothing polled after it: `eval` of 50000 functions under a 10 ms timeout returned after 1.1 s, and now throws the interrupt right after the compile.


## Every method that can run javascript has the eval timeout

Release: Unreleased.

`GetProperty`, `GetPropertyValue`, `SetProperty`, `SetPropertyValue` (and the `Value` methods that call them), `Value.MarshalJSON`, `Value.Any` and `ErrorFromValue` ran with no eval timeout. They entered the engine as a call that runs no script (`outer`), so a getter, a setter, a proxy trap, `toJSON`, a replaced `BigInt.prototype.toString` or a `toString` that `ErrorFromValue` calls on an error could run as long as it liked. With a 10 ms timeout, a getter and a setter of 200 ms ran to the end and returned 42 and no error, where `Eval` of the same loop returned the interrupted error after 10 ms.

Now each of them enters as `Eval` and `Call` do (`enter` and `leave`), so the outermost one arms the deadline, a pending `Interrupt` stops it, and a script that keeps running past the grace is killed. The conversion of the result to a Go value and the reading of an error are inside the same call and share its time. `ErrorFromValue` leaves a field empty that the timeout cut off, and panics on a VM a kill left good only for Close, as it did. Reading the error of any other call that comes back to Go outside a script (`RegisterFunc` on a name that cannot be defined, `RegisterCopyProps`, `RegisterEscapeText`) is bounded by `ErrorFromValue` too, which `takeException` calls.

`SetPropertyValue` and `SetProperty` return the exception the setter threw as their error. They used to return `failed to set property` and leave the exception pending in the context, for the next call that took one to find.

Test: `apitimeout_test.go` (`TestAPIEntriesHaveTheEvalTimeout`) runs each method with a 10 ms timeout on loops of 300 ms and requires the interrupted error within 150 ms, `killed_test.go` (`ErrorFromValue` after a kill).
## Loops over a long string read the interrupt flag in steps

Release: Unreleased.

The loops listed here read the interrupt flag at least once in every step of work, so that a script stops within a few polls of `Interrupt` or the eval timeout, far inside the 1000 polls and 50 ms after which a poll kills it. Loops that are not listed have no such bound (see the end).

The steps are about 65,536 characters, and not exactly: a leaf of a rope counts for one more than its length, an escape of a JSON string is counted when it is whole (up to 5 bytes past the step), a surrogate pair counts for one in `JSON.stringify` and the conversion of a wide text to a C string reads the flag after a whole pair (65,537 units), and a character of 8 bits that is looked at and then copied into a buffer of 16 bits counts for two (`JSON.parse` and `JSON.stringify`, so such a run is read every 32,768 characters). The steps are for the hash of a key of a Map, a Set or an object, for the compare of two strings or ropes, for the loops of a pad, for the runs, escapes and wide characters of the string of a JSON text, for the widening of a buffer to 16 bits, and for the runs and escapes of `JSON.stringify` of a string. 1,048,576 characters for the scan and the copy of a long piece (`slice`, `trim`, `split` and the like). 1,048,576 bytes for the copy of a buffer that grows.

Where a step of work is the end of one phase and the start of the next, the budget goes on or the flag is read between them: the end of a scan goes on into the copy, the last leaf of a rope into the first of the next, the hash of a key is followed by a read of the flag before its compares, the compares of the candidates of a chain of a hash table share one budget (a compare that ends at a difference counts the step it made), and the flag is read before the first step of the copy of a buffer that grows, so that the scan that filled the buffer is not added to it. A JSON string keeps one budget for its runs and its escapes, and so a string of short runs and escapes, or of nothing but escapes, is read every 65,536 bytes too.

A string shorter than a step is compared at once and hashed at once: that is a window of fewer than 65,536 characters for each string, fixed by the limit of 65,536 that the hash of a key (`map_hash_key_poll`, `js_new_string_atom`, `JS_NewAtomLen`), the compare (`js_string_eq_polls`) and the search (`js_string_find`) all use. A loop that makes many such compares keeps a budget (`js_short_eq_budget`): the elements of an array, and the records of a chain of a Map or Set, add the length of each pair of strings of one length they compare, and the flag is read when the sum would pass a step. The hash of many keys of fewer than 65,536 characters one after the other, by a loop of the engine that is not bytecode, is not counted (see the end).

What is covered, by what it was:
- `===`, `!==`, `==`, `!=` and `switch` on two strings of which one is a rope or both are longer than a step, and the key compare of a Map or Set: they used to compare the whole strings in one call. The operators of the interpreter (`js_strict_eq_slow`, `js_eq_slow`) and the Map and Set code call `js_string_rope_compare` with its `poll` argument, which reads the flag and can throw.
- `Array.prototype.indexOf`, `lastIndexOf`, `includes` and `Object.is` on strings: of a step or more with `js_string_rope_compare`, and shorter ones with the budget of `js_short_eq_budget` (`js_strict_eq2_poll`).
- `indexOf`, `lastIndexOf`, `includes`, `startsWith`, `endsWith`, `replace`, `replaceAll` and `split` with a pattern of the length of what is left of the string, so that one index is left to compare (`js_string_find_at`).
- A property key of 65,536 characters or more: its hash, and its compare with the atom of an equal string (`js_new_long_string_atom`).
- `JSON.parse`: the text as a C string (`js_string_to_cstring_json`, a copy of `js_string_to_cstring` with the reads: a text shorter than a step is scanned and encoded with no count and no read), the runs, escapes and wide characters of a string, and the widening of the buffer when a character above 0xff follows a long ASCII run (`string_buffer_widen`). `padStart` and `padEnd` write a narrow string into a wide buffer the same way (`string_buffer_write8_wide_long`, for a string of a step or more: a shorter one is copied by the loop of `string_buffer_write8`, which counts its length).
- `JSON.stringify` of a string: the runs and escapes (`json_quote_run`).
- A string buffer holding more than 1 MiB that has to grow is copied by `string_buffer_realloc2` in steps of 1 MiB, with a read of the flag before the first, and not by the allocator in one call. It needs the new block while the old one is there. The allocator needed that too when it could not extend the block in place, but it could remap a block of its own chunk with no second block, which the copy cannot, so the peak use of memory can be higher (by one block of the size of the old one, for the time of the copy). The limit of the memory is checked as `heap_realloc` checks it, against the count less the old block (`js_malloc_moving` raises the limit by the size of the old block for the one request), so a buffer that fits the limit once the old block is freed still grows; the count of the heap is over the limit for the time of the copy, until the old block is freed. The tests give the limit one byte above and one byte below that.
- `replace` and `replaceAll` with a string for the pattern search a string of at most 256 characters with a plain loop, which compares at most 256 times 256 characters in all and so needs no read of the flag, and a longer one with the search of `indexOf`.
- A Map or Set looks for a key that is a rope or a string of a step or more with the compare that reads the flag (a record of another length is known to differ), and for any other string with the compare of `js_short_eq_budget`. A key that is not a string is compared at once.

Making an error reads no interrupt flag, and `engine/test/cycles.sh` checks that `JS_ThrowError2` reaches no function that does. The loops above are therefore kept out of what an error needs: `JS_NewStringLen`, which makes the message and the stack of an error, decodes a text with a character above 127 twice (to count the units, then to write them) into a string of the exact size, and not into a string buffer; and the conversion of the text of `JSON.parse` to a C string is `js_string_to_cstring_json`, a copy of `js_string_to_cstring` with the reads, not a flag of it.

Tests: `test_poll_work_gaps` in `engine/test/unit-white.c` does not count the reads of the flag but the work between two of them. The loops say what they did with `JS_WORK(n)` (nothing in the engine), `white.c` adds it up between two reads of the flag, and a call must keep the longest stretch, the one before the first read and the one after the last included, to the step, and add up to the work it has to do. Every case gives its total. The cases are a pad whose filler ends in the middle of a step, a slice whose scan ends in the middle of a step, keys made of leaves of 65534, 65536 and 65535 characters, strings of 65537 and 131071 characters hashed and then compared, 64 keys of one hash that differ from the key asked for at the first step, the strings of a JSON text of one run, of escapes only, of short runs and escapes and of `\u` escapes, a wide character or a wide escape after 70,000 ASCII characters, a pad with a wide filler, `JSON.stringify` of runs, escapes and wide characters, the searches, `indexOf` and `Object.is` on equal strings of 200,000 characters, an array of 40 elements that are one string of 65,535 or of 65,536 characters searched for another that differs in the last one, 32 keys of one hash and 65,535 or 65,536 characters in a Map, a Map and an object, and JSON runs of narrow characters into a buffer that is wide already (parse and stringify). `test_buffer_copy_work` also gives the work of a copy that follows 60,000 units of work, and `test_buffer_limit` grows a buffer at the limit that has the room for the new block and not for both and one byte below. `test_buffer_copy_work` gives the work of the copy and the widening of a buffer of 1,500,000 characters. Putting back, one at a time, the escape count of a JSON string, the polls of the widening, the count of a compare that ends at a difference, the read of the flag between a hash and its compares, the polls of `js_string_find_at` and the polls of the compare in `Array.prototype.indexOf` makes a test fail, and so does taking out, one at a time, the read of the flag before the copy of a buffer, the budget of the short compares (`js_short_eq_budget`), the doubled count of a narrow run into a wide buffer, and the room of the old block in the limit (`js_malloc_moving`). `test_rope_polls`, `test_rope_key_compare_polls`, `test_long_key_polls` and `test_long_ops_polls` in `engine/test/unit.c` stop each call at a set read of the flag, and `TestInterruptStopsLongBuiltins` and `TestInterruptStopsLongKeys` (`internal/cengine`) stop it at six places of its polls in the generated engine, each key with a VM of its own, as the first use of a string as a key makes it an atom. A case may allow a later stop for the trials that have a reason: the first two of `padEnd`, which writes the 64 MiB of the string with one `memcpy` first, and the first of `padStart` with a filler of 32M characters, which lands in the allocation of its buffers. `padStart` with one wide filler has its trials in the last 40 % of the call, which is the copy of the string into the wide buffer (`string_buffer_write8_wide_long`), and a stop there takes at most 16 polls.

Not covered, and the bound is the length of the input:
- The compare of two equal strings by the entries that return a boolean and cannot report an exception and use `js_strict_eq2`, `js_same_value` or `js_same_value_zero`: the checks of `Object.defineProperty` and `Reflect.defineProperty` on a value, the invariants of a Proxy, `JS_IsStrictEqual`, `JS_SameValue` and `JS_SameValueZero` of the C API, and the like.
- `<`, `>`, `<=` and `>=` on two flat strings that are equal to the end (`js_string_compare`).
- The copy of a long piece of 8 bits into a string buffer of 8 bits when the buffer has the room (`memcpy` in `string_buffer_write8`, of tens of millions of characters), the copy of a piece of 16 bits (`string_buffer_write16`: the scan for a character above 0xff and the copy, which `JSON.stringify` of a string of 16 bits counts once), the final shrink of a buffer by `string_buffer_end`, and the leaves of a rope when it is made flat. The copy of a piece of 8 bits into a buffer of 16 bits is covered (`string_buffer_write8_wide_long`).
- The rehash when a Map or Set doubles its table (about 1,100 polls at 8 million entries, which a VM of the default 128 MiB cannot hold), and the free of a very large result after a stop (about 1,700 polls for 8 million small objects, likewise).
