# Strings

## Searches skip to where the string is

Release: v0.27.3 (timings in this entry were taken on the engine of that release, before the C engine).

`String.prototype.includes`, `startsWith`, `endsWith`, `indexOf` and `lastIndexOf` skip to where the string they look for is. Upstream compares the whole string with `string_cmp` at one index after the other, and `string_cmp` reads each character of both strings through `string_get`, so a search that finds nothing costs a call and a few character reads for each character of the string it looks through: about 3 ns a character. tifa looks for the marker of a Suspense boundary in the whole HTML of a page after each render, which was about 1% of a render of tifa's example shop.

Why it gives the same results: the loop still makes its own comparison at the index the search returns, so a match is only ever one `string_cmp` confirms, and the search returns the first index in the loop's direction where the characters are the same, which is the first one the loop would have found. A string of 16-bit characters may hold only characters below 0x100, so the widths of the two strings do not decide whether there is a match. `string_indexof`, which `split`, `replace` and `replaceAll` use, is left as it is: it already skips to the next index of the first character, and its strings are mostly short, where a call costs more than it saves.

A loop of `indexOf`, `lastIndexOf` or `includes` that finds nothing in a string of 1 MB used to stop 170 ms, 6.9 s and 170 ms after a 10 ms timeout, and 340 ms in a string of 16-bit characters: each search was one poll however long the string. They now stop within 20 ms of the start, building the string of 1 MB included. `startsWith` and `endsWith` compare at one index and count nothing. Over 6 rounds in 3 code layouts against the search without the count, the median of each search of about 20 characters takes 0.98 to 1.02 of the time, as much as `replace` and `split` move, which run none of the changed code (1.031 and 1.006), and searches through 1 KB and 100 KB 0.995 to 1.002. A miss of `indexOf` or `lastIndexOf` came out 1.7% slower in both of two builds of the count, about 2 ns, which is inside that spread but may be real.

Looking through 100 KB of HTML that does not hold the string takes 81 µs rather than 320 µs, and 87 µs rather than 271 µs when the HTML has 16-bit characters. A miss in a string of about 20 characters takes 108 ns rather than 164 with `indexOf` and 102 rather than 119 with `includes`, `lastIndexOf` in 1 KB 1.6 µs rather than 3.1, and `startsWith` 102 ns rather than 107 (linux/amd64, AMD EPYC 7B13, one core, without PGO, each a loop in javascript of the same call). In a Go CPU profile of tifa's six shop workbench pages, `String.prototype.includes` went from 1.06% of the samples to 0.27%: its own search from about 0.75% to 0.13%, and what is left is mostly making the rope of the HTML one string, which the render then reads anyway. On the MUI pages of tifa's test app it went from 0.63% to 0.11%. A render of the six shop pages takes 0.995 of the time (0.975 to 1.032 over 6 rounds in 6 code layouts), and the MUI pages 1.003 (0.970 to 1.024), without PGO: the gain is smaller than the spread between code layouts, which alone moves a render by about 2%. No page and no micro benchmark got slower.

The change is in C (`engine/quickjs.c`), with a search of its own: `js_string_indexOf` and `js_string_includes` call `js_string_find`, which returns only an index where it compared the whole needle, so that index is taken without comparing it again. One character is looked for with `memchr`, or a loop in a string of 16-bit characters and toward the start. A string of up to 8 characters is looked for by finding its first character that way and comparing the others there, at most 8 units of work for each index, which spares the work the Two-Way search does on the needle first (about 20 ns a search). A longer string is looked for with the Two-Way search of musl's `memmem`, written for 8-bit and 16-bit characters, for a needle of the other width and for both directions. Its time is linear in the lengths of the two strings whatever they hold, also for a needle that matches almost everywhere: on linux/amd64 (AMD EPYC 7B13), comparing the needle at each index where its first character is took 2.5 s for `'a'.repeat(131072).indexOf('a'.repeat(65536) + 'b')`, and the Two-Way search takes 0.5 ms. A search with one index to look at, as `startsWith` and `endsWith` have and as two strings of the same length have, compares the needle there and does not check the interrupt counter: that is linear in the length of the needle, as `===`, concatenation and the other operations linear in the length of a string are, and none of them checks it. `engine/test/compare/stringsearch.js` (run by `engine/test/compare.sh`) searches with long needles of few letters that repeat, and `engine/test/unit.c` checks that searches in a long string run the interrupt handler, that one long search calls it many times, with a match or none, in strings of each width and in one of each, and ends with the error `interrupted` when it asks to stop, which `try` and `catch` do not catch, that the context runs scripts and searches again once the handler is gone, that a search with one index to look at does not call it, and that needles that match almost everywhere take a fraction of a second, forward and back, in strings of each width and in one of each.


## A symbol has a string of its own

Release: v0.30.2.

`Symbol(s)` turned the string `s` itself into the symbol, even while an array, a variable or the function that holds a string literal of digits (`Symbol("12")`, which every run of the function shares) still held it. And `description` gave the symbol itself back as a string. Either way a string held by the script kept the symbol alive: a `WeakRef` to it never emptied and a `FinalizationRegistry` never called back, for as long as the string lived. Node frees such a symbol at the next collection.

Now a symbol and the strings the script sees never share their characters. `JS_NewSymbol` (`engine/quickjs.c`) gives `Symbol(s)` a copy of `s` when something else holds `s` or when `s` is an atom, and `description` (`js_symbol_get_description`) gives a copy too. The other uses of the string of a symbol, its name in a message, `String(symbol)` and the name `[desc]` of a method, already made a new string of it or kept it only for their call, and still share it. A copy of more than a million characters is made in steps that read the interrupt flag (`js_string_copy`, through `js_sub_string_long`). What cannot die keeps the old sharing: a registered symbol (`Symbol.for`), which cannot be held weakly and the symbols of the runtime, such as `Symbol.iterator`. A string atom is still made of the string itself whoever holds it: it is the same string to every holder.

The cost: the argument of `Symbol` holds the string passed to it while `Symbol` runs, so a symbol of a string is always a copy, one allocation the length of the description. A literal that is not all digits, such as `Symbol('react.element')`, is an atom and was copied before too. Each read of `description` allocates its copy, where it shared the string. Upstream QuickJS shares the string both ways.

`engine/test/compare/symbol_shared_string.js` (run by `engine/test/compare.sh`) checks that the symbols of strings held by an array, a variable and a literal of digits, and a symbol whose description is held, are freed after the job that made each `WeakRef` ends (`clearKeptObjects()`), that the strings stay strings, the description and `Symbol.for` of them, and descriptions of millions of characters, of 8 and 16 bits. Its file is what Node 24 prints. `test_symbol_copy_oom` in `engine/test/unit-oom.c` runs out of memory at each point of making symbols of held strings and of reading their descriptions, and finds the out of memory error and nothing left behind.

## The hash table of atoms holds one atom for two buckets

Release: v0.30.5.

An atom is the number the engine gives a property name or a string it keeps once. Making a key from a string, such as `o['key' + i]`, a JSON key or a name in the parser, looks the string up in the hash table of atoms (`__JS_NewAtom`) and walks the chain of its bucket. Upstream doubles the table when it holds two atoms a bucket, so a lookup walks up to about two atoms on average, each a load from the array of atoms, before it finds its own or none. Now `JS_ATOM_COUNT_RESIZE` in `engine/quickjs.c` doubles it at one atom for two buckets. In a counting build of the native C tree, the steps along the chains fall from 87K to 16K a render on MUI's orders page, 38.5K to 5.4K on MUI's home page, 10.1K to 1.8K on the workbench studio page and 6.7K to 0.9K on the shop's English home page.

Why it is safe: only the size of the table changes, never which atom a string gets, its number or the order of keys. The table grows by the same `JS_ResizeAtomHash` at another count, and when it cannot grow the atom is made in the table it has, as before. The HTML is the same on the 24 pages of the shop, MUI and React, and test262 gives the same 33 known errors.

What it costs: the table takes four times the room. After 20 renders and a full collection, on the native C tree, a VM of the shop holds 196 KB more (13.65 MB rather than 13.45 on its home page) and one of MUI 49 KB to 73 KB more. The footprint does not change. The smallest room in which a new runtime makes 600 names (`test_key_names_oom`) moved from 62,096 to 68,240 bytes.

What it gains: the instructions of a render do not move by more than the noise of the rounds (tifa's `test/ssr` on an Apple M4, three rounds, within 0.3% on each group). Fewer steps along the chains are fewer loads, each a likely cache miss, so any gain shows in time, not in instructions.

Tests: `test_key_names_oom` in `engine/test/unit-oom.c` sweeps a script that makes 600 names from no room to 80 KiB, so that some room lets it work with the larger table, and every other check of `unit`, `unit-api`, `unit-white` and `unit-oom` passes as before.

## An empty string on the left of `+` gives the string on the right

Release: v0.30.5.

`'' + x` is how React and much other code make a string of a value, and a template literal that starts with a substitution (`` `${x}px` ``) compiles to the same `+` after an empty string. QuickJS gave back the left string when the right one was empty, and the right one when the left was empty and the right a rope. An empty left and a flat right went to `JS_ConcatString2`, which grows the left string in place when it can. The empty string is almost always the atom's, which never grows in place, so it allocated a new string and copied the right one into it. `JS_ConcatString` (`engine/quickjs.c`) now frees the empty left string and gives back the right one when the right is a flat string of at most 512 characters. A longer right side still makes a rope, as before: it is rare on the pages.

Why it is safe: a string has no identity a script can see, and the result has the same characters and the same width. The right string now has one more holder, so the appends that grow a string in place, which ask for no holder but the ones they know of (`js_concat_string_in_place`), copy it rather than change it. An atom's string can now be the result, and those appends refuse an atom already. What keeps the result now keeps the right string itself: `new RegExp(p, f + 'g')` with an empty `f` puts the atom's `'g'` in the regexp cache rather than a copy, so three scripts of the corpus (`q3-regexp-prefix.js`, `q3-regexp-skip.js` and `shikire.js`) end with one more atom and the same objects, and their goldens were written again. While the regexp cache keeps such a flags string, this costs at most 32 bytes and one atom more than the copy did, and less when several entries share the atom, since each of them held a copy before. The injection goldens of the two regexp scripts were written again for the same reason.

What it gains, counted on the native C tree at 3ae98161 (linux/amd64 callgrind, the whole process, the difference of three and one timed renders after one warm render): React's page renders 2,151 such sums a render and runs 1.28% fewer instructions, MUI's three pages 4,306 and 0.49%, the fourteen store pages 2,426 and 0.17%, the six workbench pages 1,018 and 0.21%, about 150 to 210 instructions a sum.

Tests: `test_string_empty_left` in `engine/test/unit-white.c` checks that `'' + s`, `e + s` and `t = t + s` with an empty local, `''.concat(s)` and `` `${s}` `` give back the string `s` itself, and that an append to the result in place (`add_loc`, and an add into a local) leaves `s` as it was (`s` has 76 characters, past the 64 below which nothing is appended in place). With the check of `js_concat_string_in_place` loosened by one holder, the add into a local changes `s` and the test fails.

## Two strings are added without the generic path

Release: v0.30.7.

In the register loop an add whose operands are not two numbers went to `rv_binop_slow`, the slow side that add, sub and the compares share: it reads the op and its operands again, tests for numbers, then for two strings, and only then calls `JS_ConcatString`. Most adds a page makes are of two strings, the HTML, the class names and the keys it builds. Now the add handlers send two strings to `rv_add_str` (`engine/regvm-ops-basic.h`), which does only that: it takes the operands as `rv_binop_slow` takes them (a temp moved, a local, an argument or a constant copied) and calls the same `JS_ConcatString`, or `js_add_string_into` when the result goes into a local or an argument, which may grow the string of the local in place. The handler tests the tag of one operand before the call and `rv_add_str` tests both. When one is not a string it returns with nothing done, and the handler calls `rv_binop_slow` as before.

The forms of add, and what each does now:

- ADD (into a temp), ADDL (into a local or an argument), ADDK and ADDKL (a constant on the right, `x + 'px'`): the handler tests the left operand. All four go to `rv_add_str`.
- KADD (a constant on the left, `'<' + x`): the handler tests the right operand, since the left one is a constant. It goes to `rv_add_str`.
- ADDLOC and ADDLOCK (`s += x` on a local) and ADDVR and ADDVRC (`s += x` on a closure variable) already added two strings in their own helpers, `rv_addloc_slow` and `rv_addvr_slow`, without `rv_binop_slow`. They are unchanged.
- `o.s += x` and `o[k] += x` are a read, an ADD and a write, so they take the new path. SUB, SUBL, SUBK, SUBKL and KSUB never do.

Every page runs the five forms that changed. A render of MUI's orders page adds two strings 34,500 times through them, its home page 16,600, the store pages 13,700 (home) and 19,400 (products), the workbench pages 7,300 (studio) and 3,900 (stats) and React's page 2,700. KADD makes 10% of them on MUI's orders page and 65% on React's.

Why it is safe: the guard is that both operands have the tag of a string or of a rope (`JS_IsString`), and nothing else. Both are primitive strings then, so the add runs no code of the script: no `valueOf`, `toString` or `Symbol.toPrimitive`, those of `String.prototype` included. The result is what `rv_binop_slow` gives for the same operands, since it calls the same function on them: the same kind of string (a flat string of 8 or 16 bits, or a rope, by the same rules of length), the same characters, the same append in place into a local, the same `InternalError: string too long` past 2^30-1 characters, and the same exception when memory runs out. An atom's string and a string that keeps the atom it is as a key are strings like any other here: the result is a new string, or the right operand itself when the left is empty ([above](#an-empty-string-on-the-left-of--gives-the-string-on-the-right)). A String object, a number, a BigInt, a Symbol or any other value on either side goes on to `rv_binop_slow`. `rv_add_str` has the one place to throw that `rv_binop_slow` has for an add of two strings, after it takes the operands, so the places of the throw injection and their goldens stay the same. The frame of `JS_RegvmRun` stays at 256 bytes of shadow stack on amd64 and 176 on arm64.

What it costs: an add of a number and a value that is not a number (`n + ''`) tests one tag more before `rv_binop_slow`, about 3 instructions. An add whose tested operand is a string and whose other one is not (`s + n`, `s + obj`, `1 + s`) also pays the call of `rv_add_str`, which returns at once. Of the seven pages, the store's products page makes the most adds that are not of two strings and go to `rv_binop_slow`, about 3,100 a render, and only part of them pay it. The micro benchmark `int_to_string2` runs 0.7% more instructions natively. The part of the handlers that adds two ints or two floats is the same instructions as before. The change touches the C of `JS_RegvmRun`, so until the profile of tifa's pages is trained again the generator compiles that function with no profile and the pages run 0.6% to 1.1% more instructions, not fewer.

This is not "`rv_binop_slow` with 5 words" of [Tried and not done](../performance.md#what-was-tried-and-not-done), a branch that passed fewer argument words to `rv_binop_slow` for every slow add and compare and was not taken, because clang laid out the strict compare handler of `JS_RegvmRun` another way. This change leaves `rv_binop_slow` and its calls as they were and takes the adds of two strings away from it.

Tests: `engine/test/compare/string_add.js` (its output checked against Node 24) adds 12 kinds of strings (empty, an atom's, flat of 8 and 16 bits, lone surrogates, an object's key, 600 and 9,000 characters, ropes of 8 and 16 bits) in 13 forms (temp, local, argument, the local on either side, `+=` on a local, a property, an element, chains) and with 8 kinds of constant on either side, with non-string operands (objects with `valueOf`, `toString` or `Symbol.toPrimitive`, a String object, an array, numbers, `-0`, `NaN`, booleans, `null`, `undefined`, a BigInt, a function, a Symbol that throws), with the methods of `String.prototype` replaced to show none runs, in strict and sloppy code. `engine/test/regvm/js/r-stradd.js` checks the length limit in every form, that the local an add was to go into keeps its string after the error and its operands are unchanged, and has the throw injection hit each form (`inject-hit` lines). `test_string_add_kinds` in `engine/test/unit-white.c` checks that each form gives the same kind of string (rope or flat, 8 or 16 bits) and the same characters as `JS_ConcatString`. `test_string_add_oom` in `engine/test/unit-oom.c` runs the forms with each allocation failing in turn and checks the result or the exception, that an argument an add was to go into keeps its string or holds the whole new one after the error, that a string appended in place is not changed for its other holders, and that a string only its local holds is grown whole, in place or copied with room.

## A power of two prints its shortest digits

Release: v0.31.1.

`Number::toString` gives the fewest digits that read back as the number (the specification asks for the smallest k). QuickJS looked for them by rounding the number to 17 digits, then 16, and so on, and stopped at the first count whose rounding did not read back. Every float64 has its neighbours at the same distance on both sides, except a power of two: the float64 below it is twice as close as the one above. So for a power of two the digits rounded to nearest can lie below it and too far, while the digits just above it still read back, and QuickJS stopped one digit too early. It printed `2 ** -44` as `5.6843418860808015e-14`, 17 digits, where Node prints `5.684341886080802e-14`. 54 powers of two (and their negatives) were printed with one digit too many: 2^-1017, 2^-1007, 2^-957, 2^-921, 2^-808, 2^-791, 2^-788, 2^-778, 2^-705, 2^-695, 2^-662, 2^-652, 2^-645, 2^-569, 2^-549, 2^-509, 2^-499, 2^-496, 2^-489, 2^-383, 2^-366, 2^-296, 2^-140, 2^-97, 2^-77, 2^-44, 2^-24, 2^89, 2^122, 2^132, 2^149, 2^172, 2^182, 2^275, 2^305, 2^345, 2^378, 2^398, 2^405, 2^481, 2^534, 2^544, 2^554, 2^574, 2^594, 2^710, 2^740, 2^803, 2^863, 2^890, 2^896, 2^956, 2^966 and 2^976. Now, in radix 10, when the number is a power of two and its digits rounded to nearest do not read back, `js_dtoa` (`engine/dtoa.c`) tries the digits just above it, and goes on to fewer digits when those read back. These 108 numbers print as Node prints them. `toString` with another radix, `toFixed`, `toPrecision` and `toExponential` with digits are as they were.

Why it is safe: only a power of two can take the new step, and only when its rounded digits do not read back. The digits it then takes are the nearest ones above the number, and they are kept only when they read back as the number, which the loop checks as it checks every count. Every other number takes the same steps as before.

Tests: `engine/test/compare/number_to_string.js` prints what Node 24 prints for numbers converted every way a script converts them (`String`, a template, both sides of `+`, `toString`, `toString(10)`, `JSON.stringify`, a property key, `join`, `concat`), which must give one string that reads back as the number: fixed values (zeros, the infinities, NaN, the extremes, subnormals, values where the exponent form starts, hard cases), and a hash and samples of long lists: every power of two and the numbers next to it, the powers of ten and theirs, every exponent with ten significands, subnormals, 30,000 random bit patterns, 24,000 float32 values and 154,000 numbers with a few decimals. Before the change it differs from Node's output on the powers of two.

## Numbers that are not integers convert to text without big numbers

Release: v0.31.1.

`Number::toString` in radix 10 of a number that is not an integer of 53 bits or less (`String(x)`, a template, `'' + x`, `x + ''`, `toString()`, `JSON.stringify`, a property key, `join`) went through the loop of `js_dtoa` that looks for the shortest digits with big numbers: it rounds the number to 17 digits, then 16 and so on, with a multiplication by a power of ten and a conversion back for each count, then writes the digits out of a big number. That is about 5,000 instructions a number. A chart drawn by recharts and d3 writes its SVG paths with `d3-path`, which converts every coordinate, and spent about a fifth of a render there.

Now `js_dtoa` (`engine/dtoa.c`) finds those digits with Schubfach, the algorithm of Raffaello Giulietti ("The Schubfach way to render doubles", 2020), written here from the paper: integer arithmetic, three 128-bit products of the significand with a power of ten, and a few compares. The power of ten comes from a table of read-only data that all VMs share (`engine/dtoa-pow10.h`, written by `go run ./internal/dtoatable`): the 617 powers 10^-292 to 10^324, each scaled to 128 bits, 9,872 bytes. A table of 744 bytes that makes each power from one of 23 and a power of 5 costs 44 instructions more a number (callgrind), so the full table is kept. `dtoa_format10` then writes the digits and places the dot, the zeros and the exponent as the specification says, as the code after the loop did. `toFixed`, `toPrecision`, `toExponential` with digits, and `toString` with another radix keep the loop of big numbers. `toExponential()` with no digits takes the new path, since it asks for the same digits.

Why it is safe: Schubfach gives the shortest digits that read back as the number and, of those, the closest to it, and the even one on a tie, which is what the loop gives ([above](#a-power-of-two-prints-its-shortest-digits)) and what Node prints. The test of that is the comparison itself: `engine/test/dtoa-test.c` converts each number both ways and stops at the first string that differs. The loop is still in `js_dtoa`, behind the flag `JS_DTOA_BIGNUM`, for this test. The integer formulas of the code (the floor of `q*log10(2)`, of `log10(3/4*2^q)` and of `e*log2(10)`) and the table are checked by `internal/dtoatable` over every exponent they are used for, with exact rationals. The same bits come out on every target: the code uses no floating point, no fused multiply-add and no long double, and its 64 by 64 bit products are the `mul` of amd64 and the `mul` and `umulh` of arm64 (`check-symbols.sh` sees no call of a helper of the compiler). The new code has no loop that can run long (at most 17 turns), allocates nothing and throws nothing, so the stops, the memory limit and the exceptions are where they were.

What it gains, counted with callgrind: a render of the chart page converts 38,732 numbers, which cost 2,585 instructions each, 11.5% of the render, and now about 460. The chart runs 9.5% fewer instructions natively and 8.7% fewer in the Go engine with the profile trained again. No page of tifa runs more. It costs 9,872 bytes of read-only data, and 1.0% to 2.0% more instructions on `toFixed`, `toPrecision` and `toExponential` with digits, which keep the big numbers.


Tests: `engine/test/dtoa-test.c`, which `compare.sh` runs, compares both ways on 5,416,730 conversions: every exponent with 13 significands, the powers of two and the 64 numbers on each side of them, the powers of ten from 10^-330 to 10^310 and their neighbours, the subnormals up to 99,999, the hard cases of Paxson and of the papers of Ryu and Schubfach and their neighbours, 1,500,000 random bit patterns, 500,000 float32 values and numbers with a few decimals, on both signs, with the exponent form and with `-0`. With arguments it runs as many random patterns as asked, a range of float32 values, or a file of numbers. On a server it compared all 4,278,190,080 float32 values that are not infinite or NaN, 1,249,391,238 random 64-bit patterns (five seeds of 250,000,000, less infinities and NaN) and the 19,545 hard cases of the Schubfach test of OpenJDK with 16 numbers on each side (2,579,652 conversions), with no difference. `TestTableInTree` and `TestFloorLog` of `internal/dtoatable` check that the header is what the generator writes and that a formula one off at one exponent fails the check. `TestNumberToStringNode` runs `engine/test/compare/number_to_string.js` through the Go API against its Node output, and `TestNumberToStringShortest` compares 200,000 random bit patterns and the numbers next to every power of two with the shortest digits of Go's `strconv`.
