# Performance

liustack/beastjs is made for tifa, which renders React pages to HTML in the engine, so render speed is measured on the pages of tifa's example shop: one warm VM rendering the order list, an order and the stats of each of its two shops (`BenchmarkShop` in tifa's `test/ssr`). Every change for speed leaves the HTML the same byte for byte. The doc of each change in [changes](changes/README.md) has its full measurement, and tifa's [docs/performance.md](https://github.com/liustack/tifa/blob/main/docs/performance.md) has what the numbers mean for an app. How the engine compares with the other pure Go engines, on tifa's pages and on general workloads, is in [benchmarks.md](../use/benchmarks.md).

The engine changes up to v0.26.15 alone made renders 1.63 to 1.66 times as fast as on the engine liustack/beastjs started from (modernc.org/quickjs v0.25.0 with libquickjs v0.13.1), and 2.07 times as fast with the rewrites of tifa's Vite plugin and PGO (measured on 2026-10-20).

## How the numbers were measured

Unless a row says otherwise:

- Machine: a Google Cloud VM with 8 vCPUs of an AMD EPYC 7B13 (Zen 3), Linux, one core pinned with its hyperthread sibling idle. Some rows are on an Apple M4 (darwin/arm64), which is noisier.
- tifa is built without PGO (profile-guided optimization). It stopped using it with the C engine, where the profile made no difference.

## Measuring in tifa

Judge every timing by the protocol of [measuring.md](measuring.md). This section is how to build and run tifa against a checkout.

To measure a branch of liustack/beastjs before it is released, point tifa at the checkout with a `replace`, build the example app, and run the benchmarks of tifa's [docs/testing.md](https://github.com/liustack/tifa/blob/main/docs/testing.md#performance-comparisons):

```sh
# in tifa
go mod edit -replace github.com/liustack/beastjs=../beastjs
(cd examples/shop && pnpm install --frozen-lockfile && go tool tifa build)
TIFA_SSR_SHOP=1 go test -run '^$' -bench 'Shop/^render' -benchtime 2000x ./test/ssr
TIFA_SSR_SHOP=1 go test -run ShopVMMemory -v ./test/ssr
TIFA_SSR_SHOP=1 go test -run '^$' -bench ShopParallel -benchtime 15s ./test/ssr
```

- Build the test binary once for the old engine and once for the new one (`go test -c -o old.test`, `-o new.test`), and run them in turn on the same pinned core, round after round. Read the ratio of the sums of the six P50 within each round.
- `go test` builds unless given `-pgo=<file>`, and tifa builds too, so these compare the engines as tifa runs them.
- Compare the HTML of every page between the two builds. The router writes the time of the render into each match (`u:` followed by 13 digits), so mask that first.
- A benchmark with one VM cannot see contention between VMs. For a change near memory allocation, also run `BenchmarkShopParallel` and read its `speedup` and `lock-wait-%`.
- Note the load of the machine during each round, and run again when other work used more than about 10% of the CPU.
- Remove the `replace` before committing in tifa.

After a release, upgrade tifa (see [releasing.md](releasing.md#after-the-release)).

### The pages of tifa 63a2099e

From 2026-11-16, `engine/pgo/pages` holds the pages of tifa 63a2099e (v0.0.10) in place of those of tifa 07b6ce0f: the same 23 pages, with the shop on react-i18next 18, whose `useTranslation` no longer copies the i18n object on each call, and the bundles of tifa's newer plugin. They do less work, so a count or a time on the old pages does not compare with one on these. The base for the next comparison is v0.31.2 (main at 8aa30db0) on these pages. Instructions a render, summed over the pages of each kind, counted by `scripts/count-pages.sh` on linux/amd64 (AMD EPYC 7B13), the same binary on both sets:

| kind | pages | old pages | these pages | change |
| --- | ---: | ---: | ---: | ---: |
| wb | 6 | 480,754,335 | 460,449,911 | -4.22% |
| store, en-US | 7 | 1,061,261,019 | 942,359,579 | -11.20% |
| store, zh-CN | 7 | 1,023,379,913 | 906,201,218 | -11.45% |
| mui | 3 | 365,197,275 | 356,965,078 | -2.25% |

On the store, the own keys of objects take 12.7 million fewer instructions a kind, and the register loop 45 to 47 million fewer. The Proxy of react-i18next is made and freed once a render (about 26,000 instructions a page) and its traps do not run. The profile of v0.31.2 was trained on the old pages, which never wrote the modes of the start tag (`js_emit_mode_attrs` had no count). Trained again on these pages, the engine runs -0.01% to +0.12% instructions on each kind.

### Code positions

Where the interpreter's code lands in the binary changes its speed by 5% to 14% on its own, so one build against one build can show a change that is only a move. Measure each side at several positions (layouts), by the protocol of [measuring.md](measuring.md): it says which layouts (the `front` and `shift` of a position are defined there), in what order, how to read the result and what it can and cannot see.

Until that protocol, `shift` padded the first function of `cutils_amd64.s`, which is never called, so the linker dropped it with its NOPs: in the C engine of v0.29.8 a shift of 32 or 1664 bytes left every function at the same address and moved only some read-only data. The results below that name "the whole-program move" measured that.

Build every position with the same flags (`-pgo=off` or the same profile), and put a measurement of the same engine at all positions next to the one of the change.

Making the positions:

- The tool in [testing.md](testing.md#time-one-build-against-another) makes the positions of the C engine, runs the builds in turn and judges the result (`bench build`, `bench run`, `bench judge`), and counts instructions (`bench cg`). By hand: C engine (`internal/cengine`): copy the generated `*_amd64.s` files, run `go run ./internal/goasm/cmd/xform DIR shift:1664:dbuf_init2 front:JS_RegvmRun:16` on the copy (use `shift:0` and `front:...:0` for no move, and the name of the first engine function of your binary, which `go tool nm -n` shows), and build with the copy. The bytes of `shift` sit after a `RET` and never run. The bytes of `front` sit after the `PCALIGN` at the start of the interpreter body and run once per call.

A `front` that is not a multiple of 16 (8, 24, 40, 56) moves the body and the constant pool it keeps after its code together, so the pool leaves its 16 bytes. On amd64 the register loop `JS_RegvmRun` reads a 16-byte mask from its pool with `xorpd` (to flip the sign of a double), and the memory operand of `xorpd` must sit on 16 bytes. In the shipped layout the pool is on 16 bytes. At a front that is not a multiple of 16 it is not. Such a layout faults the first time a script negates a double, so the fronts are only 0, 16, 32 and 48: xform and `ParsePosition` of `bench build` refuse the others. Make the places in between with the generator instead: `-align64 JS_RegvmRun:8` puts the body at 8 with its pool on 16 bytes.

## What was tried and not done

Each item says what it would give and why it was dropped. Check here before trying one of them again. The numbers come from tifa's [docs/performance.md](https://github.com/liustack/tifa/blob/main/docs/performance.md#what-was-tried-and-not-done) and [docs/studies/engine-hotspots.md](https://github.com/liustack/tifa/blob/main/docs/studies/engine-hotspots.md), and from the docs of the changes.

- **Dispatching opcodes through closures or a table of functions**, as some Go interpreters do: a rewrite of the interpreter, against the rule of liustack/beastjs to make only mechanical changes. Not tried.
- **A check in JavaScript in front of one spread for the props of `createElement` and `cloneElement`**, measured on v0.29.1 before `RegisterCopyProps`: the plugin tested the config (the prototype, the symbols, `__proto__`, `__self` and `__source`, a getter behind `key`) and then copied it with the rest of a destructuring. The test took 310 to 380 ns a call, more than the loop takes for a config of none, one or two keys, so `createElement` took 1.57 times as long for no keys, 1.07 for one key and 1.13 to 1.40 for a `key` and one or two more. The shop took 0.99 of the time (1.6% to 2.5% fewer instructions) and no page passed the rule. It also could not rule out a proxy, a getter that deletes a later key and a setter added to `Object.prototype` after React loaded. The same checks in C cost less than the empty loop, and the function gives 2.1% to 4.1% fewer instructions.
- **A fast path for object spread** (`JS_CopyDataProperties`): one spread took 240 ns rather than 415 in a micro benchmark on the Apple M4, but the shop did not change (0.997 to 1.005). It is done since together with the listing of keys, which it shares with `for in` and `Object.keys` (see [Own keys listed from the shape](changes/objects-and-shapes.md#own-keys-listed-from-the-shape)).
- **Testing the uncatchable flag before calling `_js_uncatchable_pending`** at the entry of `JS_CallInternal`: the helper is too large to inline into the interpreter, so every JavaScript call pays a real call to it. Testing the runtime's flag inline first skips that call on the normal path, and keeps the full check, which is still needed because the flag stays set after the exception is taken. 0.06% fewer instructions on V8, 0.09% on the shop and 0.41% on MUI. Over six rounds on three code layouts, V8 took 0.9988 of the base score (0.9883 to 1.0254), the shop 0.9927 of the time (0.9859 to 1.0014) and MUI 0.9850 (0.9763 to 1.0265). The sign follows the layout: MUI took 1.027 and 1.012 of the time in the two rounds of one layout, and 0.976 to 0.988 in the four rounds of the other two. The gain cannot be told from layout noise.
- **Reading the count of locals once, alone**: at the start of a call the interpreter read `b->var_count` again after each local it set. Reading it once gave React 1.0% fewer instructions but a loop of arithmetic 3.9% more, from a register spilled in one handler, and the time did not change. It is done since together with setting four locals a turn and freeing two values a turn (see [Calls, for in and hasOwnProperty.call](changes/objects-and-shapes.md#a-for-in-loop-holds-the-shape-of-its-object)).
- **Spreading a dense array without its iterator**: `[...a]` of three elements took 165 ns rather than 615, and a call with spread arguments 394 ns rather than 869, on v0.26.17 in a micro benchmark on linux/amd64. The shop's six pages (0.997) and three MUI pages (1.007) did not change beyond the spread that the layout of the code gives, since pages rarely spread arrays. It would have added about 870 lines of fixlib rules. Corrected on 2026-11-14: that no longer holds for today's pages. wb studio spreads arrays 2,432 times a render at about 1,450 instructions each, the storefront 968 to 1,415 times, and the spread with no iterator is done since, in the C engine (see [The spread of a plain array with no iterator](changes/c-engine.md#the-spread-of-a-plain-array-with-no-iterator)).
- **A rest parameter or an array spread into a call, in the register loop** (`f(...rest)`, `f(...args)`), counted on 2026-11-15 next to [passing arguments on with apply](changes/c-engine.md#passing-arguments-on-with-apply-makes-no-arguments-object): on an Apple M4 a rest parameter spread into a call costs about 1,900 instructions more than a direct call and a spread of an array about 1,800, but the 12 React pages on widely used libraries make at most about 7,200 of each a render, so taking all of that cost away would give at most 2.3% of a render on i18n, 1.4% on table, 1.3% on radix and under 1% on the others, and a rest parameter still needs its array. Not built. `Reflect.apply(f, x, arguments)`, a spread of `arguments` and `new` or `super` with one were not built either: neither these pages nor V8's suite runs them.
- **Keeping the in-between shapes of every object literal**, before v0.26.16: about 2% more on top of the new property fast path, but the two list pages ran out of VM memory, because the kept shapes held their prototypes and everything those reach. v0.26.16 keeps only shapes whose prototype is `Object.prototype`, at most 32 keys and no unregistered symbol key, in a ring of 2048 (see [Kept shapes](changes/objects-and-shapes.md#kept-shapes)).
- **Building a shape in place when no other object has its keys**: in the first form of the shape cache, copying every shape made objects of keys no other object has 22% slower to build. v0.26.16 earns one copy for each shape found, up to 64, which leaves those objects about 6% slower.
- **Filling the fullest arena of a class first**, so that sparse arenas drain and go back whole: after each collection the arenas with a free slot were put in order, fullest first. On the store pages with new prices at each render (7,000 renders, a full collection every 250) the size after a collection stayed at 25.6 to 26.4 MB against 25.7 to 26.8, and the free slots at 8.3 to 8.9 MB against 8.4 to 9.3: each render fills every arena again before it makes a new one, so the order does not choose where the objects kept land. Dropped before counting its cost.
- **Literal templates in the bytecode**, as V8 copies a prebuilt object: needs compiler and bytecode format changes, and quickjs-ng saw no clear difference when it tried. It is done since, as one opcode for each run of plain keys whose final shape the function keeps (see [Object literals made at their final shape](changes/objects-and-shapes.md#object-literals-made-at-their-final-shape)).
- **Allocating the property array of a literal at its final size**: the opcode that makes the object does not know the count, and growing arrays differently costs memory for every small object. It pays only together with kept shapes. Done since with that opcode, which knows the count of its keys.
- **Inline caches for property reads**: quickjs-ng added and then removed them. Across 17 real tools they ranged from 11% slower to 54% faster, 4% faster on average, and used more memory. Tried after v0.27.0 as a table of 4096 entries keyed by the bytecode position, each holding a shape and the index of an own data property, checked against the shape itself (the index under its count, the same key, plain flags), so it needs no invalidation. Most reads on tifa's pages are own properties of the object, which `find_own_property` already finds in one hash step, and a hit on a prototype cannot skip the check of the shapes on the way. 0.3% fewer instructions, but the shop took 1.006 of the time and the MUI pages 1.007 (6 rounds, 3 layouts), for 96 KiB more per VM. Tried again on 2026-10-30 on the C engine as a table per function, one entry of 16 bytes for each byte of its bytecode, holding a reference to the shape: 71% to 98% of the places that read a property by name see one shape only, but a hit costs about as many instructions as the hash lookup it skips. Against the engine of v0.29.4, callgrind gave -0.29% to +0.93% of the instructions and, with the cache misses weighed in, 1.2% to 2.7% more cycles: the misses of the three reads it serves fell by 70% to 90%, but they were only 0.52% to 0.64% of the cycles, and the reads of the table missed more. A compact table, one entry for each place that reads, could win back at most about 0.4% less its own misses, for a new bytecode format and a shape held by the cache that its only object could no longer change in place. Not done. Tried a third time on 2026-11-12 on the register loop, with no table and no held shape: every shape got a 64-bit stamp, renewed at each change in place, and each GETF kept the stamp and the slot of the own property it last found, in an entry of 16 bytes next to the register code of its function, so a hit compared one number. Under a check build every hit agreed with the lookup over test262, the corpus, the units and the 23 pages. Callgrind gave 0.06% to 0.99% fewer instructions per render (MUI orders, wb-studio, the store post page), but on the Apple M4 (12 alternating rounds, the mean of each page) the workbench took 0.988 of the time, the store 0.999 and MUI 1.001, with 0.2% fewer to 0.3% more instructions. Own properties are about 80% of the reads, so this first stage had to show most of the 1.5% to 2.2% estimated for the whole cache (prototypes, missing keys, strings and writes too). It did not, and the rest was not built. Done after v0.31.1 in a fourth form: no stamp, no table and no shape held, each read keeps in its own instruction the slot it last found, and for a key of the prototype the id of the object's shape ([changes](changes/README.md#the-c-engine)). That form wins by time on the EPYC: the dependent loads of a hit go through the object and the slot only.
- **A table of shape steps for new keys**: `add_property` looks for the shape an object goes to in the shape hash table, and that lookup misses the cache often (2.4% of the instructions of a render of the shop, 7.7% of its cache misses). A table of 1024 steps per runtime, from a shape and a key to the next shape, holding both, cut 0.8% of the instructions on the shop and the MUI pages, but the shop took 1.008 of the time and the MUI pages 1.019 (6 rounds, 3 layouts): the shapes it holds alive (2718 to 3504 on an MUI page) add 28 KB to 142 KB per VM and change when the cycle collector runs.
- **Fast arrays in `every`, `some`, `forEach`, `map` and `filter`**, without asking `JS_TryGetPropertyInt64` for each element: `js_array_every`, which runs all five, spends 0.67 s of its own outside the callbacks in a profile of 85.6 s of the ten store pages of tifa's example shop, `JS_TryGetPropertyInt64` 0.19 s of it. A fast path would save at most about 0.5% of a store render, which the layout of the code hides. `find`, `findIndex` and `includes` already read fast arrays directly.
- **`+slow-unaligned-mem-16` on every file, or with the SLP vectorizer on** (C engine): the libc gets 8-byte moves in its `memcpy`, and with the vectorizer on `r_shiki_regexp` took 1.028 to 1.033 of the time and 29 SSE moves stayed in `JS_CallInternal`. Only `quickjs.c` gets it, with the vectorizer off ([numbers](changes/c-engine.md#how-a-jsvalue-is-copied)).
- **Waiting for Go 1.28**: a development build made the unchanged engine 5% faster on amd64 and 2% on arm64, but the rewritten engine 5% to 6.5% slower on amd64, for a reason not found. The rewrites still win there by 4.2% on amd64 and 15.5% on arm64.
- **Dropping function source from the bytecode** (`JS_SetStripInfo`) to save VM memory: seroval, which tifa's pages use, reads the source of its own helpers with `toString` and writes it into pages, so the browser would break.
- **Removing the store of the bytecode position on arm64**: the up to 11.6% of the interpreter's own time it seemed to take is where the sampler puts the wait for the next opcode. The store is Go saving the local `pc` for the calls that read it back, on the path every opcode takes. Only moving the instructions put the samples on the opcode load instead (8.8% down to 0.4%), with the same instruction count, cycles and render time.
- **Ropes sooner in the C engine**, for React's page string: making a rope of any result over 512 characters (`JS_STRING_ROPE_SHORT2_LEN` of 512 instead of 8192) took `q_string_build1` from 0.18 s to 0.32 s natively, since `+=` on a local then leaves its in-place append for ropes, and gained React no more than copying with room (see [Strings built by appending](changes/c-engine.md#strings-built-by-appending)).
- **Skipping leaf objects in the cycle collector**, as CPython skips tuples that hold only atoms: a plain object, array or closure variable that holds no GC value (only numbers, strings, booleans and the like) moves to a list the collector never walks, and back when a GC value is stored into it. On a render of a 400 KB Markdown page only 7.6% of what the collector visits is such an object that lives on (304k of 4.0M visits), since 61% of what it visits is garbage made since the last collection. The prototype cut the collector's work by 6.6% of its instructions and took that render to 0.978 of the time (0.964 to 0.991 over 8 positions, 5 rounds, the base's own range 2.9%), but the checks on stores and the frees it defers cost as many instructions as the collector saved (-0.00% a render), and `r_react_ssr` paid 0.11% more. tifa's pages, which rarely collect during a render, did not change (shop 1.004, MUI 0.999, bench 1.002). Every store of a GC value into an object, an array or a closure variable needs the check, about 150 places in the C, and a missed one keeps garbage until the runtime is freed, which the block count of `JS_FreeRuntime` cannot see. A build that checks the list at every collection found a missed store in the first scripts of `compare.sh` that it ran (a global variable defined after a function used it). A leaf also hides its edge to its prototype, so a context freed while its runtime lives would stay until the runtime is freed. CPython dropped the same scheme for dicts in 3.14 ([gh-127010](https://github.com/python/cpython/issues/127010)): the check on every store cost more than the collector saved. quickjs-ng has nothing like it.
- **Passing arguments and results in registers to the functions without a stack check** (the NOSPLIT ones, since Go's morestack loses registers), measured with callgrind on the C engine, not built. One call between generated functions comes every 171 to 283 instructions, and 23% to 27% of them go to a NOSPLIT callee. The stores and loads that move their arguments and results through the Go stack are 0.72% of the instructions of `r_react_ssr` and 1.25% to 1.38% of tifa's pages (arm64, from the same call counts: 0.75% to 1.49%). That is about 0.3% to 0.9% of the time, by 0.65 of the instructions or by the per-call saving of the phase 0 micro benchmark, under the 2% to 3% that the code position moves a render. The moves of all calls are 5.6% to 8.3%, but the rest goes to functions with a stack check (the argument block of `JS_CallInternal` 1.2% to 2.4%, functions on a cycle of calls 1.3% to 2.3%, calls through a pointer 0.5% to 1.0%). The 792 bytes the linker gives a chain of NOSPLIT calls are used (the tallest chain takes 752): frames smaller by 7.6 KB in all add no NOSPLIT function, and breaking each cycle of calls at one function adds 41 of them (the linker accepts it) but moves the share of moves to NOSPLIT callees by +0.2% to +0.3% on the shop and MUI pages and -0.14% on the bench pages. It would take a new kind of entry in the generator and in both post-link checks for 4 to 6 days, for a gain under the noise of the code position.
- **An absolute dispatch table** (C engine), filled once per VM with the addresses of the opcode handlers, so that a dispatch is one indirect jump instead of the 3 more instructions of the relative table llc emits for position-independent code: prototyped on 2026-10-27. The time did not change, `r_bench_table` got slower, and the table sat in writable memory, where a stray write could change where the interpreter jumps.
- **Dropping the no-ops after the prologue and the jump to the shared `RET`** (C engine): 1.6% to 2.6% of the instructions but under 1% of the time by estimate, since the no-ops are cheap. The no-ops are the `PCALIGN` that puts each body on 16 bytes, which keeps the alignment of its constant pools (`FuncPlace`) and its place for the code position measurements, and a Go epilogue at every return makes the code bigger.
- **Fewer arguments for `JS_CallInternal`** (C engine), prototyped on 2026-10-30. Its seven arguments (the context, the function, `this` and `new.target` as values, the count, the array of arguments and the flags) take 10 words, 11 with the shadow pointer, one more than the registers of an entry on amd64, so every call writes them into a block and passes its address. The prototype passed the address of the function in the caller's stack, where the interpreter keeps it under the arguments and above `this` of a method call, and read `this` and `new.target` below it when a flag said so: 6 words and no block, 10 to 14 fewer instructions a call. The engine then ran 0.77% fewer instructions a render of tifa's shop, 0.71% of its MUI pages, 0.93% of its bench pages and 0.85% of `r_react_ssr` (callgrind), under the 1% that would be worth timing at the code positions. The 6 words and the result still go through the Go stack, since the interpreter keeps its stack check, so packing the count and the flags into one word would save only about 2 more instructions a call. The prototype also made the shadow frame of the interpreter 96 bytes larger on amd64: the calls that LLVM inlines into it (`js_call`, `JS_CallFree`) each kept their own pair of the function and `this`, where they had all shared one block, and a recursion with 250 locals ended at 5978 levels instead of 6082 at the depth limit of 10000. The arguments of `js_call_c_function` (9 words, called through a pointer) were not tried: if none of them were moved at all, a render would run 0.27% (MUI) to 0.79% (bench) fewer instructions, 0.40% for `r_react_ssr`.
- **Making a call level take less Go stack**, researched on 2026-10-27. The design bound is 5,600 bytes for a call level (the longest chain of frames between two counts of the depth is 38), but real recursions use 416 to 2,224 bytes a level (a plain recursion 480). In `body` mode 71% of the bound is the same in every frame (the return address and frame pointer 608, the area for outgoing arguments 1,896, the area where registers are saved 1,480) and 29% is the locals LLVM keeps (1,616), and `preserve_none` moves the saves into the locals without making the total smaller. LLVM at `-O2` already reuses stack slots, and shrink-wrapping changes when a frame is built, not its size. Not done: passing the arguments of a call in the shadow frame with the shadow pointer in the closure register (the bound falls to 2,184, but it relies on how Go uses that register, which is no mechanism to depend on), packing the arguments of more than two words into a block (17% less, 2.5% to 2.9% slower), and counting the worst bytes of each stretch instead of 1 (it saves only memory and adds counts). Running the engine on a stack of its own, as cgo, wazero and purego do, would bring the Go stack a level takes to 0, but a fault in the C could then no longer be turned into a panic that ends only the VM, and it ends the process. That is not acceptable for a server, and the engine keeps its frames on the goroutine stack.
- **Clang PGO for the C engine**, measured on 2026-10-29. Instrumented builds trained on `r_react_ssr`, the 400 KB Markdown, 18 shop pages, 3 MUI pages and 2 bench pages. On the native C tree, 8 positions, 3 rounds: `r_react_ssr` took 1.096 of the time and the bench pages 1.083 (8 of 8 positions), the Markdown 0.962, the shop pages 0.987 and MUI 1.017 (both under the 2% the rule counts). A profile of only 4 shop pages did not make those 4 faster (1.000). On the generated engine (tifa's pages, 4 positions, 6 rounds) every page group was slower, the shop 1.058, the store 1.051, MUI 1.064 and the bench pages 1.150, the same sign at all 4 positions. The bench table page ran 32.5% more instructions: `JS_FreeValue` was no longer inlined (19.7% of its instructions as a call) and `JS_CallInternal` ran 22% to 23% more instructions with a frame of 640 bytes in place of 496. With the four inline thresholds put back to 400 it was still 29.4% more, so the thresholds are not all of the cause, and the rest was not found. The generator takes a profile without changes (a wrapped clang that adds `-fprofile-instr-use` when it makes the IR), and it makes the `.s` 22% larger (8.0 MB to 9.77 MB). It also found that the constant pools of the generated code are aligned within the function, not at their absolute address, so an aligned SSE read from a pool faults when the body of `JS_CallInternal` sits at 40 bytes of its line (the PGO build had 19 such reads). `JS_CallInternal` of main has none. Done since in another form, with the inlining held to what the build without a profile makes: see [A profile of tifa's pages](changes/generator.md#a-profile-of-tifas-pages).
- **Values of 8 bytes** (NaN boxing, `CONFIG_NAN_BOXING64`), measured on 2026-10-30 on the native C tree built with the options of the generator, the same commit with and without the flag. Reads fell by 8% to 11%, writes by 12% to 17% and misses of the data cache by 13% to 20%, but the instructions rose on every load: the shop's workbench 2.6%, the store 2.8%, MUI 4.8% and `r_react_ssr` 6.9%. The tags, the pointer mask and constants such as `undefined` are 64-bit numbers that x86-64 compares and masks only from a register, so `movabs` went from 580 to 9,310 in `quickjs.o`, `JS_CallInternal` grew by 16%, and the instruction cache missed 8% to 12% more. `JS_FreeValue` was no longer inlined, which is 70% of what `r_react_ssr` added, and forcing it inline made the four loads 2% to 11% slower. The time did not change (median of 8 positions 0.983 to 1.008), under the 3% at every position that the second step, a property of 8 bytes, needed to go on. Worth looking at again only if the memory of the VMs, not the time of a render, becomes the limit.
- **Cheaper polls**, after the cost was measured (see What the generated code costs against native C). The call of `host_poll` is not the cost: with the interval at 1,000, 10,000 and 100,000 polls a script took the same time, and `host_poll` and the Go runtime are 0.2% to 1.1% of the added instructions (0.06% to 0.16% of a tifa render). The cost is in the counting: the registers it holds, the count that is written back before and read after each call, and bigger code. Taking the counts out of the dispatch saved only 6% of the instructions, and taking away as well the register the function held for the count and the sync around its calls still left a `jsloop` at 1.41 times the instructions of an engine without polls. What was done is in [Polls and interrupts](changes/c-engine.md#polls-and-interrupts): counts only at jumps back and at the entry of a function, loops that run in chunks and count once a chunk, a count in a register or in memory for each loop, and no more `llc` options for tail duplication. What was not done:
  - **A fixed register for the count in all the code (H2).** It can be made correct under Go, but x86 would need LLVM 23, and OCaml found the count in a virtual register mostly spilled and slower, and DTVM went back to ordinary registers in its optimizing mode.
  - **Cutting the limit of a loop into chunks as HotSpot does (M1).** It works only for loops whose trip count the compiler can work out. Of the scripts it would speed up, `strsearch` 5% to 10% and React about 0, and a mistake in the arithmetic of the limit is an out of range access.
  - **Giving the small functions whose only call is `host_poll` their `NOSPLIT` back (L3).** With the counts of all the C functions taken out the ceiling is `json` 15%, `strsearch` 11%, React 4% and `r_react_ssr` 0%, so under 0.5% on a page.
  - **The `llc` options for tail duplication for the interpreter alone (M2).** Without them only `JS_CallInternal` changes in the whole engine, so giving them to it alone gives the same bytes. They are taken out since, which cost `jsloop` 20% before the counts moved to the jumps back and made it faster after.
  - **Counting nothing in short loops of the C (the shape hash chains, `lre_find`, the property loop of `free_object`).** It needs the C to promise the bound, which the generator cannot check, the same weak spot that put an earlier idea out.
  - **Skipping the targets that cannot poll in a call through a pointer (L4)**, from the type of the pointer: types only tell the number and kind of the arguments, so a comparison function that may call JavaScript shares its type with the ones that cannot.
  - `taindexof` 25% slower with polls turned out to be where the code landed: its inner loop of 7 instructions across a line of 64 bytes took 22% to 25% longer, with and without polls.

Taking one block away from the 133K direct calls of C functions a store render makes measured about 2.5 cycles a call on the M4 (noisy), so all blocks would give at most about 1.4% of a store render and 0 on amd64. It needs a register list past the 6 the pass passes now (three dummy parameters, then X0 to X7, X10, X11, ...), a new adapter between Go's argument area and those registers, a check that no argument reads X26 to X28, and bigger Go frames of the callers, which risks the depth floors unless it stays off the chains of recursion, where most of the gain is. About 4 to 6 days for at most 1.4%. A hot callee whose block is on its critical path is cut more cheaply by giving it fewer words in C, as [Fewer argument words into hot calls](changes/c-engine.md#fewer-argument-words-into-hot-calls) does.
- **Fewer words for the other hot callees** (amd64 callgrind, the share of a store render each could save at most): `JS_DefinePropertyValue` and `JS_CreateProperty` about 0.07% (every word is used), `JS_CallInternal` about 0.05% (flags and `new_target` on the plain call path, still 10 words and a block on amd64), `JS_SetPropertyInternal` about 0.01%, `js_closure` about 0.005%. The C functions with a magic number (`js_map_has`, `js_array_push`, ...) take 7 words fixed by the table of C functions and its indirect call. Below what a timing can show.
- **The engine's functions in order of heat, the hottest first** (2026-11-13 and 2026-11-14, amd64, counted and timed, callgrind's cache model with an I1 of 32 KiB and 8 ways, time over the 16 layouts of [measuring.md](measuring.md) on an AMD EPYC 7B13). The generator wrote the functions a table names first, in its order, into files whose names sort before the others, and Go's linker keeps that order (the `.s` files of a package by name, then their `TEXT` in order, on every Go version and target the module builds for). Only the place of whole functions changes: every function has the same text, frame and constant pools, and every page gives the same HTML. The table came from callgrind runs of tifa's pages, by the instructions each function runs in a render. On v0.30.3, without the profile, it took the instruction cache misses of a render down 7.4% on the workbench, 8.3% on the store and 5.5% on MUI, and the time of the mean of the layouts down 0.29% (workbench, [-0.92%, +0.34%]), 0.53% (store, [-1.12%, +0.07%]) and 0.09% (MUI), none of it faster by the rule. Tables that differed only in their tail gave from 3.6% to 5.0% fewer misses on the workbench and from 1.5% to 4.9% on MUI, a spread as wide as the gain. A table made from the profile's counters, not from callgrind, gained less or lost. On v0.30.6, with its profile, a table made again from that engine (354 functions, the same 14 pages) gives more misses on three of the five kinds the release is timed on, per render with the same instructions (within 0.03%): the store +4.29%, the workbench +3.94%, React's page +4.71%, MUI -0.42% and the long Markdown page -0.75%. So the misses follow where each function lands, not the order: the 32 KiB cache repeats every 4 KiB, the code a render runs is about 1.5 MB, and every set of the cache holds far more hot code than it can whatever the order. An order surely puts the hot code on fewer pages (on v0.30.3 the 200 hottest functions on 140 pages of 4 KiB rather than 235), which is the TLB, and callgrind does not count it. Timed on v0.30.6 all the same, against the release (the 14-page table, the five kinds, 2 rounds, delta 1%), the mean of the layouts was +0.21% on the workbench ([-0.19%, +0.61%]), +0.11% on the store ([-0.32%, +0.54%]), +0.19% on MUI ([-0.35%, +0.73%]), +0.84% on React's page ([-0.27%, +1.97%], with a layout SD of 1.75%) and +0.18% on the long Markdown page ([-0.20%, +0.56%]): none of them faster. The formal layout was 0.7% to 1.3% faster on every kind but the Markdown page (past zero on the store, -0.80%, and on MUI, -1.27%), but the layouts keep the order within each section and that gain is gone from their mean, so it came from where this one build put the code, not from the order. If it is tried again: the table has to come from the build it orders, the counts move by about 4% with the table alone, and only a timing over the layouts can tell a gain of the pages from the place of the code.

- **A frozen bit on the shape**, as Hermes marks a hidden class sealed or frozen, so that `Object.isFrozen` of a frozen object answers without going over its properties. - **Less work between two renders, for more renders per core per second**, counted on 2026-11-16 on a copy of tifa's pool (callgrind on linux/amd64, one core, tifa's seven judged pages, React's page and a long Markdown page). All the work between two renders (the young collection, the release, the goroutine that puts the VM back) is 0.3% to 2.7% of a render's instructions. A warm snapshot copied back after each render would copy 900 to 1,500 changed pages of a store render, 2 to 4.5 ms against about 0.5 ms for the young collection, and needs the kernel to find them. Sharing what the VMs of a pool have in common saves no instructions: about 1 MB is read only today, and two VMs on two cores already give 2.00 times one. None was built. The one cost found is on a page whose render passes the GC threshold, such as the Markdown page: `ReleaseMemory(0)` after the full collection between renders gives back about 50 MB that the next render faults in again (23,577 page faults a render), and keeping the room up to the threshold cut the faults by 59%, an estimated 0.6% to 1.2% of such a render. That is a change to tifa's pool, not to the engine.

## Where to continue

What is left for the C engine, none of it large. A change under about 3% needs the positions of [Code positions](#code-positions), and callgrind below that.

- **llc's ext-TSP block placement, first without a profile, then with the counts of a profile** (2026-11-13 and 2026-11-14, amd64 product, callgrind on tifa's pages, time over the 16 layouts of [measuring.md](measuring.md) on an AMD EPYC 7B13). `-enable-ext-tsp-block-placement` at llc orders the blocks of each function so that the paths that run together sit together. It changes no frame, no shadow frame and no HTML, and runs 0.07% to 0.22% fewer instructions. Without a profile (`-ext-tsp-apply-without-profile`, so llc guesses which way each branch goes) it took the instruction cache misses of a render down 15.0% on the store's home page, 8.7% on the workbench, 3.8% on MUI's orders and 2.1% on the React page. The time did not move: store -0.01% [-0.54%, +0.53%], workbench -0.20% [-1.08%, +0.68%]. On top of the PGO build that keeps the inlining of the build without a profile, llc has the real count of each branch. There it took a further 5.5% (workbench), 7.4% (MUI orders) and 10.7% (React) of the misses that build leaves. Against that build, over the layouts and 8 rounds: workbench +0.58% [+0.08%, +1.07%] slower, store -0.05% [-0.34%, +0.24%], MUI +0.44% [+0.03%, +0.85%] slower, React -1.01% [-1.57%, -0.45%] faster. It is slower on every workbench page (+0.46% to +0.70%) and every MUI page (+0.17% to +0.52%). Fewer instruction cache misses did not buy time here: on this CPU a miss that hits L2 costs little, and the new block order cost more than that on two of the four groups.
- **The place of the register loop** `JS_RegvmRun` in its line of 64 bytes: its body sits after a `PCALIGN $16` like any other function and moves with the code linked before it. In the build measured on 2026-11-13 it started on a boundary of 32 bytes, not 64. Fixing its place does not pay. On 2026-11-13 (batch 2's engine, amd64, an AMD EPYC 7B13, 16 layouts of [measuring.md](measuring.md), 4 rounds per group) the generator's `-align64` put the body at byte 0 or byte 8 of its line, against the base, whose body the layouts put at 0, 16, 32 and 48. Mean of the layouts, byte 0 then byte 8: workbench -0.22% [-0.64%, +0.20%] and -0.17% [-0.57%, +0.24%], store -0.20% [-0.55%, +0.14%] and -0.44% [-0.89%, +0.01%], MUI +0.28% [-0.22%, +0.78%] and -0.19% [-0.67%, +0.30%]. Fitted over every side and layout, each of the 8 places of the body takes 0.992 to 1.008 of the mean time, and the best place differs by group (workbench 40 or 48, store 24 or 40, MUI 56 or 0).
- **Memory** per VM: the free pages of the render's temporary space, the pages the shadow stack touched and the holes between free blocks make up the gap between a VM's resident memory and the engine's count of its blocks (4.2 MiB on the shop and 2.9 on MUI per VM, from 8 VMs against 1 after the renders). `ReleaseMemory` gives back the free pages when the pool lets a VM wait.
- **Results of the functions Go code calls**: the 91 functions Go code calls still store their result, because Go reads the result of an assembly function from memory. A generated Go entry for each hot one, which calls a body that stores nothing, would remove the stores of those bodies when generated code calls them: at most 0.24% of the instructions on the store pages, 0.21% on the workbench, 0.11% on MUI and 0.14% on React (arm64, writing each such store twice), less one extra call for each call from Go. It needs a new kind of function in both post-link checks.
- **Arrays that keep their elements in one block with holes**: an Array written past its end, or with an element deleted, becomes an array of properties and never becomes a fast array again ([An index of an Array that is not a fast array is read and written by its atom](changes/c-engine.md#an-index-of-an-array-that-is-not-a-fast-array-is-read-and-written-by-its-atom)). V8 keeps such an array in its block, with a mark for each missing element. Upstream QuickJS and quickjs-ng turn it into properties, as this engine does. Keeping the block would need the mark checked wherever the engine reads the block of a fast array: about 60 functions of `quickjs.c` (`js_get_fast_array` and its callers, the fast paths of `push`, `pop`, `includes`, `indexOf`, `slice`, `splice`, `with` and `toSpliced`, JSON, `for in`, `for of`, `delete`, `set_array_length`, `JS_GetOwnPropertyNames`, the collector and the free of an object, `JS_WriteArray`, `build_arg_list`, `JS_CopySubArray`) and the register loop (GETEL, GETEL3, PUTEL, DSTART and DNEXT, the spread, the built-ins it answers), and every read of an element on the pages would pay the check, while the pages make no such reads. The read by atom takes about 94 instructions where an element of a block takes about 10, so the block would gain only where such arrays are hot, Crypto among the V8 benchmarks.
