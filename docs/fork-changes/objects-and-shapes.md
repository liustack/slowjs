# Objects and shapes

A shape is the list of an object's keys in order, shared by objects with the same keys. All the changes here change only the generated Go, through `internal/fixlib`, with no C form.

## New properties of plain objects skip the generic path

Release: v0.26.13.

Defining a new property on a plain object costs less. Object literals, spread, class fields, `JSON.parse` and every new function go through `JS_DefinePropertyValue`, which handed each property on to `JS_DefineProperty` and `JS_CreateProperty` before `add_property` did the work, with a TLS frame and a deferred free at each step. Now `JS_DefinePropertyValue` first calls `objlitDefine` (`lib/objlit.go`), which calls `add_property` itself when the object is extensible and not exotic, not a fast array and not the global object, the property has no getter or setter, and the object does not have it yet. Every other case takes the old path, and so does assignment (`o.x = v`, `Object.assign`). Nothing is cached, so memory use is the same. A property of an object literal takes about 55 ns rather than 95 on linux/amd64 (AMD EPYC), and a server render of a page of tifa's example shop about 6% less, with the same HTML. `fixlib` puts the call into all 5 files and takes the object bit fields `objlitDefine` checks from each file's `JS_NewObjectFromShape`, checked against the checks of the same bits in the old path. This changes only the generated Go, with no C hunk (`internal/fixlib/define.go`).

Tests: `lib/objlit_test.go`, `lib/objlit_memgrind_test.go`, `internal/fixlib/define_test.go`.

The C tree (`engine/quickjs.c`) has the same fast path in C, at the start of `JS_DefinePropertyValue`. `engine/test/compare.sh` runs `testdata/objlit.js` on it and on the Go engine.

### When upstream changes it

What to do when `go run ./internal/fixlib` stops on this change after an upstream release. [upgrading.md](../upgrading.md) has the whole procedure and the order in which to update the lists `fixlib` checks against.

If it reports that `JS_DefinePropertyValue`, `JS_DefineProperty`, `JS_CreateProperty`, `add_property`, `find_own_property` or `find_own_property1` changed (a fingerprint other than the one in `internal/fixlib/definesites.go`), read the new code against `objlitDefine` in `lib/objlit.go`. For a new data property of an extensible object that is not exotic, not a fast array and not the global object, the old path must still end in `add_property` with the `C_W_E` bits of the flags and then store the value, and every other case must still fail one of the checks of `objlitDefine`. Change `objlitDefine` if it no longer matches, then put the new fingerprints into `definesites.go`: `go run ./internal/fixlib -define` prints them, for the files with all of `fixlib`'s other changes made. Any edit to those functions changes the fingerprint, even one that does not matter here, and so does a change to another `fixlib` step that touches them (`fixUp` does). If it reports that `JS_DefinePropertyValue` has a new signature, update the call (`defineCall`) and `reDefineValueHead` in `internal/fixlib/define.go`. `objlitDefine` reads `extensible`, `is_exotic` and `fast_array` through constants that `fixlib` takes from the bit fields `JS_NewObjectFromShape` sets (the second, fourth and fifth, all in one byte), and checks against the checks of those bits in `JS_CreateProperty` and `JS_DefineProperty`. If it reports that `JS_NewObjectFromShape` changed shape, that one of those checks is gone, or that a check disagrees with `JS_NewObjectFromShape`, then the layout of `JSObject` moved or `JS_NewObjectFromShape` sets the fields in another order: find where the three bits are now and update `objectBits` and its patterns in `internal/fixlib/define.go`.

## Kept shapes

Release: v0.26.16.

A VM keeps the shapes of plain objects once their objects are gone. The shape of an object is its keys in order, and an object literal goes through one shape for each key. `add_property` grew a shape in place when only its object used it, so the shapes in between were gone once the object had its keys, and the last one went with the last object: the next literal with the same keys copied and grew them all again. Now `js_free_shape0` keeps a shape whose count drops to zero in a ring of the last n, with a count of one, and `add_property` copies a shape that only its object uses instead of growing it, so that the shapes in between are kept too (`lib/shapecache.go`). The next literal with the same keys finds every shape it needs in the shape hash table, and makes none. The times in this entry were all taken without PGO, on linux/amd64 (AMD EPYC). A copy costs an allocation and the keys so far, which an object that gets keys no other object has, one at a time, pays for each key and never gets back: such objects took 22% longer to build. So each shape `add_property` finds earns one copy, up to 64, and without credit the shape grows in place. The shapes in between are then still kept, only later: the shape an object leaves when it finds the next one kept is kept. Objects of keys no other object has now take about 6% longer to build than with the cache off, and object literals with the same keys 30% less. Only shapes whose prototype is the `Object.prototype` of the VM, that have at most 32 keys and no key that is a symbol not registered are kept, so a kept shape holds nothing alive but that prototype and the atoms of its keys, and a `WeakRef` or `FinalizationRegistry` whose target is a symbol sees it go as it would without the cache. Shapes the cycle collector frees are not kept, and `JS_FreeRuntime` lets every kept shape go. The ring is in the state of the runtime, next to the [front cache](memory-and-allocation.md#a-front-cache-for-small-blocks). In `lib` it is off until `JS_SetShapeCache(ctx, n)`, which refuses a ring whose size does not fit in a `size_t`. A new VM keeps `DefaultShapeCache` (2048) shapes, `VM.SetShapeCache` changes it, and `VM.Close` turns it off before it frees the context.

Memory: one VM of the shop holds 647 KiB more after a GC, and with the front cache as well 722 KiB more (8.03 MiB rather than 7.33). With 1024 shapes it was 190 KiB and 461 to 502 KiB more, and with 4096 shapes and the front cache 1.26 MiB more. How the blocks fall in the arenas moves these by up to 0.5 MiB from one run to another, with the same shapes and objects left. Loading the shop's bundle alone keeps about 1250 shapes, so a ring of 1024 is full before the first render. Kept shapes count against the memory limit of the VM, and they are not let go when an allocation fails: an allocation in `add_property` can come right before the object takes a shape that only the cache holds. A shape of 32 keys of about ten characters, that no other object has, takes about 3 KiB with the atoms of its keys, so 2048 of them take about 6 MiB, and the atom table keeps the size it grew to after they go. A script that runs close to its memory limit can run out of memory with the cache on where it would not without it: give such a VM a smaller cache, or none. Without PGO, on linux/amd64 (AMD EPYC), with the same HTML, the shape cache alone makes a render 3.6% faster, and with the front cache and the [interrupt countdown](interpreter-loop.md#the-interrupt-countdown-inside-the-interpreter) a render takes 4.5% less time than without the three (six rounds). Two VMs on two hardware threads of one core render 2.9% more pages a second. Generated Go only, no C hunk (`internal/fixlib/shapecache.go`).

Tests: `lib/shapecache_test.go` (reuse, which shapes are kept, symbol keys, the ring, the credit for copies, the cycle collector, `JS_FreeRuntime` with the cache on, out of memory, a ring too large for a `size_t`, 8 runtimes on 8 goroutines), `shapecache_test.go` (the memory limit, and objects built in many ways that read the same with the cache on and off) and `internal/fixlib/shapecache_test.go`.

The C tree (`engine/quickjs.c`) has the same cache in C: the field `shape_cache` of `JSRuntime`, `js_shape_keep` in `js_free_shape0`, `js_shape_keepable` and `js_shape_found` in `add_property`, `JS_SetShapeCache(ctx, n)` in `quickjs.h`, and `JS_FreeRuntime` lets every kept shape go. It is off until `JS_SetShapeCache` turns it on. `js_shape_keep` returns the shape it lets go of when the ring is full, which `js_free_shape0` then frees, rather than freeing it itself. The native runners (`jsrun` and `run-test262`) keep 2048 shapes, as a new VM does. `engine/test/compare/shapecache.js` runs the scripts of `TestShapeCacheSameResults` on the C tree and on the Go engine (`engine/test/compare.sh`), and `engine/test/unit.c` checks which shapes are kept: the shapes in between, the ring, up to 32 keys, symbols that are not registered, objects without a prototype, the credit for copies, and the cache turned off. It also checks that a full and a young collection leave the kept shapes, that the cycle collector frees the shapes of the cycles it frees, that a full ring lets its oldest shapes go, that a runtime freed with kept shapes frees them and its context, and that an allocation that fails leaves the ring whole.

### When upstream changes it

If it reports that the functions of `shapeFuncs` or `JSShape` changed (`internal/fixlib/shapesites.go`), read them against `lib/shapecache.go`: `add_property` must still copy a shape whose count is not one, link the copy into the hash table, and take a shape it finds there on the line `shapeFound` is put before. A shape whose count is not one must still never change in place: `js_shape_prepare_update` copies it, and `resize_properties` and `compact_properties` change only a shape of count one that an object has. Outside the cycle collector a shape must still be freed only through `js_free_shape0` (`free_object` frees the shape of an object that way, and `JS_NewObjectFromShape` takes the count it is given), `js_new_shape2` must still grow the hash table when it is half full, `__JS_NewAtom` must still put the index of a symbol that is not registered in its `hash_next`, where `js_get_atom_index` and `JS_FreeAtomStruct` read it and which `JS_ResizeAtomHash` leaves alone, and the cycle collector must still free the shapes of a cycle itself while `gc_phase` is `JS_GC_PHASE_REMOVE_CYCLES`. Then run `-shape`. If it reports that `gc_phase` is not the byte right after `tmp_obj_list`, change `gcPhaseOffset` in `lib/shapecache.go` to where it is.

## for in skips prototypes with no enumerable property

Release: v0.26.17.

A `for in` loop no longer lists the property names of each prototype to find out that it has no enumerable property. When a loop runs out of the object's own properties, the engine checks the objects of its prototype chain for enumerable string keys, to know whether it must walk the chain. It did that with `JS_GetOwnPropertyNamesInternal`, which mallocs a list, takes a reference to each name and frees it all again, in every loop and for every prototype, mostly for `Object.prototype`, which has dozens of names and none of them enumerable. `js_for_in_prepare_prototype_chain_enum` now first calls `forInNoEnum` (`lib/forin.go`), which reads the shape of a prototype that is not exotic: when no property of the shape has a name and the enumerable flag, it gives the same empty list without allocating, and the loop goes on as before.

Why this is safe: for an object that is not exotic, `JS_GetOwnPropertyNamesInternal` with these flags counts only shape properties with a name, the enumerable flag and a string key, calls no method of the class and throws for nothing it does not count, so with no such property its list is empty. `forInNoEnum` answers no for every exotic object (arrays, `String` objects, proxies, ...) and for every object with an enumerable property, symbols included, and the engine lists the names as before, so the traps of a proxy in the chain run as they did. The only difference is out of memory: the empty list needs no memory, where the engine mallocs one entry, so with no memory left the loop goes on where it used to fail. `fixlib` puts the call into all 5 files and takes the two bit fields `forInNoEnum` reads, the flags of a shape property and the `is_exotic` bit of an object, from each file's own `JS_GetOwnPropertyNamesInternal`. It pins the text of `js_for_in_prepare_prototype_chain_enum`, `JS_GetOwnPropertyNamesInternal`, `get_shape_prop` and `JS_FreePropertyEnum` by fingerprints (`forInSites`). This changes only the generated Go, with no C hunk (`internal/fixlib/forin.go`).

On linux/amd64 without PGO, against v0.26.16 over 10 rounds, the spiral page of tifa's bench app, which runs many for in loops, renders in 0.983 of the time (a wide range, 0.888 to 1.041) and the table page in 0.971 (0.871 to 1.035). tifa's example shop barely changes (0.996, 0.987 to 1.001), nor do the MUI pages. The HTML and the memory of a VM stay the same.

Tests: `lib/forin_test.go`, whose `testdata/forin.txt` is what the engine gave before the change, and `internal/fixlib/forin_test.go`.

The C tree (`engine/quickjs.c`) has the same change in C: `js_for_in_prepare_prototype_chain_enum` calls `js_for_in_no_enum` first. `engine/test/compare.sh` runs `testdata/forin.js` on it and on the Go engine.

### When upstream changes it

If it reports that `js_for_in_prepare_prototype_chain_enum`, `JS_GetOwnPropertyNamesInternal`, `get_shape_prop` or `JS_FreePropertyEnum` changed (a fingerprint other than the one in `internal/fixlib/forinsites.go`), read them against `lib/forin.go`: for an object that is not exotic, the names listed with `JS_GPN_STRING_MASK` and `JS_GPN_ENUM_ONLY` must still be only shape properties with a name and the enumerable flag, the loop must still go on to the next prototype when the list is empty, and freeing an empty list must still do nothing. If it reports that the reads of the enumerable flag or the test of `is_exotic` changed shape, find where the bits are now and update the patterns in `internal/fixlib/forin.go`. Then put the new fingerprints in (`go run ./internal/fixlib -forin` prints them) and run `go test -run ForIn ./lib`.

## String keys that are already atoms

Release: v0.26.17.

A string key that is already an atom costs less. `o[k]`, `o[k] = v`, `k in o`, `hasOwnProperty(k)`, computed keys of literals and every other path that turns a value into a property key go through `JS_ValueToAtom`, which took a TLS frame, duplicated the string (`JS_ToPropertyKey`), checked that it is no index (`is_num_string`) and looked its index up (`__JS_NewAtom`), even when the string was the atom itself: a name the code has, a key from `for...in`, `Object.keys` or `JSON.parse`. On the pages of tifa's example shop, 92% of the strings `JS_ValueToAtom` gets are such atoms. Now, for a string, it first calls `atomKey` (`lib/atomkey.go`): an atom string that is not empty and does not start with a digit, for which `is_num_string` is false, gets its index from the atom table and one more reference, none for a constant atom, as the generic path gives. Every other string, numbers and symbols take the generic path, and a number does not even make the call. Nothing is cached, so memory use is the same.

On linux/amd64 without PGO (AMD EPYC 7B13, one core), against v0.26.16, a micro benchmark reads with a string key in 13% less time, writes in 30% less, runs `k in o` in 26% less and `hasOwnProperty(k)` in 14% less, and a server render of a page of the shop takes 1.3% less time (median of 6 rounds, 0.9% to 1.5% over the rounds), with the same HTML. These were measured before the [for in](#for-in-skips-prototypes-with-no-enumerable-property), bitwise and comparison changes (see [operators.md](operators.md)).

`fixlib` puts the call into all 5 files and takes the atom type and the length of a `JSString` from each file's `__JS_NewAtom` and `is_num_string`. Generated Go only, no C hunk (`internal/fixlib/atomkey.go`).

Tests: `lib/atomkey_test.go` (the atom and the reference counts against the generic path, the keys it leaves to that path, an atom freed and made again, the description of a symbol and the key of a registered symbol, strings that share the symbol's atom), `lib/atomkey_memgrind_test.go` (the same tests leave no C memory behind), `atomkey_test.go` (keys that look like numbers, index strings, symbols, the text of symbols and constant atoms through every way a key goes, against Node, and the atom count after keys are dropped) and `internal/fixlib/atomkey_test.go`.

The C tree (`engine/quickjs.c`) has the same change in C, at the start of `JS_ValueToAtom`: such a string returns `JS_DupAtom` of its own index. `engine/test/compare.sh` runs `testdata/atom_keys.js` on it and on the Go engine, and `engine/test/unit.c` checks that an atom made from a string at run time and used as a key many times is freed with the last value that holds it.

### When upstream changes it

If it reports that `JS_ValueToAtom` or a function of `atomKeyFuncs` changed (`internal/fixlib/atomkeysites.go`), read them against `lib/atomkey.go`: for a string that is an atom and does not start with a digit, `JS_ToPropertyKey` must still return it with one more reference, `is_num_string` must still be false for it, and `__JS_NewAtom` must still answer with `js_get_atom_index` and drop that reference only for a constant atom. Then run `-atomkey`. If it reports that `JS_ValueToAtom` has another signature, or that the atom type test of `__JS_NewAtom` or the length read of `is_num_string` changed shape, update `reAtomKeyHead`, `reAtomKeyType` or `reAtomKeyLen` in `internal/fixlib/atomkey.go`: `atomKey` reads the atom type and the length through the constants `fixlib` takes from them.

## New functions get length and name at once

Release: v0.26.17.

A new function gets its `length` and `name` without the shapes in between. `js_function_set_properties` gave every new function the two through `JS_DefinePropertyValue` and `add_property`, one at a time: the function went from the empty shape of its prototype, through a shape with `length` only, to the shape with both. Nothing held the empty shape or the one with `length` only for long, so they were made again for each function and freed again a moment later (3,000 arrows, methods and constructors made 5,001 shapes). Now `js_function_set_properties` calls `funcShape` first (`lib/funcshape.go`). For each of the four prototypes of new functions (`Function.prototype` and those of async, generator and async generator functions) it remembers the empty shape and the shape with both, the first time a function goes through `add_property`, and puts the next functions with that empty shape straight onto the shape with both, and writes the two values (the same 3,000 functions made 2,000 shapes, for the object literals and the `prototype` of the constructors).

Why this is safe: a shape is shared and never changes in place while more than one object holds it (`add_property` and `js_shape_prepare_update` copy it first), and `funcShape` holds both, so they stay as they were and the empty shape cannot be freed and its memory taken by another shape. The shape with both is the one `add_property` gives, with the same prototype, keys, order, flags and size of the property array, and the name is made before the function changes, so the cycle collector, which can run there, finds it as it is. The shapes are held for the context, as it holds the shapes of its arrays and `arguments` objects: `JS_MarkContext` marks them, so the cycle collector frees a context that only they hold alive, and `JS_FreeContext` lets them go. Everything else, an object that is not an ordinary extensible one or has another shape, takes the old path.

The shapes held add one or two shapes to a VM (88 to 176 bytes in one VM of the shop). Without PGO, on linux/amd64 (AMD EPYC, one core), with the same HTML, a render of tifa's example shop takes 0.982 of the time it took with the [regexp change for alternatives](regexp.md#alternatives-that-cannot-match-are-not-pushed) alone (the median of 10 rounds, 0.967 to 0.989), the MUI pages 0.993 to 1.000 and the bench pages 0.984 and 0.995, each from one build of each side. Against `80261af`, with the code elsewhere, the shop took 0.972 (0.951 to 1.003), the MUI pages 0.990 to 1.004, and the bench pages 0.993 and 0.995. On `de42e83`, 3 rounds gave the shop 0.988 and the MUI pages 0.983 to 0.997.

`fixlib` puts the three calls into all 5 files, and checks the text of `js_function_set_properties`, `add_property`, `find_hashed_shape_prop`, `add_shape_property`, `js_shape_prepare_update`, `js_clone_shape`, `JS_NewObjectFromShape`, `JS_AtomToString`, `JS_MarkContext`, `JS_FreeContext` and `JSShape` against fingerprints. This changes only the generated Go, with no C hunk (`internal/fixlib/funcshape.go`).

Tests: `lib/funcshape_test.go`, whose `testdata/funcshape.txt` holds what Node gives for the own properties of 36 kinds of new functions, made many times and changed after they were made (the engine before the change gives the same), the shapes it holds and lets go, and a context that only they hold alive, `lib/funcshape_memgrind_test.go` and `internal/fixlib/funcshape_test.go`.

The C tree (`engine/quickjs.c`) has the same change in C: `js_function_set_properties` calls `js_function_shape` first. There the shapes are held per context, in the field `func_shapes` of `JSContext`, rather than per runtime for the context that made the last function, so two contexts of a runtime do not take the slots from each other. `JS_MarkContext` marks them and `JS_FreeContext` lets them go. `engine/test/compare.sh` runs `testdata/funcshape.js` on it and on the Go engine, and `engine/test/unit.c` checks that each of the four prototypes keeps its two shapes and new functions reuse them, that two contexts keep their own, that the cycle collector frees a context that only they hold alive, and leaves them in a live one.

### When upstream changes it

If it reports that the functions of `funcShapeFuncs` or `JSShape` changed (`internal/fixlib/funcshapesites.go`), read them against `lib/funcshape.go`: `js_function_set_properties` must still give `length` and then `name`, both configurable only, through `JS_DefinePropertyValue`, `add_property` must still move an object onto a shape it finds in the hash table as `funcShape` does (`shapeFound`, a new count, the old shape freed, the property array kept when the sizes match), a shape whose count is not one must still never change in place, `JS_NewObjectFromShape` must still give an object a property array of the size of its shape, and `JS_MarkContext` and `JS_FreeContext` must still mark and free the shape of arrays where `funcShapesMark` and `funcShapesFree` are put. Then run `-funcshape`.

## Methods of strings, numbers and arrays found in the interpreter

Release: v0.27.1.

`s.charCodeAt(i)`, `n.toFixed(2)` and `a.push(x)` find their method in the interpreter. `get_field` and `get_field2`, the opcodes of `o.x` and `o.x(...)`, look for the key on the object and its prototypes in a loop of their own, and handed everything else to `JS_GetPropertyInternal`: every value that is not an object, and every object with exotic behavior, arrays included. The CSS-in-JS code of tifa's MUI pages reads string methods about 320000 times in a render of the order list, and both of tifa's apps read array methods a few thousand times. Now the loop starts at `String.prototype` for a string and a key that is no index and not `length`, and at `Number.prototype` for a number, through `fieldProto` (`lib/fieldchain.go`), and goes on past a fast array that is not a typed array for a key that is no index, through `fieldGoesOn`. Every other value or object takes `JS_GetPropertyInternal` as before.

Why this is safe: those are the keys for which `JS_GetPropertyInternal` itself goes straight to the prototype. A string has its indexes and `length` of its own and nothing else, and a number nothing. A fast array has its elements at indexes, and a typed array also answers `undefined` for a key that is a number in canonical form, such as `Infinity`, so typed arrays stay on the old path. The value stays on the interpreter's stack, so a getter, a proxy or another exotic object further up the chain still takes the slow path with the value as `this`, and a method or getter added to the prototype later is found where it is. Nothing is cached, so memory use is the same.

Without PGO, on linux/amd64 (AMD EPYC 7B13, one core), against v0.27.0 with the same HTML, the four MUI pages of tifa's test app render in 0.975 of the time (0.966 to 0.986 over 6 rounds in 3 code layouts) and the six pages of the shop in 0.996 (0.992 to 0.998). Under callgrind the engine runs 1.0% fewer instructions on the MUI pages and under 0.1% fewer on the shop. The time drops more than the instruction count: `JS_GetPropertyInternal` and its property lookup were mostly waiting on memory.

`fixlib` puts the calls into the 5 files, where `fieldProto` reads the struct form of a `JSValue`, and takes the fast array bit from each file's `JS_GetPropertyInternal`. Generated Go only, no C hunk (`internal/fixlib/fieldchain.go`).

Tests: `fieldchain_test.go`, whose `testdata/field_chain.js` reads methods, missing keys and keys added later on strings, ropes, numbers and arrays, with getters in sloppy and strict mode, read-only keys, a proxy and a frozen object above `String.prototype`, frozen, sealed, sparse and typed arrays, `arguments`, String objects, symbols, `with` and `eval`, against Node, and checks that an interrupt or running out of memory in such a getter or method cannot be caught. `internal/fixlib/fieldchain_test.go` checks the rule.

### When upstream changes it

If it reports that `JS_GetPropertyInternal`, `JS_GetPrototypePrimitive` or `__JS_AtomIsTaggedInt` changed (`internal/fixlib/fieldchainsites.go`), read them against `lib/fieldchain.go`: for a string and a key that is no index and not `length`, and for a number, `JS_GetPropertyInternal` must still look for the key from the prototype `JS_GetPrototypePrimitive` gives with the value as `this`, and for a fast array that is not a typed array and a key that is no index it must still go on to the prototype. Then run `-fieldchain`. If it reports that the loop of `get_field` or `get_field2`, their test of exotic behavior or their slow path changed shape, update `reFieldEntry`, `reFieldExotic` or `reFieldSlow` in `internal/fixlib/fieldchain.go`.

## Own keys listed from the shape

Release: Unreleased.

Listing the own keys of an ordinary object costs less. `for in`, `Object.keys`, `values` and `entries`, `Object.getOwnPropertyNames`, `Reflect.ownKeys`, object spread and the rest of a destructuring, `Object.assign` and `JSON.stringify` all go through `JS_GetOwnPropertyNamesInternal`, which walks the shape twice and asks the atom table of each key whether it is a string, a symbol or a private name and whether it is an array index, with a call and a TLS frame for each question. Then spread and rest (`JS_CopyDataProperties`) and `Object.keys`, `values` and `entries` (`JS_GetOwnPropertyNames2`) look each key up again to read its value. React's `jsx` spreads and copies props in nearly every element. Now the three call `ownKeys`, `copyData` and `ownKeysArray` first (`lib/ownkeys.go`). For an object that is not exotic they list the keys from the shape in Go, in the engine's order (array indexes by value, then strings, then symbols and private names, each in shape order), and spread, rest, `values` and `entries` read the values of plain data properties straight from the object. A spread into an empty object literal of an object whose keys are all enumerable, writable and configurable strings, then symbols, with the same prototype, gives the new object the shape of the source, which defining the keys one by one would have led it to, and copies the values.

The kinds of the keys of a shape are kept in a key cache of the runtime, 256 entries of the kinds of up to 24 keys, about 8 KiB per VM, so that the next listing of an object of that shape reads no atom. It differs from the [table of shape steps](../performance.md#what-was-tried-and-not-done) that was dropped: that table held shapes alive, which added 28 KB to 142 KB per VM and changed when the cycle collector runs. The key cache holds no shape, atom or object, only a byte per key. It keeps entries only for shapes in the shape hash table and drops the entry of a shape when it leaves the table (`js_shape_hash_unlink` calls `ownKeyCacheDrop`). A shape in the table never changes in place: it leaves the table before a key is added (`add_shape_property`), before a key is deleted or its flags change (`js_shape_prepare_update`) and before it is freed (`js_free_shape0`). So the kinds the cache has for a shape are those of its keys, and its memory cannot have gone to another shape. The flags are read from the shape at each listing.

Why this is safe: for an object that is not exotic, `JS_GetOwnPropertyNamesInternal` reads only the shape, calls no method of the class, and throws only for a binding of a module namespace not yet initialized, listed with `JS_GPN_ENUM_ONLY` or `JS_GPN_SET_ENUM`. `ownKeys` leaves such a binding, and objects with more than 16 array indexes, to the engine. Exotic objects (arrays, `arguments`, `String` objects, typed arrays, proxies, module namespaces) take the old path, so the traps of a proxy run as before. Values are read directly only when every key listed is a plain data property: then nothing runs between the listing and the reads that could change the object. An object with a getter, a setter or a binding, or with a `stack` key, which can hold the marker of an [error stack](errors-and-stacks.md#error-stacks-formatted-when-first-read) not formatted yet, takes the engine's path for its values. `Object.assign` sets rather than defines, and keeps its path after the listing. What upstream does differently from Node stays: a spread whose getter deletes a key it has not copied yet still copies that key, and the spread of a string primitive copies nothing.

On linux/amd64 without PGO (AMD EPYC 7B13, one core), against v0.28.2 with the same HTML, the six bench pages of tifa's example shop render in 0.990 of the time (0.958 to 1.020 over 6 rounds in 3 code layouts), its ten store pages in 0.994 (0.952 to 1.036) and the four MUI pages of tifa's test app in 0.987 (0.957 to 1.047). The gain depends on the layout of the code: 0.976 to 0.978 of the time in one layout, 0.991 to 1.006 in the other two. Of the listings of a render 99.9% take the new path, with about four keys each, and about a quarter of the spreads take the shape of their source. On the Apple M4, a spread of six keys into a new literal takes 74 ns rather than 250, `{...a, ...b}` 155 rather than 372, the rest of a destructuring 239 rather than 316, `Object.keys` of six keys 134 rather than 542, `Object.values` 128 rather than 567, `Object.entries` 529 rather than 1452, and a bare `for in` 261 rather than 291. The key cache adds 8 KiB to a VM.

`fixlib` puts the four calls into all 5 files and pins the text of `JS_GetOwnPropertyNamesInternal`, `JS_CopyDataProperties`, `JS_GetOwnPropertyNames2`, `JS_AtomGetKind`, `JS_AtomIsArrayIndex`, `is_num_string`, `get_shape_prop`, the functions that link, unlink, grow, change, copy and free shapes, `add_property`, `expand_fast_array`, `add_fast_array_element` and `JSShape` by fingerprints (`ownKeysSites`). The bit fields it reads are the constants of [for in](#for-in-skips-prototypes-with-no-enumerable-property), [string keys](#string-keys-that-are-already-atoms) and [new properties](#new-properties-of-plain-objects-skip-the-generic-path). Generated Go only, no C hunk (`internal/fixlib/ownkeys.go`).

### When upstream changes it

If it reports that a function of `ownKeysFuncs` or `JSShape` changed (`internal/fixlib/ownkeyssites.go`), read them against `lib/ownkeys.go`: for an object that is not exotic, `JS_GetOwnPropertyNamesInternal` must still list the keys of the shape with an atom, array indexes by value, then strings, then symbols and private names, and throw only for a module binding, `JS_CopyDataProperties` without `setprop` and `JS_GetOwnPropertyNames2` must still define or collect the values in that order, a shape in the hash table must still leave it through `js_shape_hash_unlink` before it changes or is freed, and `add_property` must still move an object onto a shape it finds as `copyShape` does. Then run `-ownkeys`. If it reports that one of the four functions has another signature, update its `head` and `text` in `ownKeysHooks` in `internal/fixlib/ownkeys.go`.
