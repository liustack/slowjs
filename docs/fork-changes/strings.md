# Strings

## Searches skip to where the string is

Release: v0.27.3.

`String.prototype.includes`, `startsWith`, `endsWith`, `indexOf` and `lastIndexOf` find the string they look for with the search of package bytes. Upstream compares the whole string with `string_cmp` at one index after the other, and `string_cmp` reads each character of both strings through `string_get`, so a search that finds nothing costs a call and a few character reads for each character of the string it looks through: about 3 ns a character. tifa looks for the marker of a Suspense boundary in the whole HTML of a page after each render, which was about 1% of a render of tifa's example shop.

`fixStringSearch` puts a call of `stringFind` (`lib/stringsearch.go`) at the start of the loops of `js_string_includes` and `js_string_indexOf`. From the index the loop is at, it returns the next index where the string is, in the direction the loop goes, and the loop compares there as before, finds it and ends. When there is none, it returns -1 and the loop ends without a match. When both strings have 8-bit characters, `stringFind` uses `bytes.Index` or `bytes.LastIndex`. When the string it looks through has 16-bit characters, it searches its bytes for the bytes of the other string widened to 16 bits, and takes only a match at an even offset. A string of 8-bit characters longer than 64 looked for in one of 16-bit characters, or the other way round, is compared one character after the other, as `string_cmp` does, with no copy. `startsWith` and `endsWith` compare at one index: there `stringFind` returns that index at once, inlined, and the loop compares.

Why it gives the same results: the loop still makes its own comparison at the index `stringFind` returns, so a match is only ever one `string_cmp` confirms, and `stringFind` returns the first index in the loop's direction where the characters are the same, which is the first one the loop would have found. A string of 16-bit characters may hold only characters below 0x100, so the widths of the two strings do not decide whether there is a match. The strings are read where `string_get` reads them, with the constants `fixJSONStrings` takes from each generated file. `string_indexof`, which `split`, `replace` and `replaceAll` use, is left as it is: it already skips to the next index of the first character, and its strings are mostly short, where a call costs more than it saves.

A search also counts a step toward the interrupt check for each 8 indexes it looks through, found or not, as the string buffer counts the characters it makes room for ([Parsing and building strings count toward the interrupt check](uncatchable.md#parsing-and-building-strings-count-toward-the-interrupt-check)): `stringFind` calls `_js_charge_interrupts` of `lib/charge.go` with the context of the method. A loop of `indexOf`, `lastIndexOf` or `includes` that finds nothing in a string of 1 MB used to stop 170 ms, 6.9 s and 170 ms after a 10 ms timeout, and 340 ms in a string of 16-bit characters: each search was one poll however long the string. They now stop within 20 ms of the start, building the string of 1 MB included. `startsWith` and `endsWith` compare at one index and count nothing. Over 6 rounds in 3 code layouts against the search without the count, the median of each search of about 20 characters takes 0.98 to 1.02 of the time, as much as `replace` and `split` move, which run none of the changed code (1.031 and 1.006), and searches through 1 KB and 100 KB 0.995 to 1.002. A miss of `indexOf` or `lastIndexOf` came out 1.7% slower in both of two builds of the count, about 2 ns, which is inside that spread but may be real.

Looking through 100 KB of HTML that does not hold the string takes 81 µs rather than 320 µs, and 87 µs rather than 271 µs when the HTML has 16-bit characters. A miss in a string of about 20 characters takes 108 ns rather than 164 with `indexOf` and 102 rather than 119 with `includes`, `lastIndexOf` in 1 KB 1.6 µs rather than 3.1, and `startsWith` 102 ns rather than 107 (linux/amd64, AMD EPYC 7B13, one core, without PGO, each a loop in javascript of the same call). In a Go CPU profile of tifa's six shop workbench pages, `String.prototype.includes` went from 1.06% of the samples to 0.27%: its own search from about 0.75% to 0.13%, and what is left is mostly making the rope of the HTML one string, which the render then reads anyway. On the MUI pages of tifa's test app it went from 0.63% to 0.11%. A render of the six shop pages takes 0.995 of the time (0.975 to 1.032 over 6 rounds in 6 code layouts), and the MUI pages 1.003 (0.970 to 1.024), without PGO: the gain is smaller than the spread between code layouts, which alone moves a render by about 2%. No page and no micro benchmark got slower.

Generated Go only, no C hunk (`internal/fixlib/stringsearch.go`). The memory is the same: the widened string is an array of 64 characters on the Go stack.

Tests: `lib/stringsearch_test.go` checks the five methods, with every position argument, and `split`, `replace` and `replaceAll`, against a search written with `charCodeAt` alone, on strings of 8-bit and 16-bit characters, ropes and slices, found and not found, at the ends, more than once and longer than 64 characters, and `stringFind` directly on strings of each width, 16-bit strings that hold only characters below 0x100, characters whose bytes match at odd offsets, and both directions. `TestStringFindCountsSteps` checks the steps each method counts, and `TestStringSearchStops` in `workstop_test.go` that a loop of searches in 1 MB stops within 50 ms of a 10 ms timeout. `lib/stringsearch_memgrind_test.go` checks that no C memory is left behind, and `internal/fixlib/stringsearch_test.go` the rewrite.

The C tree (`engine/quickjs.c`) has the same change in C, with a search of its own: the loops of `js_string_indexOf` and `js_string_includes` call `js_string_find` at the start of each turn. One character is looked for with `memchr`, or a loop in a string of 16-bit characters and toward the start. A string of up to 8 characters is looked for by finding its first character that way and comparing the others there, at most 8 units of work for each index, which spares the work the Two-Way search does on the needle first (about 20 ns a search). A longer string is looked for with the Two-Way search of musl's `memmem`, written for 8-bit and 16-bit characters, for a needle of the other width and for both directions. Its time is linear in the lengths of the two strings whatever they hold, also for a needle that matches almost everywhere: on linux/amd64 (AMD EPYC 7B13), comparing the needle at each index where its first character is took 2.5 s for `'a'.repeat(131072).indexOf('a'.repeat(65536) + 'b')`, and the Two-Way search takes 0.5 ms. The search counts a step for each 8 units of work, a character looked at or compared, and checks the interrupt counter after at most 2^17 units, calling the interrupt handler when the counter runs out, as the interpreter does: a handler that asks to stop ends a long search in the middle, where the Go engine counts once the search is over. `engine/test/compare/stringsearch.js` runs the script of `TestStringSearch` on it and on the Go engine (`engine/test/compare.sh`), with long needles of few letters that repeat, and `engine/test/unit.c` checks that searches in a long string run the interrupt handler, that one long search calls it many times and ends with the error `interrupted` when it asks to stop, and that needles that match almost everywhere take a fraction of a second, forward and back, in strings of each width and in one of each.

### When upstream changes it

What to do when `go run ./internal/fixlib` stops on this change after an upstream release. [upgrading.md](../upgrading.md) has the whole procedure and the order in which to update the lists `fixlib` checks against.

If it reports that a function of `searchFuncs` changed (`internal/fixlib/stringsearch.go`), read them against `lib/stringsearch.go`: the loops of `js_string_includes` and `js_string_indexOf` must still compare the whole string with `string_cmp` at each index from `start` to `stop`, both included, by a step of 1 (or `inc`, 1 or -1, in `js_string_indexOf`), and stop at the first match, with the characters of both strings in range. `string_cmp` must still compare the characters `string_get` reads, and `string_get` must still read them as the constants of `fixJSONStrings` say. The call passes the context as `ctx2`, the name ccgo gives the parameter in both functions: if a release renames it, the fingerprints change too, and the name goes into `searchCall`. Then run `-search`. If it reports that a loop changed shape, update `reSearchLoop` in `internal/fixlib/stringsearch.go`, and run `go test -run 'StringSearch|StringFind' ./lib ./internal/fixlib`.
