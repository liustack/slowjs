# The C tree of the new engine

`engine/` is the C engine that will replace the ccgo one of `lib/` (see [architecture.md](../architecture.md)). Nothing here is in the Go API or in a release yet: the generated Go and the interpreter of `lib/goasm_*` are made from the pinned archive, `lib/internal/patch/quickjs.diff` and `cpatch.py`, and do not read `engine/`. What follows changes only `engine/`. It is written down here so that the switch has the list of what users will see, and the Go side of each item is known. When the switch is made, each row goes to the changelogs in both languages.

| Change | What changes for a program | Checked by |
| --- | --- | --- |
| The engine builds with `-ffreestanding -nostdinc` against `engine/libc` | `Math.*` gives the same bits on linux/amd64 as the Go engine today. On the other targets it can change in the last digit (see "The small libc") | `check-symbols.sh`, `libc-test.sh`, `math.sh` |
| `Date` and the seed of `Math.random` come from `host_now` | the Go host answers with the clock of the VM | the native host, `HOST_CLOCK` |
| `abort` is a request to the host: `host_call` with `HOST_CALL_ABORT` | the Go host panics and the VM can only be closed, as it is now. A trap would be a signal and would end the process | `api-test.c` |
| `Atomics.wait` throws, `Atomics.notify` wakes nobody | `Atomics.wait` throws a `TypeError` as the main thread of a browser does. There are no threads in the engine | test262 with `engine/test/test262.conf` |
| `Atomics.pause` sends no hint to the CPU | it checks its argument and returns `undefined`. The specification has an engine send the hint only if its platform can, and the engine holds no inline assembly | test262 `built-ins/Atomics/pause`, the generator (no stub) |
| A format is a string constant, or the format of a `printf` function, and agrees with its arguments | nothing changes for a program. A new format that `snprintf` would abort on cannot be built | the build (`-Werror=format-nonliteral`), the generator, `libc-test.c` |
| `JS_NewClassID(rt, &id)` counts per runtime | the Go side keeps its class IDs per VM | `api-test.c` |
| `JS_DumpMemoryUsage(buf, size, ...)` writes to a buffer | no `FILE`. The Go side gets a string | `api-test.c` |
| The tools that print are gone: `JS_Dump*`, `dump_token` and the like | the `DUMP_*` options of the C do not build | the build |
| `JS_PrintValue` and its options are there only with `CONFIG_PRINT_VALUE` | the generated engine has no value printer. A host that prints values with it defines `CONFIG_PRINT_VALUE`, as the native test host does, and `DUMP_BYTECODE` asks for it | the build, `cycles.sh` |
| `JSClassExoticMethods` has no `get_prototype` | a class of the host cannot give its objects a prototype of its own. A proxy is the one object that does, and `JS_GetPrototype` calls it by name | the build, test262 |
| Recursion is bounded by counted depths, not by the stack: 5000 calls by default, at most 10000, and 2000 levels of C recursion | the Go engine counts 10000 TLS stack slots, so a script that recursed deeper than 5000 calls gets a `RangeError` sooner. `JS_SetMaxCallDepth` replaces `JS_SetMaxStackSize`. Chains of bound functions, `finally` and iterator helpers that crashed now throw, and so do chains of more than 2000 modules (imports, `export * from`, `export { x } from`). Parentheses nest 665 deep. `JS_GetCallDepth` and `JS_SetCallDepth` (and the internal pair) let a host hand the depths from one runtime to another | `unit.c`, test262 |

## The small libc

`engine/libc` is musl's string and math functions at commit `7ada6dd` (the one `modernc.org/libc` v1.77.1 is translated from), a `snprintf` that does the formats the engine uses, and the headers. See its [README](../../engine/libc/README.md).

The math is the same C that the Go engine runs on linux/amd64, built with `-ffp-contract=off -U__FP_FAST_FMA`, so that `log`, `log2` and `pow` take the same branch on every machine. What is tested, and what is not:

- linux/amd64: `engine/test/math.sh` compares, bit for bit, 100000 inputs for each of 33 functions of libc (against `modernc.org/libc`, the musl the Go engine runs) and for 33 `Math` operations as JavaScript sees them (against the Go engine). Both are the same on every result. The JavaScript comparison writes a NaN as the one NaN of JavaScript, so it does not compare the sign and payload of a NaN. The libc comparison does.
- macOS arm64: compared once with the linux/amd64 results, by hand and outside the tests. The JavaScript results are the same. The libc results are the same except for the sign of a NaN, which the processor chooses (positive on arm64, negative on amd64). This is not a test that runs.
- The other targets (linux/arm64, darwin/amd64, windows/amd64) are not compared. So the same last digit on all five targets is the aim of the flags and of the shared C, and is shown for two of them.

On the targets where the Go engine takes `Math` from Go's own `math` package today (darwin and windows) the results change in the last digit from what it gives, which is what the switch is for.


`snprintf` reads a whole conversion, flags to conversion letter, and checks it before it takes any argument for it, a `*` included. It calls `abort` on a floating point conversion, `%n`, a positional argument, a length on `c`, `s`, `p` or `%`, any flag, width or precision written on `%` (a `*` there counts, whatever it would be given), a format that ends inside a conversion, and a width or precision that does not fit an int. A width of INT_MIN given for a `*`, and an output longer than INT_MAX, abort too, but only after the arguments are taken, since they depend on them. A new format in the engine cannot print the wrong thing. It is the `abort` of the small libc, which asks the host like every other abort, and not a trap, which in Go would end the process. `libc-test.c` lists the formats that abort and counts the arguments taken before each one does, and `api-test.c` checks that one reaches the host. The only trap left in `engine/` is the one after the `host_call` in `abort`, for a host that returns.

A format is checked before it can reach that `abort`. The engine files are built with `-Werror=format` and `-Werror=format-nonliteral` (`engine/test/flags.sh`), so a format agrees with its arguments, and is either a string constant or the format of a function that has the `printf` attribute and passes it on (`JS_ThrowError2`, `JS_ThrowError` and `js_parse_error_v` have it, with the `va_list` form `format(printf, 3, 0)`). The two helpers behind `JS_ThrowTypeErrorAtom` and `JS_ThrowSyntaxErrorAtom` pass their format with the name of an atom in place of their arguments, which clang cannot follow, and a pragma turns the check off for just those two. The generator then holds every constant to the table of formats `stdio.c` takes (`internal/goasm/gen/formats.go`, `testdata/formats/cases.txt`), and `libc-test.c` holds `vsnprintf` to the same table, so the two cannot drift apart.

`check-symbols.sh` proves the symbol level only. The engine files, with the libc, leave undefined nothing but the callbacks of `engine/host.h` and `host_memory_grow` of `engine/heap.h`. The allocator ([allocator.md](../allocator.md)) is among the engine files, and the engine calls no malloc: `dbuf` and `CharRange` have no default allocator, and `stdlib.h` of the libc declares none. It does not prove that the machine code uses no thread local storage, no system call instruction and no fixed address. Those checks come with the generator, not before.

## Time, abort and the host

`engine/host.h` declares what the engine asks of its host. `host_now(vm, kind)` gives the wall clock or a monotonic one in nanoseconds. `host_call(vm, &this, argc, argv, magic)` calls a function of the host, and a magic below 0 is a request of the engine: `HOST_CALL_ABORT` for `abort()`. The this value goes by address, and a request of the engine has none and passes NULL: a JSValue by value is two words, which with the shadow pointer, `vm`, `argc`, `argv` and `magic` makes 7, and the generated code passes a callback at most 6 words in registers in the `body` calling mode. The `vm` is the one `JS_NewRuntime` was given, and `Date` asks the clock of the VM of its runtime. `Math.random` asks no clock: it starts from the seed `JS_NewRuntime` was given, the same in every context of the runtime. `abort` does not know its VM and passes 0. `host_memory_grow` is in `engine/heap.h` and comes with the allocator. Two kinds of `host_call` below 0 are the allocator's: `HOST_CALL_MEMORY_RELEASE` gives a dedicated chunk back and `HOST_CALL_MEMORY_REMAP` grows one (linux, when the host said so with `JS_SetHostRemap`). They run no user code and do not call back into the engine. The other callbacks (`host_poll`, `host_release`) come with the interrupt.

## Depth of calls and of C recursion

The engine never reads the stack pointer. The generated assembly runs on a Go stack, which moves and grows, and keeps the locals whose address is taken on a shadow stack of its own, so an address on the stack says nothing about how deep the engine is. It counts instead, with two counts in the runtime, and throws `RangeError: Maximum call stack size exceeded` past either. Neither is ever reset: each level that is entered is left on every path, and a level that cannot be entered counts nothing, so the error path recurses no further.

- **The call depth** counts each call of a function while it runs. `JS_CallInternal` counts before it sends a call to a class, so a built-in function, a bound function and a proxy count a level as a JavaScript function does. A constructor that `JS_CallConstructorInternal` sends to a class counts there. The fast path of `JS_IteratorNext2`, which calls the C `next` of a built-in iterator directly, counts a level too: a chain of iterator helpers recursed through it with no other count. The exported functions that run code (`JS_Call`, `JS_CallConstructor`, `JS_CallConstructor2`, `JS_Invoke`, `JS_Eval`, `JS_EvalThis`, `JS_EvalFunction`, `JS_ExecutePendingJob`) count one level for the entry of the host, so that a host function that calls back into the engine adds a level even when the path to the next call is long, as in the parser of `JS_Eval`. The engine itself calls forms of them that do not count (`js_call` and the like). The limit is 5000 by default (`JS_DEFAULT_MAX_CALL_DEPTH`) and at most 10000 (`JS_MAX_CALL_DEPTH_LIMIT`). `JS_SetMaxCallDepth(rt, n)` sets it, and returns -1 and changes nothing when `n` is out of that range or the runtime is running code. A plain recursive function gets 2 levels short of the limit when the host started it with `JS_Eval`: one for the entry and one for the global code.
- **The internal depth** counts the recursions of C that make no call: the parser (`js_parse_unary`, `js_parse_postfix_expr`, `js_parse_assign_expr2`, `js_parse_statement_or_decl`, `js_parse_destructuring_element` and `js_parse_function_decl2`, which cut every cycle of it: the binary and logical operators are read in loops), making the functions of a script (`js_create_function`, and `get_closure_var` for a variable of a function around), `json_parse_value`, `internalize_json_property`, `js_json_to_str`, the parser of regexps (`re_parse_disjunction` and `re_parse_nested_class`, through `lre_depth_enter`), modules (`js_resolve_module` for their imports, `js_create_module_function`, `get_exported_names` for a namespace, `js_resolve_export1` for an export, linking and evaluation), `JS_ReadObjectRec` and `JS_WriteObjectRec`, `JS_FlattenIntoArray`, the methods of a proxy that go on to the target (all but call and construct, which count as calls, and the prototype, which `JS_GetPrototype` asks the proxy by name), `JS_OrdinaryIsInstanceOf` on a bound function and `JS_GetFunctionRealm`. Each is a wrapper that counts around the original function, renamed with a `1` at the end (`js_resolve_export1`, whose name has one already, wraps `js_resolve_export2`). The limit is `JS_MAX_INTERNAL_DEPTH`, 2000, and it is a constant of the build, not a setting like `JS_SetMaxCallDepth`: the bound on the stack the engine can use multiplies it by the stack of the deepest of these recursions, and a bound needs one fixed biggest value for any call depth. A host cannot change it, and `JS_SetInternalDepth` (below) moves the point the count starts from, not the limit. A regexp too deep throws `SyntaxError: stack overflow`, as it did.

Each runtime counts for itself, and the Go stack that the runtimes of one host share sees them all. A host that runs code of one runtime from inside a call of another therefore hands the depths over, so that the chain is held to one limit and not to one limit for each runtime in it. `JS_GetCallDepth(rt)` and `JS_SetCallDepth(rt, n)` read and write the call depth, and `JS_GetInternalDepth` and `JS_SetInternalDepth` the internal depth. Around the call, the host reads both depths of the runtime that calls, sets those of the other runtime to them, makes the call, and sets the other's old depths back (the other runtime may be in the chain already, when two runtimes call each other, and its old depths are then its own outer levels). A write takes 0 up to the limit (`JS_MAX_CALL_DEPTH_LIMIT`, `JS_MAX_INTERNAL_DEPTH`) and returns -1 and changes nothing for anything else. A depth above the limit of that runtime (the other one has a bigger limit) is kept, and the next call in it is a `RangeError`: the chain is deeper than it allows. Unlike `JS_SetMaxCallDepth`, the writes work while the runtime runs code, which is when a host makes them, and a depth that was set must be set back before the code that was running goes on, since each call that ends counts one level off whatever the depth is by then. The internal depth is handed over too: the bound on the Go stack adds the internal levels of everything on it, and runtimes that counted their own would add up to the limit once for each runtime in the chain. `unit.c` runs two runtimes that call each other until a `RangeError`: with the depths handed over the chain is one limit long, and without it twice that.

How deep nesting goes with the limit at 2000, measured on the native host by nesting one form in itself until the next level throws (`RangeError`, a `SyntaxError` for a regexp):

| Form (each nested in itself) | Levels that fit | Counted per level |
| --- | --- | --- |
| Parentheses `((1))`, calls `f(f(1))`, arrays `[[]]` | 665, 665, 666 | 3 (an assignment expression, a unary one and a postfix one, whatever operators are between) |
| Object literals `({a: {a: 1}})` | 664 | 3 |
| Arrow functions `() => () => 1` | 998 | 2 |
| Function expressions `(function () { return (function () { return 1 }) })` | 249 | 8 |
| Blocks `{{}}`, and `if (1) if (1) ;` | 2000, 1997 | 1 |
| Labeled blocks `L0:{L1:{}}` | 1000 | 2 |
| `JSON.parse` and `JSON.stringify` of nested arrays | 2000, 2000 | 1 |

Real code stays far under it. Of 79525 files (npm packages, JSX compiled by esbuild, the output of emscripten, wasm2js, peggy, ajv and the like, and JSON), the deepest parse reaches 632, in the asm.js build of sql.js, which writes the cases of a big `switch` as 290 labeled blocks inside each other. No other file goes past 282, one in a thousand reaches 100, and the middle file 17. A C program with a `switch` of more than about 1000 jump targets, built to asm.js, would not parse. Rendering the pages of tifa's example shop takes the parser 110 levels deep, its MUI pages 99, the bench pages 62 (with the Intl polyfill), and all of test262 256. Everything else stays small on those pages: regexps 49 counted on top of the parser that compiles them, closures 15 (`get_closure_var`), making functions 8, JSON 6, `JS_GetFunctionRealm` 2. The call depth of those renders stays under 600.

Each count also checks the stack left. `__shadow_remaining()` gives the bytes left: the generator turns it into the room left on the shadow stack, and the native test host gives the room left on its thread's stack. Entering either depth needs `JS_STACK_MARGIN` (64 KiB) left, and an `alloca` of a call (the locals of `JS_CallInternal`, the arguments of a bound function) needs its size on top, or it throws the same `RangeError`. So a dynamic alloca never crosses the end of the shadow stack, whatever the depths allow.

A few recursions must not fail, so a count that throws does not fit them, and each is a loop or has a bound that a proof gives. Ropes are read, hashed and freed by loops. A concatenation that makes a rope deeper than `JS_STRING_ROPE_MAX_DEPTH` (60) rebuilds it from its strings in order by a binary count, at most 30 deep whatever their lengths (upstream's rebuild by lengths could leave one 53 deep, and recursed). The parse records of `JSON.parse` with a reviver and the definitions of functions are freed by loops. The case conversions, the decompositions and the emoji sequences of the Unicode tables, and the strings of `\q{...}` in a class of a `v` regexp, are loops. The value printer recursed too and is left out (`CONFIG_PRINT_VALUE` above). Freeing an object can free others: `free_zero_refcount` frees in a loop of its own every object whose count reaches zero while it runs, and nothing it calls starts a collection, so it is never entered twice. `js_nest_enter(rt, JS_NEST_FREE, 1)` counts it and aborts past 1, which cannot happen as long as a finalizer, the host's among them, starts no collection (`JS_RunGC`, `JS_RunYoungGC`).

What the counts do not cover yet: the property layer, one cycle of 169 functions (properties, atoms, conversions, errors, string buffers, big integers and the collector), which exists only in the static call graph. It is bounded without a count, and the generator's proof that no cycle is left uncounted needs it rewritten first. `engine/test/cycles.sh` lists the cycles that no count cuts, and they must be those of `engine/test/cycles.txt`: that one is all it lists now.

The checks: `unit.c` (see [testing.md](../testing.md#the-c-tree-and-its-native-test-host)) and test262, whose 58 known errors stay the same.

## When the engine fails

C can fail where Go code cannot, and a Go process ends for most of it: a read or a write at an address mapped to nothing prints "unexpected fault address" and exits, since only an address below 0x1000 is a panic by default, and a trap instruction (`ud2` on amd64, `brk` on arm64) is SIGILL or SIGTRAP, which the runtime never lets a program recover. The generated engine is held to this: every way it can fail is a panic that the host recovers, or cannot happen. A VM that failed is broken, as after any panic that leaves through engine frames: it refuses every call but `Close`, and the process and the other VMs go on.

| The C does | What the host sees |
| --- | --- |
| Reads or writes an address mapped to nothing: a wild pointer, or the guard page above the shadow stack | A `runtime.Error` panic that names the address. `Enter` of `internal/gohost` turns on `debug.SetPanicOnFault` for the goroutine, and the `Leave` that matches it puts back what the goroutine had. A pointer that is not canonical on amd64 faults with no address and is a panic too |
| Divides by zero (undefined in C) | amd64 raises a divide error, which Go always turns into a panic. arm64 has no such fault and gives 0 |
| Calls `abort` | `host_call` with `HOST_CALL_ABORT` panics with `gohost.ErrAbort` |
| Reaches a trap | None is left in the output. The shadow-stack pass puts a call of `host_trap(sp)` where the C has `__builtin_trap` (the one after the `host_call` in `abort`) and where its own check on a dynamic `alloca` would cross the end of the shadow stack. It panics with `gohost.ErrTrap` |
| Runs out of the shadow stack | The counts throw `RangeError` first. The guard page is the net behind them |

The generator holds this: its checks refuse `ud0`, `ud1`, `ud2`, `hlt` and `int3` in the text and in the decoded code, in llc's object and in the linked binary of amd64, and `brk`, `udf`, `hlt` and `dcps` on arm64, in the text and as words of the assembled object. arm64 has no check of the linked binary yet. `debugtrap` and `ubsantrap` stop the pass, and so does a trap in a register-entry leaf, which has no shadow pointer to call `host_trap` with.

Not covered, as in a program written in C: a write through a bad pointer to memory that is mapped changes that memory and nothing tells; a loop that never ends runs until the host interrupts it (`host_poll` is not inserted yet); the runtime ends the process when a goroutine stack passes 1 GB, which the counted depths keep the engine from; and the system may kill the process for memory.

Turning on `SetPanicOnFault` takes two calls of the runtime, 3.5 ns at each entry from Go into the engine (an entry and its `Leave` go from 2.5 to 6.0 ns, and a script that does next to nothing, 1.5 µs, takes 10 ns more), and an entry from a callback inside the engine takes nothing. The scripts of the speed set take 0.3 to 0.8 s and enter the engine a few times, so it cannot be seen there. It sits in `Enter` and not where a pool lends a VM because the setting belongs to the goroutine, and a VM may be lent to a different goroutine each time. `TestFault*` in [testing.md](../testing.md#the-go-host-of-the-generated-engine) run each failure on the real engine.

## Atomics without threads

`Atomics.wait` converts its arguments in the order the specification gives and then throws `TypeError: cannot block in this thread`. `Atomics.notify` converts its arguments and returns 0. test262 gives the same 58 known errors as before with 66 tests excluded in `engine/test/test262.conf`, all of `built-ins/Atomics/wait` and `notify`: 7 wait on the main thread for a time out, and 59 start agents with `$262.agent.safeBroadcast`. That function begins with an `Atomics.wait` on a value that differs, which must return at once and now throws. In 53 of the 59 an agent also waits for a wake up or a time out. In 6 nobody waits and only that probe keeps them out. `api-test.c` keeps what those 6 say that still holds: `Atomics.notify` gives 0 when nobody waits, and `Atomics.wait` converts its arguments in the order of the specification (the array and its shared buffer, the index, the value, the timeout) and throws what a conversion throws before it throws that it cannot block. It also checks that a wait with a value that differs, or with no timeout, throws the same.

`Atomics.pause` is the one function of `Atomics` that is a hint and not an operation. It used to run `pause` (x86) or `yield` (arm64) as inline assembly, which the generator cannot take, so it was the last function the generator had to stub. ecma262 has an engine send the hint only if its platform supports signaling the CPU, so the function now does nothing. Its argument is still checked: undefined or an integral Number, else a `TypeError`. The test262 the tree is pinned to tests that (`non-integral-iterationnumber-throws.js`), but ecma262 dropped the argument in June 2026 (pull request 3847) and test262 stopped testing it a few weeks later (pull request 5075), so the check can go when the pin moves.

## When upstream changes it

Nothing here follows upstream: `engine/` is a copy that changes on its own. A release of QuickJS is taken into `lib/` as [upgrading.md](../upgrading.md) says, and into `engine/` by hand.
