# Regular expressions

The engine compiles a regexp to bytecode and runs it in a backtracking machine. The first two changes here are in `lib/regexskip.go`, the cache of compiled regexps in `lib/regexcache.go`. These three change only the generated Go, through `internal/fixlib`, with no C form. The change to the classes of regexps with the v flag is a fix of the parser, with a C form in `lib/internal/patch/quickjs.diff`.

## Skip to where a regexp can match

Release: v0.26.15.

A regexp that is not sticky no longer tries every position of the string in the backtracking machine. Its bytecode starts with a loop that tries the match at one position, steps over one character and tries again. `lre_exec` now first calls `lreSkip` (`lib/regexskip.go`): when the regexp starts with one character or one class of characters, such as `/["&<>]/` or `/\d+/`, it finds the first position that holds one in a plain Go loop and starts there, and when there is none it answers no match without running the bytecode. A regexp that starts with `^` outside multiline mode is run at position 0 only. Unicode regexps (`u`, `v`), regexps that ignore case or are multiline (`i`, `m`), and every other first op took the old path, until the change for [alternatives](#alternatives-that-cannot-match-are-not-pushed). `lreSkip` checks for an interrupt after every 65,536 characters it looks at, as the backtracking machine does every 10,000 steps, so the eval timeout and `Interrupt` stop a regexp that runs again and again on a long string as before. A server render of a page of tifa's example shop takes about 3% less time on linux/amd64 (AMD EPYC), with the same HTML. `fixlib` puts the call into all 5 files, and checks the text of `lre_compile`, `lre_exec` and `lre_exec_backtrack`, whose bytecode and ops `lreSkip` reads, against fingerprints. This changes only the generated Go, with no C hunk (`internal/fixlib/regexskip.go`).

Tests: `lib/regexskip_test.go`, whose `testdata/regex.txt` holds what 61 regexps give on 47 strings through every API that runs one, from the engine before the change, `internal/fixlib/regexskip_test.go`, and `TestRegexScanStops` in `timeout_test.go`.

The C tree (`engine/libregexp.c`) has the same change in C: `lre_skip`, `lre_first_set`, `lre_find` and `lre_run`, called by `lre_exec`. A char at the start of a regexp is found in an 8-bit string with `memchr`. `lre_first_set` walks the ways of the splits with a list of its own instead of recursion, which gives the same set and the same budget. `engine/test/compare.sh` runs `testdata/regex.js`, `regexsplit.js`, `regexpv.js`, `shikire.js` and `engine/test/compare/regexskip.js` (strings longer than a chunk, 8-bit and 16-bit, alternations past both budgets) on it and on the Go engine.

### When upstream changes it

What to do when `go run ./internal/fixlib` stops on this change after an upstream release. [upgrading.md](../upgrading.md) has the whole procedure and the order in which to update the lists `fixlib` checks against.

If it reports that `Xlre_compile`, `Xlre_exec`, `_lre_exec_backtrack`, `Xlre_canonicalize` or `_lre_case_folding_entry` changed (a fingerprint other than the one in `internal/fixlib/regexsites.go`), read the new code against `lib/regexskip.go`: the loop and `save_start 0` at the start of the bytecode, the header fields it reads, the size and the meaning of every op `lreFirstSet` follows, what the character and class ops match at a position and how `GET_CHAR` reads it (`lreSplit`), that the split ops only push a state, that a failed match at one position undoes its captures down to the loop (`lreRun`), that `lre_canonicalize` gives an ASCII result outside unicode mode only for ASCII units, that `lre_poll_timeout` counts one step and returns non-zero when the machine must stop (`lreRun` and the split ops call it), and `lre_exec` must still return `LRE_RET_TIMEOUT` when `lre_check_timeout` asks it to stop. Then put the new fingerprints in (`go run ./internal/fixlib -regex` prints them, even while the table is wrong) and run `go test -run 'Regex|Canonicalize' ./lib`. If it reports that it cannot find the handler of the split ops, its push or the jump to the next op, update the patterns `reRegexSplit`, `reRegexSplitPush` and `reRegexNext` in `internal/fixlib/regexskip.go` after reading the new handler.

## Alternatives that cannot match are not pushed

Release: v0.26.17.

A regexp of alternatives no longer tries each alternative that cannot match at a position. An alternation such as `(red|blue|...)` compiles to a chain of split ops, each pushing a state for the next alternative before the machine tries one, so at every position of the string the machine pushed and popped a state for each alternative, which for the 148 color names react-spring tests its values against (`new RegExp('(' + names.join('|') + ')(?!\\w)', 'g')`) was 147 states per position. Two changes, both in `lib/regexskip.go`:

- The split ops of `lre_exec_backtrack` ask `lreSplit` first whether the way they push can start at the position: when it begins with a character or a class of characters, after nothing but saves of captures, and the character at the position does not match it, the way would fail as soon as it is popped, and nothing is pushed. When the way the machine takes is another split op, as in an alternation, `lreSplit` goes on with that one in the same call, for up to 4096 split ops, after which it gives back the one it is at to be pushed as usual. It reads the character as the machine does and tests it as the op does, with the same `lre_canonicalize` for a regexp that ignores case, so this holds for every regexp and flag, lookbehinds and sticky regexps included.
- `lreSkip` knows more first ops. `lreFirstSet` follows the bytecode from the start of the regexp through both ways of every split, over saves and assertions (`^`, `$`, `\b`, lookaheads and lookbehinds, to the op after them), up to the first op on each path that reads a character, and collects the characters a match can start with: a set of the 256 Latin-1 units and one bit for all others. It gives up, and the regexp takes the old path, when a path can reach the end without reading a character (the regexp can match the empty string), at a jump back, at an op it does not know (`.`, `\s`, a back reference, a class that ignores case, ...), and after 1024 ops. A character that ignores case counts as itself and its lower case when it is ASCII: outside unicode mode `lre_canonicalize` gives no other unit an ASCII canonical form (`TestCanonicalizeASCII` checks every unit). Regexps that ignore case or are multiline now take this path too. `lre_exec` then calls `lreRun` in place of the machine: it tries the match at the first position that can start one, without the loop over positions at the start of the bytecode, and when that fails, finds the next such position in Go and tries again, for the regexps of `lreSkip` that start with one character or class too. That is what the loop does: it tries each position in turn, from the captures as they were before the loop, all cleared, which `lreRun` clears again before each try. It polls the interrupt counter of the machine after each failed try and checks for an interrupt every 65,536 characters it looks at.

Why this is safe: a state that is not pushed is one that would have been popped only to fail at its first character, after saves the machine undoes when it fails, and a position that is skipped is one where no path of the regexp can read its character. Results, captures, `lastIndex` and the errors a regexp throws are the same. The machine counts a step toward its interrupt check, and checks, at each `goto`, each loop and each failed pop, and a greedy `x+` jumps back by a split op, so over a long string it counted only through the pops of the states it pushed. A split op that pushes nothing therefore counts a step and checks itself, and one long match still stops when the eval timeout fires or `Interrupt` is called. What differs is how many steps are counted: one for each call of `lreSplit` that pushes nothing, however many splits it stepped over, where the machine counted one for each state it popped. So an interrupt stops a match after a different number of ops. And states not pushed take no room on the backtracking stack, so a regexp near the memory limit can go on where it ran out of memory.

`BenchmarkRegexColors` times a `replace` with the react-spring regexp of color names: on linux/amd64 (AMD EPYC, one core) it takes 5.9 µs where it took 44.5 on a value with no color name, and 8.5 µs where it took 20.2 on one with a name (the medians of 10 runs). Without PGO, with the same HTML and the same memory of a VM, a render of tifa's example shop takes about 1% to 2.5% less time, and the MUI pages of tifa's test apps about 3% to 5% less. The medians of 10 rounds against `a84c8ed`, before the split ops counted their steps toward the interrupt check, were 0.989 for the shop (0.981 to 1.015 over the rounds) and 0.946 to 0.954 for the MUI pages, and two runs against `80261af` gave 0.983 and 0.987 for the shop and 0.947 to 0.965 for the MUI pages. With the steps counted, two runs of 3 rounds against `de42e83` gave 0.983 and 0.975 for the shop and 0.962 to 0.993 for the MUI pages. The bench pages moved by less than their noise (table varies by 10% between rounds by itself). Other work ran on other cores of the machine during the rounds (a load average of up to 6). Each figure is from one build of each side: where the code sits moves a render by up to 2.4% (see [One TLS frame per call on linux](calls-and-tls-frames.md#one-tls-frame-per-call-on-linux)).

`fixlib` puts the question to `lreSplit` into the handler of the split ops in all 5 files, after it finds that the handler pushes the way it computes and jumps to the next op, and pins `lre_canonicalize`, `lre_case_folding_entry` and `lre_poll_timeout` beside the functions `regexSites` pinned already. This changes only the generated Go, with no C hunk (`internal/fixlib/regexskip.go`).

Tests: `lib/regexskip_test.go`, whose `testdata/regexsplit.txt` holds what Node gives for 84 regexps on 73 strings through every API that runs one (the engine before the change gives the same), with `testdata/regex.txt` as before, `lib/regexskip_memgrind_test.go`, `internal/fixlib/regexskip_test.go`, and `TestRegexScanStops` and `TestRegexMatchStops` in `timeout_test.go`, which stop regexps that try every position, and single long matches.

The C tree (`engine/libregexp.c`) has the same change in C: the split ops of `lre_exec_backtrack` call `lre_split`, with the same ops, budget and interrupt step.

## Compiled regexps kept per VM

Release: v0.27.0.

A VM keeps the bytecode of the regexps it compiled. Code that makes a new `RegExp` of the same pattern on every call compiled it every time: a syntax highlighter made anew for each render, as react-markdown makes one, compiles the regexps of its grammar again on each page. Now `js_compile_regexp`, which compiles every regexp (a literal when the parser meets it, `new RegExp`, `RegExp`, `RegExp.prototype.compile`, and the copy `split` and the other built-ins make of a regexp with new flags), first looks the pattern and the flags up in a cache of the runtime, and keeps there what it compiled (`lib/regexcache.go`).

Why this is safe: the bytecode is a string the engine never changes once `lre_compile` wrote it, and `lastIndex` is a property of each object, so objects made from the cache share it, as the objects of one literal and `new RegExp(re)` already did. Only a pattern that is a flat string, with flags that are undefined or a flat string, is looked up and kept: converting anything else can run a script or allocate, which `js_compile_regexp` does before it compiles, and a rope (a string made of others and not yet flattened) is converted too. A compile that fails is not kept, so a pattern that throws a `SyntaxError` throws it every time. What differs: a hit can succeed where compiling again would fail, for lack of memory or of stack.

The cache keeps at most 256 regexps in 1 MiB, counting each entry, its pattern, flags and bytecode, and lets go of the one used least recently first. Its table of hash chains is not in those bytes: it has one pointer for each entry that fits in them, at most 65,536 (512 KiB on 64-bit targets), however many entries the limit allows, and counts against the memory limit of the VM. With the defaults it takes 2 KiB. The limits come from the pages measured: the journal post of tifa's example shop that highlights CSS compiles 392 regexps per render, 162 of them different, which take 714 KiB, so they fit with room to spare. The other pages of the shop and of an app built on MUI compile at most 83 per render, of at most 11 patterns, in under 15 KiB. In `lib`, `JS_SetRegExpCache(rt, n, bytes)` changes the limits, 0 and 0 turning it off. A new VM keeps `DefaultRegExpCache` regexps in `DefaultRegExpCacheBytes`, and [`VM.SetRegExpCache`](go-api.md#setregexpcache-and-defaultregexpcache) changes it. `JS_FreeRuntime` lets every entry go first.

Memory: the entries are kept in C memory, in the state of the runtime next to the [shape cache](objects-and-shapes.md#kept-shapes), so they count against the memory limit of the VM. They are not let go when an allocation fails: freeing a string can free an atom, and the allocation that fails can be one in the middle of growing the atom table. So a script that runs close to its memory limit can run out of memory with the cache on where it would not without it: give such a VM a smaller cache, or none. One VM of the shop holds 12 KiB more after a GC (12.84 MiB rather than 12.83, measured with tifa's `TestShopVMMemory`), and a VM that rendered the CSS post holds the 714 KiB of its 162 regexps.

Without PGO, on linux/amd64 (AMD EPYC 7B13, one core), against `ff35232` (the engine of v0.26.17), the CSS post renders in 0.893 of the time: the median of 6 rounds in 3 code layouts, 0.841 to 0.903 over them. The other pages, which compile no regexp after their first render, render in the same time: 1.003 for the shop, 1.000 for the other store pages and 0.999 for the MUI pages, inside the 1% by which the code layout moves a render. The HTML is the same.

`fixlib` puts the lookup and the store into `js_compile_regexp` and the release into `JS_FreeRuntime` in all 5 files, and pins the text of `js_compile_regexp` and of the functions the cache hashes, compares, counts and frees strings with. This changes only the generated Go, with no C hunk (`internal/fixlib/regexcache.go`).

Tests: `lib/regexcache_test.go`, whose `testdata/regexcache.txt` is what Node 24 prints for `testdata/regexcache.js` (patterns and flags of every kind, `v`, named groups, `d`, errors, made again through every way that compiles a regexp and used on their own, with the cache at its defaults, at four entries and off), the sharing of bytecode, a pattern that is an object whose `toString` is called every time, the LRU by count and by bytes, the size of the table for limits up to `math.MaxInt32` entries, a regexp that outlives its entry and a GC, the memory the cache counts, out of memory at every limit, and 8 runtimes on 8 goroutines. Also `lib/regexcache_memgrind_test.go` (no C memory left behind), `regexcache_test.go` (the memory limit, `SetRegExpCache`, and the timeout and `Interrupt` in loops that make regexps) and `internal/fixlib/regexcache_test.go`.

The C tree (`engine/quickjs.c`) has the same cache in C: the field `regexp_cache` of `JSRuntime`, `js_regexp_cache_get` and `js_regexp_cache_put` in `js_compile_regexp`, `JS_SetRegExpCache(rt, n, bytes)` and the defaults `JS_REGEXP_CACHE_ENTRIES` and `JS_REGEXP_CACHE_BYTES` in `quickjs.h`, and `JS_FreeRuntime` lets every entry go. `engine/test/compare.sh` runs `testdata/regexcache.js` on it and on the Go engine, and `engine/test/unit.c` checks that regexps of the same pattern share their bytecode only with the cache on. It also checks the limits of entries and of bytes, that setting them lets every entry go, that a regexp works once the cache let its bytecode go, that the cache works after allocations that fail in turn, and that it outlives the context that filled it.

### When upstream changes it

If `fixlib` reports that a function of `regexCacheFuncs` changed (a fingerprint other than the one in `internal/fixlib/regexcachesites.go`), read the new code against `lib/regexcache.go`: `js_compile_regexp` must still only read a pattern and flags that are flat strings, return the bytecode as a new 8-bit string and not change it after, and every other return must still be of an exception. `hash_string`, `js_string_compare` and `js_string_memcmp` must still read a string as the cache hashes and compares it, `js_free_string` and the reference count (`js_rc`) must still free a string as the cache frees its entries, and `js_malloc_usable_size_rt` must still give the size the memory limit counts. Then put the new fingerprints in (`go run ./internal/fixlib -recache` prints them, even while the table is wrong) and run `go test -vet=off -run 'RegexCache|RegExpCache' ./lib .`. If it reports that the bytecode is not returned at the end of `js_compile_regexp`, or that it has another number of returns of `ret`, read the new end of the function and teach `addRegexCache` where the bytecode is made.

## Classes of regexps with the v flag

Release: Unreleased.

The parser reads a class of a regexp with the v flag (unicodeSets) as the specification does. It threw a SyntaxError for three things the specification allows and Node accepts:

- In a class, `\` before one of ``& ! # % , : ; < = > @ ` ~`` (a ClassSetReservedPunctuator) is that character, as in `[\&\;]` or `[\!\|]`. `get_class_atom` took `\-` already, and threw "invalid escape sequence" for the others. Outside a class, and in a class of a regexp with the u flag, these escapes stay a SyntaxError, as the specification says.
- `get_class_atom` also reads a character outside a class, and checked it as in a class: a doubled punctuator such as `&&`, and `( ) [ ] { } / - |`, threw there too, so `/-/v`, `/a&&b/v` and `new RegExp('/', 'v')` did not compile. This is upstream's commit a479eff ("fixed regexp unicode set parsing", after the release this fork follows), which checks them only in a class.
- `\q{...}` read its characters as outside a class. With a479eff alone, `\q{(}`, `\q{-}` and `\q{&&}` would then compile, which Node rejects. It reads them as in a class instead, which also lets `\q{\-}` and `\q{\&}` compile.

shiki's JavaScript engine, which shiki offers in place of its Oniguruma engine where there is no WebAssembly, as in this engine, turns the grammars it highlights with into regexps with the v flag full of such escapes: of the 552 regexps it makes for its grammars of bash, css, go, html, json, typescript and yaml, the engine threw for 204. Now it compiles all of them but 3, which have more capture groups than a regexp can hold (see [At most 254 capture groups](#at-most-254-capture-groups)).

Why this is safe: a pattern that compiled before compiles to the same bytecode. Only patterns that threw now compile, and only those the specification allows, as `TestRegexpVSemantics` checks against Node for every punctuator escaped and not, in and out of classes and `\q{}`, with the v flag, the u flag and neither. A native build of the patched C gives the same transcripts as Node.

The change is in C, in `lib/internal/patch/quickjs.diff`, and `fixlib` makes its Go form in all 5 files: it puts the test of the punctuators before the switch over the character after `\` in `_get_class_atom`, adds `inclass != 0` to the two tests of a v regexp there, and passes `TRUE` for `inclass` in `_parse_class_string_disjunction`. It pins the text of `get_class_atom`, `parse_class_string_disjunction` and `lre_parse_escape`, which reads every other escape (`internal/fixlib/classescape.go`).

Tests: `lib/regexpv_test.go`. `TestRegexpVSemantics` compares `testdata/regexpv.txt`, what Node prints for `testdata/regexpv.js`, line by line. `TestRegexpShiki` compiles the regexps of shiki in `testdata/shiki/regexps.json`, which `testdata/shiki/record.mjs` recorded while shiki 4.5.0 highlighted `testdata/shiki/input.md`, and runs each from every position of every line of that input: `testdata/shikire.txt` is what Node prints. `internal/fixlib/classescape_test.go` checks that `fixClassEscapes` makes its change once, takes it out and puts it back the same, and stops on a changed function.

### When upstream changes it

If `fixlib` reports that `get_class_atom`, `parse_class_string_disjunction` or `lre_parse_escape` changed (a fingerprint other than the one in `internal/fixlib/classescapesites.go`), read the new code against the three parts above. A release with upstream's commit a479eff has `inclass &&` in the two tests already: drop that part of `fixClassEscapes` and of the C hunk, keep the other two, and check that `\q{(}` still throws. Then put the new fingerprints in (`go run ./internal/fixlib -classescape` prints them) and run `go test -run 'RegexpV|RegexpShiki' ./lib` and `go test -run ClassEscapes ./internal/fixlib`.

## At most 254 capture groups

A regexp holds at most 254 capture groups, as in upstream QuickJS and QuickJS-NG, and throws `SyntaxError: too many captures` past that. V8 allows 32,767. shiki's JavaScript engine makes three regexps with more, for its grammars of typescript (551 and 555 groups) and html (912), so those two grammars still fail to highlight in this engine.

The limit stays, as raising it changes the format of the bytecode of every regexp. The bytecode keeps the index of a group in one byte: in the ops that save where a group starts and ends, in the op that clears groups before a quantifier repeats, in the list of groups of a back reference, and in the header, which holds the count. Two bytes for each costs 2 bytes more for each group, 2 for each clearing op and 1 for each group of a back reference, and the header grows by 2. A match takes 16 bytes of heap for each group, for the array of where groups start and end, and the backtracking stack saves a group only when the match changes it, so no stack grows with the number of groups. A native build of the C with two-byte indices and a limit of 32,767 gives Node's transcripts, highlights the code of `testdata/shiki/input.md` with shiki as Node does, typescript and html included, and runs regexps with and without groups in the same time within the noise. The cost is the Go form: 10 functions of the generated files (`re_parse_captures`, `find_group_name`, `re_need_check_adv_and_capture_init`, `re_parse_term`, `compute_register_count`, `lre_compile`, `lre_exec_backtrack`, `lre_exec`, `lre_get_alloc_count` and `lre_get_capture_count`), in all 5 files and pinned by `fixlib`, the header constants, the table of op sizes, `BC_VERSION` (bytecode saved by an older engine holds regexps of the old format), and `lib/regexskip.go`, which reads the header and the sizes of the save ops. tifa's pages do not run shiki when they render: the journal of its example shop highlights with highlight.js, whose regexps the engine compiles.
