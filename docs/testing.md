# Testing and verification

## Before committing

Every change must pass:

```sh
go build ./...
gofmt -l -s . | grep -v -e '^internal/cengine/engine_'   # prints nothing
go vet -asmdecl=false ./...
scripts/docs-list.sh --check           # every doc has a summary
go test -count=1 -p 1 .                # about a minute
```

- `go vet` leaves out `-asmdecl`, which reports the generated assembly (a return it does not see written, a function with no Go declaration). The generator and the tests of `internal/cengine` check the declarations of that assembly instead.
- A change to the C of `engine/`, to the generator or to the flags of `scripts/gen-engine.sh` also makes the generated engine again, in the same commit (`make gen`, `make gen ARCH=arm64`), and runs `make check-fast`. At the end of a batch it runs `make check-full` (see [Generate and check](#generate-and-check)).
- A change to `intl/` also runs `go test ./intl` (the golden test is part of it).
- A change to `internal/gointl` also runs `go test ./internal/gointl/...` and `make gointl`.
- A change to `compare/engines` also runs `go test ./cmd/... ./internal/... ./tifa` there. It is a module of its own, so the commands above do not reach it and CI does not run it. The tests cover the helper tools (the far-behind list, the page tables and archive, the module-to-script tool, the notices generator) and the shell scripts of `tifa/` with stand-ins.
- A change to `temporal/` also runs `go test ./temporal` without `-short` (the Chromium comparison and the link test are part of it), and the Temporal lines of the focused checks and the race detector section.
- A change to the engine also runs the [focused checks](#focused-checks) of what it touches, and [test262](#test262).
- `-p 1` runs one package at a time: the tests of the root package start many VMs, and each VM maps its own memory.

New behavior and bugs with a known cause: write the test first, see it fail, then write the fix. A change to the engine is tested in `engine/test/` (a script with its recorded output, or a check in C, see [The C tree and its native test host](#the-c-tree-and-its-native-test-host)) and in the root package (through the Go API).

## Tests that skip without their tools

The tests of the generator in `internal/goasm/gen` need LLVM and skip (and still pass) when it is not given, so `go test ./internal/goasm/gen` on its own checks only the rules. Set these three variables to run all of them:

```sh
export SLOWJS_LLVM=/usr/lib/llvm-22/bin                          # LLVM 22.1.8 bin directory (clang, opt, llc)
export SLOWJS_SHADOW_PASS=$PWD/internal/goasm/gen/internal/_shadow.so   # the built pass, made by internal/goasm/gen/proto.sh
export SLOWJS_LLD=/usr/lib/llvm-22/bin/ld.lld                    # the linker (GNU ld, /usr/bin/ld, also works on linux)
go test -p 2 -timeout 30m ./internal/goasm/gen/...
```

With only `SLOWJS_LLVM` and `SLOWJS_SHADOW_PASS`, the tests that need `ld.lld` (`TestVarargsNative`, `TestSampleRuns`, `TestNarrowArgs`) still skip. A skipped test prints `--- SKIP` with the names of the variables it wants: run with `-v` and look for it before you trust a green run. `SLOWJS_QEMU_AARCH64` (optional) names an emulator that lets the arm64 cases run on an amd64 host.

`go test -race` needs `CGO_ENABLED=1` and a C compiler, as the race runtime is linked through cgo. This repository builds with `CGO_ENABLED=0`, so set it for the command only: `CGO_ENABLED=1 go test -race ...`. Every `-race` command in this doc is meant this way.

## Focused checks

The recorded outputs, the sanitizers and the checks in C are in [The C tree and its native test host](#the-c-tree-and-its-native-test-host). These are the checks of the Go side, by name:

```sh
go test -short -timeout 30m ./...                        # all packages
go test -run 'TestErrorStack' .                          # stack text and memory of lazy error stacks
go test -run 'CallDepth|ShadowStack|StackGrowth|CallAllocs' .  # depth limits, shadow stack use, deep recursion while Go moves the stack, no Go allocation per call
go test -run 'HostPanic|Handover|Clock' .                # a panic or Goexit in a Go function or a clock, a VM handed to another goroutine
go test -run 'Interrupt|Killed' .                        # Interrupt, and the kill of a script that does not stop
go test -run 'Regex(Scan|Match)Stops' .                  # a timeout stops a regexp on a long string
go test -run 'RegExpCacheStops|BuiltinWorkStops|StringSearchStops' . # a timeout stops loops of regexp compiles, parsing, string building and searches within 50ms
go test -run 'AtomKeys|FieldChain|OwnKeys' .             # keys and property reads give what Node gives (testdata/*.golden)
go test -run 'ShapeCache|RegExpCache' .                  # the shape cache and the regexp cache give what Node gives and keep to their limits
go test -run 'YoungGC|Ephemeron' .                       # the young collection and WeakMap ephemerons
go test -run 'SharedBytecode' .                          # one copy of source text and line tables for every VM
go test -run 'RunGC|GCThreshold|GCAfterClose' .          # RunGC, MemorySize and GCThreshold (gc_test.go)
go test -run OnClose .                                   # OnClose runs once, in order, and keeps no VM alive
go test -run 'Close(Twice|CallbackPanics)' .             # Close again does nothing, and a panicking OnClose function keeps no other step from running
go test -tags testhooks -run 'CloseUnmap|CloseSharedDrop|MapRefused|ReleaseRefused|RemapRefused' . # Close again frees what the OS refused to unmap, and a refused map ends the call with out of memory
go test -run 'SameAsEngine|UTF8Units|BuiltinStringRoundTrip|BuiltinLatin1UTF16|EscapeView' . # strings of Builtins converted in Go give what the engine gives
go test -p 2 -run 'VMClock|MonoNow' .                    # VM.SetClock: Date, Intl and Temporal share one clock, reset, Close and timeouts
go test -tags testhooks ./internal/cengine ./internal/gohost ./internal/hostmem ./internal/idtable # the generated engine's host, with the test hooks
HOSTMEM_RESIDENCY=1 go test -run StackResidency ./internal/hostmem # exact counts of shadow stack pages in memory, a snapshot the system can change
go test -p 2 ./temporal -run 'DateTimeFormatTemporal|DurationLocaleString|Chromium' # Temporal formatting against Chromium 156
go test -p 2 ./intl -run 'GoIntlMigration|EmbeddedZonePack|FormatStringMatchesParts' # rounding, calendars and embedded time zones
go test -p 2 ./internal/intlhook                        # private state across GC and Close
go test -run LinksOnlyReadData ./temporal               # the packs a program with Temporal links
go test -run QJSTZVersion ./internal/gointl              # tz.bin holds the zones of the update qjstz names
internal/gointl/qjs-sync.sh pack -check                  # shared Intl data is what the generator makes
go test -run '^$' -bench Call .                          # the cost of each kind of call
go test -run '^$' -bench RegexColors .                   # the cost of a replace with react-spring's color names
go test -run '^$' -bench Clock .                         # the cost of Date.now and new Date()
```

Each doc under [changes](changes/README.md) names the tests of its changes.

## test262

test262 runs on the C tree with the native test host, `engine/test/test262.sh` (see the next section):

```sh
engine/test/build.sh plain
engine/test/test262.sh -m plain -T 2      # about 1.5 minutes
```

- `engine/test/test262_errors.txt` lists the 58 tests known to fail, one line each (the file, the line and the error). The script compares the errors it found with that list, line by line, and fails on any difference. A change to the engine must leave the same 58 errors.
- The runner is `engine/test/run-test262.c`, upstream QuickJS's runner with a few changes. The configuration is `engine/test/test262.conf` and the patch to test262 is `engine/test/test262.diff`.
- The Go API and the Go host are not run on test262. What they add is tested by the Go tests of the root package, and what crosses between Go and the engine by the tests of `internal/cengine`.

## The C tree and its native test host

`engine/` is the C tree of the engine. `engine/test/` is its native test host: the C tree built with its own small libc (`engine/libc`, see its [README](../engine/libc/README.md)) by plain clang, and test262 run on it. It tests the C itself, with no Go in the way. It is a tool for testing, never part of a Go build or of the product, and `engine/` holds no Go file (`TestRepositoryLayout` in the root package fails if it does, or if a folder with Go files holds a C file).

```sh
engine/test/build.sh asan              # plain (default), asan, asan-heap, asan-heap-iter, ubsan or asan-ubsan: engine/test/out/MODE/run-test262
engine/test/test262.sh -m asan -T 2    # test262 on that build, with 2 runner threads
engine/test/libc-test.sh               # the string functions and snprintf of engine/libc against the system's, and vsnprintf against the generator's table of formats
engine/test/api-test.sh asan           # JS_DumpMemoryUsage, JS_NewClassID, abort and the limit of a resize, on real runtimes
engine/test/host-test.sh tsan          # the test host alone: threads making and freeing runtimes, stops asked from another thread
engine/test/math.sh                    # Math.* and the libm functions against the hashes kept in engine/test/math, bit for bit
engine/test/check-symbols.sh           # what the engine uses and does not define
engine/test/cycles.sh                  # the recursions no counted depth bounds yet, against cycles.txt
engine/libc/vendor.sh --verify         # the files taken from musl are the ones in MUSL.sha256
go test ./internal/goasm/cmd/cycles      # the checks of the cycles tool
```

It builds and runs on Linux and on macOS (Apple clang 15 and later)..

- The engine and `engine/libc` are built freestanding, with `-nostdinc` and only `engine/libc` for headers (the flags are in `flags.sh`, which `build.sh`, `check-symbols.sh`, `cycles.sh`, `libc-test.sh` and the generator of `internal/goasm/gen` all read, so that what is built and what is checked cannot differ). The host, the test runner and the test programs use the system's headers and libc. The engine does not link the system's libm: `Math.*` is musl's, so its results are the same on every machine.
- `run-test262.c` is upstream's runner with a few changes (see its header): it includes `host.h`, makes its runtimes with `host_new_runtime()` and frees them with `host_free_runtime()`, prints the memory report through a buffer, keeps 2048 shapes in each test as a VM of the Go API does, and no longer calls `JS_SetCanBlock`. `host.c` copies the three functions the runner takes from `quickjs-libc.c`, interrupts a test that runs over 120 seconds, which the runner cannot do (a thread of the host asks such a runtime to stop, and the engine's thread sets its interrupt flag at its next `host_poll`, see [c-engine.md](changes/c-engine.md#polls-and-interrupts)), and implements the callbacks of `engine/host.h`. It also defines `__shadow_remaining`, the bytes of stack left, from the stack of its thread: the engine counts its recursion and asks for that only to bound an alloca and keep a margin (see [c-engine.md](changes/c-engine.md#depth-of-calls-and-of-c-recursion)). The runner's threads, and those of `jsrun` and of the depth tests of `unit`, have stacks of 512 MiB (`HOST_THREAD_STACK`, only reserved until used), so that a recursion to the deepest limits never runs off one.
- `host.c` also gives the memory of the allocator (see [allocator.md](allocator.md)): `host_memory_grow` maps each chunk of a runtime, and `host_free_runtime` unmaps them after `JS_FreeRuntime`. A runtime that still has blocks in use then is a leak: the process exits with status 87, which `test262.sh` reports as a failure. `HOST_MAX_MEMORY=BYTES` makes the host refuse a runtime more memory than that, as a system without memory would. `HOST_TIMEOUT_SEC=N` changes the 120 seconds a runtime may run, 0 for no limit (`render` sets 0). The host also answers the two memory kinds of `host_call` (a dedicated chunk goes back, or is remapped). On linux it tells the engine it can remap (`JS_SetHostRemap`), and `HOST_NO_REMAP=1` leaves that out, so that a dedicated block that outgrows its chunk gets a new chunk and a copy: `staging/sm/String/replace-math.js`, a string of 1 GiB grown by realloc, takes 1.05 GB and 1.2 seconds with remap, 2.0 GB and 4.5 seconds without.
- Time is fixed. `host_now` answers 2026-01-01T00:00:00Z for the wall clock, which fixes `Date` and the seed of `Math.random`. A few tests wait for the clock to move, such as `language/expressions/dynamic-import/await-import-evaluation.js`, and never end on a fixed one, so `test262.sh` sets `HOST_CLOCK=running`: the time starts at the same instant and passes. A test sets the wall clock of its thread to a time of its own (a negative one is before 1970) with `host_set_wall`, and `host_poll_reads` and `host_poll_stop_after` of `host.h` count the readings of the interrupt flag and set the flag at the nth one.
- `test262.sh` downloads the test262 archive it pins (or takes the copy `-z` names, checked against its SHA-256), applies `engine/test/test262.diff`, uses `engine/test/test262.conf` and runs `-a`. It writes the errors it found and compares them line by line with `engine/test/test262_errors.txt`. It exits 0 only when they are the same lines. The results are in `engine/test/out/test262-MODE/`: `run.log`, `test262_errors.txt` and `errors.diff`.
- `engine/test/test262.conf` is upstream's configuration with one addition, the tests under "no blocking Atomics" in its `[exclude]` section: 59 that start agents, and 7 that wait on the main thread for a time out. The engine has no threads, so `Atomics.wait` throws a `TypeError` and `Atomics.notify` wakes nobody. The 59 start their agents with `$262.agent.safeBroadcast` of `harness/atomicsHelper.js`, which begins with an `Atomics.wait` on a value that differs. It must return at once, and now throws. In 53 of the 59 an agent also waits for a wake up or a time out. In 6 nobody waits (`notify-with-no-agents-waiting.js`, `notify-with-no-matching-agents-waiting.js` and four `*-throws-agent.js` tests of `wait`), and only that probe keeps them out. Without the 59, the runner waits for ever for an agent that has ended.
- A full run (83426 tests, 3422 excluded) takes about 1.5 minutes in plain mode, 2.5 minutes under UndefinedBehaviorSanitizer and 11 minutes under AddressSanitizer, on 2 hyperthreads of one EPYC core. All give the 58 known errors with 2 threads. Sanitizer reports go to `run.log`. The AddressSanitizer build goes on after a report: run it with `ASAN_OPTIONS=halt_on_error=0:detect_leaks=1`. The UndefinedBehaviorSanitizer build always goes on: give it `UBSAN_OPTIONS=print_stacktrace=1`, and it reports each place once.
- `asan` gets every block from the system malloc (`JS_HEAP_SYSTEM_MALLOC`, `heap-system.c` in place of `heap.c` and `tlsf.c`), so that red zones and LeakSanitizer see each block alone. `asan-heap` keeps the engine's allocator and poisons what is free in it (`JS_HEAP_POISON`: free slots, free TLSF blocks, the rest of an arena, the blocks that wait in the caches), which finds a use after free inside our own memory. `poison-test.c` asks AddressSanitizer which bytes are poisoned, runs itself on a use after free of a cached large block to see that AddressSanitizer reports it, and says what the poison does not cover (see [allocator.md](allocator.md#testing)). Run both over test262.
- AddressSanitizer reports nothing over test262, leaks included. UndefinedBehaviorSanitizer reports one place, in QuickJS's own code: `js_typed_array_slice` adds an offset to a null pointer (`quickjs.c`, `slice_memcpy`). It used to report three more. A null source of length 0 passed to `memcpy` was one, because the system's header says the pointer is not null and `engine/libc/string.h` does not. The calls of `js_realloc_rt` by `dbuf_claim` and `dbuf_free` through the type `DynBufReallocFunc` (`cutils.c`) were the other two: a `DynBuf` now calls it through `js_dbuf_realloc_rt`, which has that type. Anything else in a report is new.
- `libc-test.sh` builds `engine/libc` with its functions renamed to `sl_NAME`, so that they sit in one program with the system's, and compares them on random inputs with fixed seeds: the string functions at every alignment and length up to 300, `memcpy` on its own at every size from 0 to 1100 bytes with the source and the destination each at 16 offsets from a multiple of 64 (the destination is filled with a byte no source byte has, so a byte written outside the range shows, and the source must not change) and at 300 random sizes up to 70000, then again with the source against a page that cannot be read, ending right before it and starting right after one, at every size to 1100 and 300 random sizes to 70000, so that a read past either end of the source faults, on amd64 and on arm64, and `snprintf` on every format the engine uses and many it does not, cut at every length from nothing to two past the end of the output, with a canary after the buffer. It also runs formats that must abort (floating point, `%n`, positional arguments, a length on `c`, `s`, `p` or `%`, a format that ends inside a conversion, numbers that do not fit an int, an output over INT_MAX) in a child process and checks that it died of SIGABRT, and not of a trap, and that it had taken no argument by then: `libc-test.sh` builds `stdio.c` with a `stdarg.h` that counts every `va_arg` (`engine/test/counting`), and formats like `%*ls`, `%.*f`, `%*2$d`, `%*%` and `%.*%` must be refused before the `*` takes its int. It also checks that a huge width with a small buffer costs nothing, and feeds every line of the generator's table of formats (`internal/goasm/gen/testdata/formats/cases.txt`, which `formats_test.go` holds to its checker) to `vsnprintf`: an `ok` format must return after taking exactly the arguments it names, and a `bad` one must die of SIGABRT. A format that the table and `stdio.c` do not agree on fails here. In this program `abort` is the system's. `api-test.c` checks the same for a few of them through the engine's own `abort` and the host. It takes MODE like `build.sh`.
- `api-test.sh` runs `api-test.c` on real runtimes. `JS_DumpMemoryUsage` is given a runtime that holds objects, so that the part that names classes runs, and its report is checked for its text, for its length when there is no buffer, and cut to every size from 0 to past the end, with a canary after the cut. Run it in asan mode: the first version wrote past a buffer on the stack, in the part that a call with no runtime does not reach. `JS_NewClassID` is checked with two runtimes taking IDs by turns, a repeated query, a preset ID, and the built-in classes, which keep their numbers. The averages of the report, with one decimal, are compared with `%.1f` of the C library for about 190000 pairs of numbers, 1.05, 0.15, 0.05, 2.45 and 1.25 among them (the report rounds the exact value once). `Atomics.notify` gives 0 when nobody waits, and `Atomics.wait` converts its arguments in the order of the specification and throws what they throw before it throws that it cannot block (the Symbol and the throwing `valueOf` for the index, the value and the timeout). `abort`, and a format `snprintf` does not do, must end the process with `SIGABRT` after the host has heard it. A resize meets the memory limit as upstream does (`count` + the new size - the usable size of the old block), to the byte, for growing in place, moving, a chunk of its own, shrinking and the same size, and a refused resize leaves the block and the count as they were.
- `host-test.sh` runs `host-test.c`, the test host (`host.c`) linked with stubs in place of the engine. A runtime that does not start must leave no VM and no chunk in the host, two threads that make and free runtimes must not race, and a stop asked from another thread (`host_interrupt`) or by the thread that ends long tests (after 1 second there) must set the interrupt flag at the next `host_poll` of the thread that runs the runtime, with no other thread writing the flag: `host-test.sh tsan` builds it with ThreadSanitizer, which `asan` and `ubsan` cannot replace. It takes MODE like `build.sh`.
- `math.sh` checks the math of the C tree against hashes kept in `engine/test/math`, bit for bit, in two ways, on inputs from the fixed generator of `mathcmp.js` (random bits, ranges of values, numbers near multiples of pi/2, every pair of edge values such as zeros, infinities, NaN, subnormals and the limits of `exp` for the functions of two arguments), 100000 for each function. Each file holds, for every function, the SHA-256 of the line of inputs and of the line of results.
  - Math as JavaScript sees it (`math/js.hashes`): `mathcmp.js` runs on the C tree (`mathdump`) for 33 operations. A NaN is written as the one NaN of JavaScript, so its sign and payload are not checked here. Not every operation reaches the libc function of its name: `Math.round` is the engine's own code, and a Uint8ClampedArray store and `Atomics.pause` use `lrint` and `modf` only for a conversion and a test.
  - The libc functions themselves (`math/libc.hashes`): `libmath` calls the 33 functions of `engine/libc` the engine uses (`round`, `modf` and `lrint` included). A NaN is taken as it is, and its sign is the machine's, so this is checked on x86-64 only.
  - The hashes were first recorded on linux/amd64 from the previous engine, and the C tree gives the same bits. `MATH_UPDATE=1 engine/test/math.sh` writes them again from the C tree, on x86-64, to be read before they go into a commit.
- `check-symbols.sh` builds the engine files and `engine/libc` freestanding at several optimization levels, with and without `NDEBUG`, and fails when they use a symbol that `engine/libc/symbols.txt` does not allow: only the libc functions, the callbacks of `engine/host.h` and `host_memory_grow`. The allocator is among the engine files (`heap.c`, `tlsf.c`), so there is no malloc on the list. Give it target triples to check other targets (`CC=clang NM=llvm-nm engine/test/check-symbols.sh x86_64-linux-gnu aarch64-linux-gnu`): the objects are only compiled, so it needs no cross toolchain. A failure of `nm` on an object ends the script, and it checks at the start that it rejects an unlisted symbol and an object it cannot read. It proves the symbol level only. It does not show that the machine code has no thread local storage, no system call instruction and no fixed address. Those checks come with the generator, not before.
- `cycles.sh` checks that the counted depths bound every recursion of the engine (see [c-engine.md](changes/c-engine.md#depth-of-calls-and-of-c-recursion)). It compiles the engine files to one module of LLVM IR with the flags of the generator, at -O0 so that every function of the source is there and every count is a call of its own, and with `-fsanitize=kcfi`, then `internal/goasm/cmd/cycles` builds the call graph: direct calls, and each indirect call joined to every function of its kcfi type whose address is taken, as the generator joins them. A function that counts a depth (`js_call_enter`, `js_internal_enter`, `js_internal_enter_rt`, `lre_depth_enter`, `js_nest_enter`) cuts the cycles through it. The cycles left must be those of `cycles.txt`, line for line, and it is empty: every recursion goes through a count. The tool also checks pairs of functions where the first must not reach the second by any path, counted or not (`noReach`), and prints a shortest path for each that does: making an error (`JS_ThrowError2`) reaches neither `JS_CallInternal` nor `JS_ThrowInterrupted`, nor a function that reads the interrupt flag (`js_poll_interrupts`, `lre_check_timeout`, `lre_poll_timeout`, `rqsort_stop`), a collection (`JS_RunGC`, `JS_RunYoungGC`) does not reach `JS_ThrowError2`, and `free_zero_refcount` starts no collection. The nesting of errors and of freeing is bounded on those. A function of a pair that the module does not define is an error, so a rename cannot turn a check off. The value printer is built only with `CONFIG_PRINT_VALUE`, which `build.sh` defines for the host and `cycles.sh` does not, as the generator does not. A new cycle fails the check, and so does a cycle that goes away without its line. It needs LLVM 22 (the folder of `clang` and `llvm-link` as its argument, `/usr/lib/llvm-22/bin` by default). The tests of `internal/goasm/cmd/cycles` (the `goasm` step of `check.sh` runs them) check that the tool finds a cycle through direct and typed indirect calls, that a count cuts it, and that it finds the path from one function to another through direct and typed indirect calls and through counts, as `noReach` needs.
- `vendor.sh --verify` checks that the files of `engine/libc` taken from musl are the ones `MUSL.sha256` lists, that none is missing or added, and that the patch is the recorded one. Given a musl checkout (`vendor.sh --verify MUSL_DIR`) it also checks the recorded hash of each file in musl and applies the patch to the original again.

### The Go host of the generated engine

`internal/gohost` answers the engine's callbacks (memory, clocks, poll, `host_call`), and its tests run on any machine without the engine. `internal/cengine` is where the generator writes the engine as Go assembly, next to the checked-in host files, which build only with. Generate it on the build machine, as in [internal/goasm/gen/README.md](../internal/goasm/gen/README.md), with `-out internal/cengine`, then:

```sh
go test -race -tags testhooks ./internal/gohost         # VMs by id and by shadow stack, chunks, release and remap, clocks, poll, abort, what is left when the OS refuses
go test -tags testhooks ./internal/cengine      # scripts on the engine: results, leaks, footprint, release and remap counts, Go heap, the shape cache, Close and New under panics and refusals, polls and Interrupt
go run ./internal/cengine/cmd/jsrun -n 10 -mem file.js   # one script, timed, on the C engine
go test -p 1 .                    # the tests of package slowjs on the C engine (linux/amd64, linux/arm64, darwin/arm64), lib-only tests left out by their tag
go run ./internal/cengine/cmd/jsrun -n 10 file.js                      # the same on package slowjs
go test -run 'TestShadowStack' -v .      # how far up its 32 MiB shadow stack a VM goes at depth limits of 5000 and 10000, and in C recursion
go test -tags testhooks -run 'TestMapRefused|TestReleaseRefused|TestRemapRefused' .   # the system refuses memory in the middle of a render
go test -run TestInterruptStopsLongBuiltins -v .   # long calls of built-ins stop soon after Interrupt, not by the kill
go run ./internal/cengine/cmd/interrupt -n 10       # time from Interrupt to the return of Eval, for the scripts of cmd/scenarios (also without the tag, for lib)
go run ./internal/cengine/cmd/gcpause -secs 10      # how long the Go GC waits to stop VMs that stay inside one operation, for the same scripts
```

The engine builds on linux/amd64 and darwin/arm64 only, and every other target gets `internal/unsupported`, whose error names the two. linux/arm64 is generated too (its qemu run is below) but no machine of its own has run it, so it is refused until one has. Generate arm64 on the linux/amd64 build machine with `-arch arm64 -mode pn`: the files of each architecture end in its name, so both sit in `internal/cengine` at once. The same arm64 package runs on a Mac (run the tests there as above) and on linux/arm64. With no arm64 Linux machine, cross-build the test binaries (`GOOS=linux GOARCH=arm64 go test -c -tags testhooks`) and run each under `qemu-aarch64` from its package folder, with three limits of the emulator: a test that starts the test binary again as a child (`TestExceptionConversionThrows`, `TestCloseRetry`, `TestCloseTwice`, `TestDateLocalTimeIsUTC`, `TestRegisterExistingName`) fails with "exec format error" unless binfmt runs it, `TestStackNoHugePages` fails as qemu does not pass `madvise(MADV_NOHUGEPAGE)` on, and `TestInterruptStopsLongBuiltins` fails there, killed after its 50 ms grace, while it passes on darwin/arm64 and linux/amd64: confirm it on arm64 hardware. Check the arm64 post-link on linux/amd64: build `GOOS=linux GOARCH=arm64 go test -c -tags goasmkeep ./internal/cengine` and pass it to the generator run with `-arch arm64` as `-verify-bin`.

To check that two builds of the engine print the same, run `internal/cengine/cmd/jsrun` built with each over the scripts of `engine/test/compare.sh` and compare the outputs file by file. The recorded outputs of `compare.sh` are the same on darwin/arm64 and linux/amd64.

A formal build of the engine passes `-release` to the generator: it stops on any stub, and refuses the switches made for surveys and tests (`-keep-going`, `-poison`, `GEN_KEEP_NARROW` and the others the README lists), so the package it writes has no `goasmMissing` stub. Until the last stub of the C is gone it stops on that one.

The generator writes the same package from the same C every time, byte for byte (`TestOutputReproducible` runs it with 1 and 4 compile jobs and compares every file).

`jsrun` times one call per run, the evaluation of the script with its jobs and the result as a string, and its `timed:` line says so. The source is already a string and the VM is made, collected, released and closed outside the time.

The tag `testhooks` turns on the hooks of these tests, which the normal build does not have: `hostmem.SetFault` makes calls to the OS fail, and `callbackHook` of `internal/cengine` stops the engine in a callback (with a count of engine teardowns beside it). Without the tag the code holds no check for them, so a normal build pays nothing. A run without the tag skips the tests that need them and says so (`TestFailingCalls`, `TestRefusedCalls`, `TestLifecycleHooks`), so use the tag for the whole suite.

`TestFault*` (`internal/cengine/fault_test.go`, with `-tags testhooks`) make the engine fail on purpose by calling its entries with what no caller gives: a read and a write through a pointer to unmapped memory (0xdead0000, 1 << 46, 0x4000, which is below the code Go links at 0x10000 on linux/arm64, and one that is not canonical on amd64), an entry given a shadow stack with nothing left, `abort`, and a trap (`callOverrideHook` answers the `host_call` of the abort itself so that the code after it, the call of `host_trap`, runs). Each must be a panic that recovers, with the VM broken so that every entry but `Close` returns `ErrBroken`, the host holding no memory after `Close`, the goroutine's `SetPanicOnFault` as it was, and a new VM running a script in the same process. `TestFaultsAmongVMs` makes 40 of them beside 4 goroutines that run scripts on VMs of their own. `TestFaultNoSplit` faults in `strlen` called from `js_strdup`, two functions without a stack check (the generator's NOSPLIT list, `noSplitList`), from fresh goroutines that make the call at every 8 bytes over 8 KiB of their stacks: below such a chain the generator leaves room for the call of `runtime.sigpanic` that a fault adds and for its call of morestack. `TestSampleRuns/nosplit_fault` of the generator does the same on a sample whose chain is 24 calls deep, from goroutines that start with the smallest stack, and requires faults where only sigpanic grew the stack. It also checks that the linker refuses a NOSPLIT recursion and a chain too deep for its room. The same faults, and a division by zero, run on the generated code of the proto package (`testdata/fault_test.go.txt`) for arm64 too: generate it on linux/amd64 with `ARCH=arm64 OUT=internal/goasm/gen/internal/proto-a64 sh internal/goasm/gen/proto.sh`, copy the folder to a Mac and run `go test -vet=off` on it. `TestBigFrames` looks for the frames of a package named `proto`, so name the folder `proto` there, or it fails on the names alone. `go test -run '^$' -bench 'Enter|EvalTiny' ./internal/cengine` and `-bench EnterLeave ./internal/gohost` give the cost of an entry, `SetPanicOnFault` included.

The poll tests (`internal/cengine/poll_test.go`) need an engine generated with `-poll` and skip themselves without it. `TestPollEveryCycle` runs tight loops of the interpreter (with the loops that jump back through `do while`, a `continue` to a label, a catch, a `finally` block and `with`, and a function of 3000 lines with no jump) and of the C (typed arrays, regexps, string searches, `repeat`, sorts, JSON) and the allocation scripts with the default interval and with an interval of 1, which makes every count poll: the results must be the same, which shows that a poll keeps what the generated code holds in registers. `TestGCInTightLoops` runs them while another goroutine keeps starting collections. `TestInterrupt` stops endless scripts in each place that reads the interrupt flag with `InternalError: interrupted`, and the VM runs code and catches exceptions after it. `TestInterruptOneProc` does it with `GOMAXPROCS=1`, where the goroutine that calls `Interrupt` runs only when the engine's goroutine stops at a poll. `TestKill` kills a script that does not read the flag in time: `ErrKilled`, a broken VM, `SetPanicOnFault` as it was, and a new VM that runs. `TestTimeout` stops an endless loop at the timeout of the VM, each `Eval` with the whole timeout, and kills a join once the grace after the deadline is over. `TestNoKillOutsideScripts` calls `Interrupt` over and over while the VM collects, with a grace of 0 and a poll on every cycle, and nothing is killed. The generator's `TestPassPolls` (`internal/goasm/gen`, with `SLOWJS_LLVM` and `SLOWJS_SHADOW_PASS` set) checks where the pass puts the counts, in a register or in memory, and that the pass's own check stops on each fault `-shadow-poll-fault` puts in: a count whose test never polls, an interpreter without the count of its entry, marks of the interpreter without their counts, and a count kept in a register that is not written back before a call that may poll, not read again after it, or not written back where its loop is left. `TestInterpreterJumpsCount` (`internal/goasm/gen`, no LLVM needed) reads `JS_CallInternal` in `engine/quickjs.c` and fails when `pc` moves other than by a constant step forward, `JUMP_TO` or `JUMP_COUNTED`, when those stop counting, when the entry count does not come first or when `OP_nop` does not count, and checks that copies of it with each of these broken fail. `unit-white` checks `check_polls` and `insert_polls` (below).

`TestShadowStackAtDepth` and `TestShadowStackInternalDepth` (root package) read the highest word of the shadow stack that is not zero after 30 kinds of recursion and 11 of C recursion, and log the bytes a level takes. Every recursion must end in a `RangeError`, and one with an ordinary frame must leave a quarter of the stack. `TestMapRefusedSweep`, `TestMapRefusedAmongVMs`, `TestReleaseRefused` and `TestRemapRefused` (`-tags testhooks`) make `hostmem.SetFault` refuse the system's chunks, releases and remaps in the middle of a script, for each chunk in turn and for one of four goroutines: the call that was refused ends in out of memory, `Close` leaves nothing mapped, and no other VM fails. `TestInterruptStopsLongBuiltins` runs `replace`, `fill`, `join` and `normalize` on input that takes them longer than the 50 ms grace of the kill and requires that `Interrupt` stops them within 40 ms and that the VM is not killed. A new built-in with a long loop belongs in it. `cmd/gcpause` and `cmd/interrupt` run the scripts of `cmd/scenarios`, each of which stays inside one long operation: `fib`, regexps, `JSON`, string searches, `split`, `join`, sorts, `fill`, `normalize` and BigInt products. `gcpause` forces a GC every few milliseconds and reports the time the runtime waited for the VMs to stop. `interrupt` stops each script at random points and reports the time `Eval` took to return. [performance.md](performance.md#stability-under-load) has the numbers, with those of the ccgo engine to compare with.

`TestDeepRecursion` recurses to the engine's call depth limit and past it (a `RangeError`, no fault of the process). It needs an engine generated for the whole 32 MiB shadow stack (`-shadow-size-log2=25` of the generator) and skips itself for a smaller one, by the `shadowSizeLog2` that `engine_decl_<arch>.go` records, which `New` also holds the stack size to.

Two more runs of the same tests guard the calling convention between Go and the generated code. A poison build (`-poison` of the generator) writes garbage into the registers at each entry before the arguments are loaded, after each call before the result is read, and at each return: the tests must pass on it too. The preemption hammer keeps setting the stack guard of the goroutine in the engine so that the next generated function's stack check goes through the scheduler. It reports how many requests it made (writes of the guard), which is more than the preemptions that happened, as requests made before the scheduler answers merge. It writes into the runtime's `g`, hence a tag of its own:

```sh
CENGINE_HAMMER_N=3000 go test -tags cenginehammer -run Hammer ./internal/cengine
```

[allocator.md](allocator.md) says what is tested and how. `heap.sh` takes `-m MODE` for `asan-heap`, `asan-heap-iter` and `ubsan`. `asan-heap-iter` is `asan-heap` with `JS_MALLOC_USE_ITER`, the list of every allocated block that the engine does not use: it keeps the macro building, with the scenarios, the random sequences and `poison-test` passing. A change to `engine/heap.c`, `engine/tlsf.c` or the allocator part of `engine/quickjs.c` runs all of them, test262 in `plain` and `asan-heap`, `asan` over test262 for the system malloc, and a soak of 3000 renders of tifa's pages (`render.c`), whose count, blocks and footprint must not grow after the first hundred.

## The race detector

The engine itself has no shared state, but the registries of Go functions, the lazy setup of error stacks and intl's shared locale data are shared by every VM of the process. Run these with `-race` after touching them:

```sh
go test -race -run 'TestInterrupt|TestConcurrentVMsMemory|TestErrorStackConcurrent' .
go test -race -run TestErrorStackFirstUseRace .       # on its own, so no other test made a stack first
go test -race -run 'TestConcurrentVMs|TestRegistryConcurrent|TestRegistryGoIntlConcurrent' ./intl
go test -race -run QJS ./internal/gointl               # the packs go-intl's loaders add to Embedded
go test -race -run 'Concurrent|Tamper|Clock' ./temporal  # Temporal on VMs at once, pages changing built-ins, clocks per VM
go test -race -tags testhooks ./internal/hostmem         # VMs mapping memory on many goroutines, and one VM handed between them
```

The whole of `./intl` under `-race` takes about 25 minutes on one core of an EPYC, most of it the golden test: give it `-timeout 60m`.

The race detector ignores atomic operations on memory outside Go's heap, such as the interrupt flag in C memory. `Interrupt` and `Close` meet at a mutex on Go's heap for that reason (see [architecture.md](architecture.md#the-eval-timeout-and-interrupt)).

## Every target

```sh
make build_all_targets
```

It builds every package and compiles the tests of every package (not only the root), each package to a test binary of its own, as two packages share the name `gen`, for the two targets the engine runs on (linux/amd64 and darwin/arm64), plain and with `-tags testhooks`. It takes a long time. For a quick look, build the main ones:

```sh
for t in linux/amd64 darwin/arm64; do
	GOOS=${t%/*} GOARCH=${t#*/} go build ./...
done
```

A build for any other target fails with the error of `internal/unsupported` and no other (`TestEngineUnsupportedTarget` checks it for windows/amd64, darwin/amd64, linux/arm64 and linux/386).

## go.work

There is normally no `go.work`. The whole repository, `make benchmark` in `compare/` included (it reaches the root module through its `replace`), builds and tests in plain module mode. `go.work` is ignored and `make clean` deletes it: treat it as a temporary tool, not as configuration.

Make one with `make work` for one case only: working on a module next to this one (tifa, for example) against this checkout. Delete it (`make clean`, or `rm -f go.work go.work.sum`) when you are done, or the tree keeps building against whatever is in the working copy next door instead of the version in `go.mod`.

While a `go.work` exists it must keep listing `./compare`. A workspace is found by walking up from the current folder, so it also governs builds inside `compare/`, which then fail with `main module (github.com/liustack/slowjs) does not contain package github.com/liustack/slowjs/compare`. `make work` writes the current toolchain into the `go` line: a `go.work` left over from an older toolchain, below the `go` version of `compare/go.mod`, breaks `make benchmark` with `module . listed in go.work file requires go >= …`.

## Developer tools: generate, check, time

Make targets run the work on the machine you are on. Linux with LLVM 22.1.8 (`/usr/lib/llvm-22/bin`, `LLVM_BIN` changes it) is all that `make gen` and the generator tests of `make check-*` need. `make remote` runs the same targets on another machine over ssh, for a Mac or a laptop without LLVM.

### Generate and check

```sh
make gen                       # the engine into internal/cengine: the pass, the generator, a formal build (-release)
make gen ARCH=arm64            # the other architecture, next to the first
make check-gen                 # the files checked in are what the generator makes now, for both architectures
GEN_KEEP=.build/gen-base make gen    # also keep a copy of the generated files
CHECK_LIST=1 scripts/check.sh full   # the steps and their tier
make check-fast                # every commit
make check-full                # the end of a batch
CHECK_ONLY="goasm root" make check-full     # some steps (CHECK_SKIP leaves some out, CHECK_STOP=1 stops at the first failure)
```

The generated engine is checked in: `internal/cengine` holds the `.s`, `engine_decl_<arch>.go` and `engine_keep_<arch>.go` files of amd64 and arm64 (about 15 MiB, 3 MiB compressed), because a user of the module has no LLVM. A change to the C of `engine/`, to the generator or to the flags of `scripts/gen-engine.sh` goes in with the files made again by `make gen` and `make gen ARCH=arm64`, in the same commit, and `make check-gen` fails when they are not. It compares the bytes in the git index, so run `git add internal/cengine` after `make gen` and before `make check-gen`. The generator gives the same bytes whatever `GEN_JOBS` and whichever folder it runs in.

`scripts/gen-engine.sh` checks the LLVM version, rebuilds the pass when its sources changed, builds the generator and runs it with the flags of a formal build (`GEN_RELEASE=0` allows the survey and test switches and says so). `scripts/check.sh` runs its steps one after another, writes a log for each under `.build/check-logs/` (`CHECK_LOGS` changes it), goes on after a failure and ends with one table. Skips inside `go test` are counted and named in the table, because a skipped test checked nothing: the one expected skip is `TestVarargsNative/aarch64`, which wants `ld.lld` and an aarch64 emulator. The steps that need the engine use the one checked in, so run `make gen` first only after a change that needs new files.

| Step | Tier | What it runs |
| --- | --- | --- |
| `build`, `gofmt`, `docs` | fast | `go build ./...`, `gofmt -l -s .` (generated files left out), `scripts/docs-list.sh --check` |
| `goasm` | fast | the tests of `internal/goasm/...` with `SLOWJS_LLVM`, `SLOWJS_SHADOW_PASS` and `SLOWJS_LLD` set, so that they do not skip |
| `cengine` | fast | `go test -tags testhooks ./internal/cengine` |
| `host-plain`, `compare-plain`, `cycles` | fast | `engine/test/build.sh plain`, `compare.sh plain`, `cycles.sh` |
| `gen` | full | `scripts/check-gen.sh` (`make check-gen`): generates both architectures into `.build/check-gen/` and requires every file of `internal/cengine` to be the same bytes, with none missing, none left over and none outside git. What is checked in is what the git index holds (an ignored file is not, and `git add` the files after `make gen`), the folder has to be the same bytes, the generated files are found by their `Code generated` header anywhere in them, and the names of an older generator (`engine_decl.go`, `engine_keep.go`, `engine_negative.go`) count as left over with or without it |
| `math` | full | `engine/test/math.sh` (about 4 minutes, most of it hashing in the shell) |
| `testhooks` | full | `go test -tags testhooks ./internal/gohost ./internal/hostmem ./internal/idtable` |
| `root` | full | `go test -p 1 .` |
| `race` | full | `go test -race -short -p 1` of the root package and the three above |
| `host-asan`, `compare-asan`, `host-ubsan`, `compare-ubsan` | full | `engine/test/build.sh` and `compare.sh` under the sanitizers |
| `test262` | full | `engine/test/test262.sh -m plain -T 2` |

The list is in `scripts/check.sh`. A new check goes there and into the table above.

### Time one build against another

A speed result is read at several code positions (see [Code positions](performance.md#code-positions)). `go tool sjdev bench` (the Go program in `internal/sjdev`, standard library only, registered as a tool in `go.mod`) makes the positions, runs them in turn and reads the result by that rule. `make bench ARGS="..."` runs the same.

```sh
# 1. a binary per position for each side. Generate the engine in each tree first (make gen).
go tool sjdev bench build -side base -tree ../base -app ../tifa -pkg ./test/ssr -test -out bin
go tool sjdev bench build -side new  -tree .       -app ../tifa -pkg ./test/ssr -test -out bin   # -positions all for 8
# 2. run them in turn, 5 rounds. Records are appended to the file, so a stopped run goes on.
go tool sjdev bench run -bin bin -out shop.jsonl -kind shop -rounds 5 -parse gobench:p50-ms \
    -dir ../tifa/test/ssr -env TIFA_SSR_SHOP=1 -env GOMAXPROCS=1 -cpu 1 -sib 5 \
    -- -test.run '^$' -test.bench 'Shop/^render' -test.benchtime 100x
# 3. the result, as a Markdown table
go tool sjdev bench report -in shop.jsonl -kind shop -base base -new new          # -detail adds each position
```

- `bench build` copies the generated `*_amd64.s` files, moves the code with `internal/goasm/cmd/xform` (the whole program by 0 or 32 bytes, the body of the interpreter by 0, 8, 16 or 24) and builds with `go build -overlay`, so the tree is not touched. A position is written `shift.front`, such as `32.16`. `quick` is 0.0, 0.16, 32.0 and 32.16. The interpreter is `JS_CallInternal_block` in the generated assembly, since it takes its arguments in a block, and `bench build` finds that name by itself. With `-app`, it builds in that module (tifa) through a `go.work` it writes. Only amd64 has positions.
- `bench run` runs the binaries as `side@position` in a random order per round (the order depends on the round only, so a restart repeats it), and both sides of a position one after the other. With `-cpu` and `-sib` it reads `/proc/stat` and runs a process again, up to 3 tries, when the sibling hyperthread or other work was busy while it ran. `-parse gobench:UNIT` reads the UNIT metric of each Benchmark line, `-parse jsrun` the median of the `eval:` line of `jsrun`.
- The memory of a process is the `vmhwm-kb: N` line it prints itself (`internal/sjdev/hwm`, which `jsrun` uses). Reading the peak of a child with `wait4` is wrong: the child starts with the peak of its parent.
- `bench report` takes, for each metric and position, the median over rounds of the paired ratios of the two sides, then the median over positions, and the range of the base's own positions. It calls a change "faster" or "slower" only when it is over 2% **and** over half of that range **and** most positions agree on the sign. A change under 3% is marked "see callgrind": count instructions instead.

```sh
go tool sjdev bench cg -bin bin/base@0.0 -bin bin/new@0.0 -small 2 -big 12 -out cg \
    -- -test.run '^$' -test.bench 'Shop/^render' -test.benchtime {N}x    # instructions per render, side by side
go tool sjdev bench cgdiff -renders 10 small.incl big.incl                  # the same from callgrind_annotate files you have
```

`bench cg` runs valgrind's callgrind on each binary twice and takes the difference, so that loading and compiling cancel. `-valgrind-root DIR` names a folder with `usr/bin/valgrind` inside when valgrind is not installed (`apt-get download valgrind` and `dpkg -x` into a folder is enough). Collect inside one function with `-toggle`.

A run on the same code on both sides (an A/A run) must say "no change" for every metric. Do one after a change to the tool or to the machine.

### On another machine

`scripts/remote.sh` (POSIX sh) runs a make target on a machine you can reach with ssh, in the background, in a checkout of its own, on chosen cores under a memory cap. Nothing about the machine is in the repository: it all comes from the environment.

```sh
export SLOWJS_REMOTE=user@host SLOWJS_REMOTE_DIR='~/work'     # the machine and a folder it may own
export SLOWJS_REMOTE_CPUS=1,5 SLOWJS_REMOTE_MEM=4G           # optional: taskset and a systemd memory cap
make remote RUN="gen"                          # HEAD, as the tree "main" on the machine
make remote REF=my-branch TREE=new RUN="check-fast"
make remote RUN="bench ARGS='run ...'" SLOWJS_REMOTE_CPUS=1      # a timing job on one core, its sibling idle
scripts/remote.sh -g shop.jsonl HEAD -- make bench ARGS='report ...'      # copy a file back to .build/remote/
```

- Push the branch first. The machine fetches the commit from the git remote `origin` (the machine needs access to it, and `. ~/.profile` runs before the target). A commit that is not pushed, or that the machine cannot fetch, goes as a git bundle with only what the machine lacks. A tree is a clone of its own that shares the objects of `DIR/repo.git`, never a git worktree. A new commit moves the tracked files only: the generated engine and `.build/` stay.
- The log of the target is printed (its last 40 lines) and saved in `.build/remote/`. `-w SECONDS` (default 3600) is how long to wait, then the script exits with 124 and the job goes on, with its log and done file in `DIR/jobs`. The exit status is the target's.
- Cores: a timing job uses one core and leaves its hyperthread sibling idle. Builds and checks may use both. Keep to the cores that are yours when the machine is shared.
- Nothing here kills a process. A job you started is stopped through its own scope.

## CI

GitHub Actions (`.github/workflows/`) checks every push, and every pull request from a fork, on linux/amd64 (`ubuntu-24.04`) and darwin/arm64 (`macos-15`), the two targets of the C engine. It checks that things are right and times nothing: shared machines are too noisy for that, so timing stays on the build machine.

`ci.yml` has these steps, each one on its own so that the run page shows how long it took (8 to 12 minutes in all on both platforms with a warm Go cache, most of it the root package and the native C engine):

| Step | What it runs |
| --- | --- |
| Build, Vet | `go build ./...` and `go vet -asmdecl=false ./...` |
| Format and docs | the `gofmt` and `docs` steps of `scripts/check.sh` |
| Test, packages other than the root | `go test -count=1 -short -p 2` on every package but the root one |
| Test, internal packages with the test hooks | `go test -tags testhooks` on `internal/cengine`, `internal/gohost`, `internal/hostmem` and `internal/idtable` |
| Test, root package | the `root` step (`go test -p 1 .`) |
| Native C engine | the `host-plain` and `compare-plain` steps: `engine/test/build.sh plain` and `compare.sh plain`, built with the C compiler the runner has (clang on both, so nothing is installed) |

`llvm-steps.yml` is a second workflow with one job, on linux/amd64 only, that installs LLVM 22.1.8 from apt.llvm.org (15 to 25 seconds, the version `scripts/gen-engine.sh` insists on) and runs these steps. It stops a commit that leaves the checked-in generated engine different from what the generator makes from `engine/`:

| Step | What it runs |
| --- | --- |
| Generated engine | `make check-gen` (`GEN_JOBS=4`): the `.s` and `engine_*` files of amd64 and arm64 against a fresh `make gen` |
| Generator and cycles | `CHECK_ONLY="goasm cycles" scripts/check.sh fast`: the tests of `internal/goasm` (the generator) and the check that every recursion of the C engine is counted |

The steps of `scripts/check.sh` are chosen with `CHECK_ONLY`, and their logs are kept as an artifact for 7 days. The skips in them are expected ones: `TestStackResidency` wants `HOSTMEM_RESIDENCY=1`, and the remap tests and `TestStackWithoutHugePages` are linux only.

`go-latest.yml` runs the C engine tests (`internal/cengine`, `internal/gohost`, `internal/hostmem`, `internal/idtable` and the root package) on the newest stable Go once a week, on both platforms. The checked-in assembly relies on details inside Go, and this finds out early when a new release changes one. It does not block merging. A red run is a reason to look at what the new Go changed.

Left out on purpose:

- **test262, the race detector and the sanitizer builds.** They take long. Run them with `make check-full`.
- **Timing and memory measurements**, `make gointl` (it clones go-intl) and `make build_all_targets`.

The job takes about 4 minutes on `ubuntu-24.04`: the install 15 seconds, `make check-gen` 2.3 minutes, the other two steps 1.1 minutes together. `clang --version` must print 22.1.8: if apt.llvm.org moves to a newer 22.1.x, pin the package versions.
