- Run on 2026-11-14 in one session, after [2026-11-14-v0.30.6-gcp-v8](2026-11-14-v0.30.6-gcp-v8.md), on another machine than that file. Scores of the two files are not compared.

## Which Hermes is "V1"

- The README of facebook/hermes and `doc/Branches.md` (branch `static_h`) say: development is on `static_h` (the default branch, named after Static Hermes), and its releases are what React Native calls Hermes V1. They are versioned apart from React Native, on branches `<version>-stable`: `260318099.0.0-stable` is the release of 2026-03-18 with bytecode version 99. The classic Hermes is the `main` branch and the `v0.x` tags (last `v0.13.0`), which `doc/Branches.md` calls the legacy line.
- The React Native 0.83 post (reactnative.dev/blog/2025/12/10/react-native-0.83) names Hermes V1 as the opt-in successor, with `hermes-compiler` 250829098.0.4. The release measured here is a later one.
- Hermes release rows: `260318099.0.0-stable`, head `fd22091391c38ea0111fdd45bd2693d2f50bfc6f` (2026-11-13, the grafts on that branch). It reports `Hermes release version: 1.0.0`, bytecode version 99.
- Hermes head rows: `static_h` at `44f5f48c3edfd3ae5c0b03f86486a1c7254bd30a` (2026-11-13). Bytecode version 100. Only this tree has the x86-64 JIT: `include/hermes/VM/JIT/Config.h` of the release branch enables the JIT on arm64 only.
- JIT default: the CMake option `HERMESVM_ALLOW_JIT` is 0 (off) unless set, so a default build has no JIT. In a build with `HERMESVM_ALLOW_JIT=1` the JIT is still off at run time until `-Xjit` is given (`RuntimeFlags.h`: "JIT mode (default off)"). `doc/JIT.md` calls it opt-in. So Hermes V1 on linux/amd64 runs its interpreter by default, and the JIT is an extra row.

## How Hermes was built and run

- Both trees: `cmake -GNinja -DCMAKE_BUILD_TYPE=Release -DCMAKE_C_COMPILER=clang -DCMAKE_CXX_COMPILER=clang++ -DHERMES_ENABLE_INTL=OFF`, clang 22.1.8, `ninja hermes hermesc`. Release tree: `-DHERMESVM_ALLOW_JIT=0`. Head tree: `-DHERMESVM_ALLOW_JIT=1`. Built on another server of the same type, copied here (the binaries link only system libraries, which `ldd` finds here). The binaries still list the system ICU libraries.
- `native/hermes-v8.js` is the driver. It runs the files of `internal/arewefastyet/v8-v7` as global scripts in one runtime, then `BenchmarkSuite.RunSuites`, as the other sides do. The Hermes shell has no way to read a file, so the driver uses `hermescli.loadFile` and `hermescli.loadHBC`, which exist only with `-Xhermes-internal-test-methods`, and takes its arguments after `--`.
- Hermes from source (`hrel-src`): `hermes -Xhermes-internal-test-methods hermes-v8.js -- src <dir>`. Each file is read and run with an indirect `eval`, so Hermes compiles it from source, with no `-O`. This is the closest to handing Hermes a source file.
- Hermes bytecode (`hrel-hbc`, `hhead-hbc`): each file compiled once by `hermesc -O -emit-binary -out <name>.hbc <name>.js`, then `hermes ... hermes-v8.js -- hbc <dir>` runs the `.hbc` files with `hermescli.loadHBC`. This is how React Native ships code. The compile is not timed. `hermesc` warns about the direct `eval` in `sc_jsNew` of earley-boyer and a repeated key, and compiles.
- Hermes head with JIT (`hhead-jit`): the same bytecode, with `-Xjit`.
- All 8 benchmarks of the suite ran on every Hermes row and gave a score, so each Hermes row has a suite score. No benchmark failed.

## Notes

- liustack/quickjs round 1 scored 1447 (Splay 3626), the other four 1516 to 1529 (Splay 4616 to 4738). The median is not affected.
- Hermes with the JIT varies most: NavierStokes ran between 6287 and 9137 across the rounds.
- Hermes is ahead of v0.30.6 on every benchmark but Splay and RegExp (equal for the release) when it runs bytecode. From source it is about equal on the score: it is ahead on RayTrace and EarleyBoyer and behind on Splay and NavierStokes.
- Hermes compiles each file once, ahead of the run, which this suite does not time. The Go sides and C QuickJS compile their source inside the timed run, which the suite times only as part of a benchmark's setup.
